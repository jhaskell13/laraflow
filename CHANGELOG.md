# Changelog

All notable changes to Laraflow are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until the first tagged release, breaking changes may land in any commit and are recorded under *Unreleased*.

## [Unreleased]

### Milestone 6 — compatibility, quality, and release readiness

#### Fixed

- **A `Retry-After` HTTP-date was read in the application's timezone rather than GMT.** `DateTimeInterface::RFC7231` escapes the literal `GMT` instead of parsing it as a zone, so `Wed, 21 Oct 2015 07:28:00 GMT` was read as local time: on an application running `America/New_York`, a four-hour error in both the in-attempt transport wait and the durable retry `OutcomeRecorder` scheduled. Any installation not running UTC retried hours early or late. The existing coverage passed only because the suite runs in UTC; the regression test now pins a non-UTC default timezone.
- **A next-page link was followed unchecked when a connector declared no base URL.** The same-host guard compared against the connection's host and returned early when there was none — so a connector built on absolute URIs would follow an absolute `Link` to any host with its `Authorization` header attached, which is exactly what the guard exists to prevent. An unverifiable link is now refused with `PaginationException::unverifiableHost()`.
- **`config/laraflow.php` declared `http` twice.** PHP kept the second silently, so the first block — the one under the *Integrations* heading — was dead configuration that an operator could edit with no effect. The duplicate and a stray heading left with it are removed; the surviving block is unchanged, so no default moved.

#### Changed

- **Fixed, found by the first real CI run:** the PHP 8.2 matrix cells could not resolve dependencies at all — `laravel/pint` raised its PHP floor to ^8.3 in a patch release (1.30.5), so the `^1.32` constraint was unsatisfiable on a platform the package declares support for. Pint is pinned to 1.30.4, the last 8.2-compatible version, until PHP 8.2 is dropped at its security end-of-life (December 2026); an exact pin because even its own patch series crossed the floor. Analysing under a *simulated* 8.2 platform (`config.platform.php`) — which the development machine's 8.3 could not see — also surfaced two real findings in `src/`: on PHP 8.2 `DateTimeImmutable::modify()` is typed as returning `false` on a bad format, so `RetentionPolicy::cutoff()` and the runner's timeout arithmetic now use `sub()`/`add()` with a `DateInterval`, which cannot. Both legs of the matrix were re-verified under the simulated 8.2 platform before pushing.

- **CI proves the dependency axis, not just the PHP one.** The workflow splits into a quality job — `composer validate --strict`, `composer audit` against the committed lock, Pint, PHPStan — and a test matrix of PHP 8.2/8.3/8.4 per supported Laravel major, pinned through Testbench so Laravel 13 becomes one matrix line. A `prefer-lowest` cell on PHP 8.2 resolves every constraint to its true floor (Testbench 10.0.0, Laravel 12.4.1, PHPUnit 11.5.3) and must pass the suite *and* static analysis there. Every leg was run locally before being committed; the floor surfaced two stub-drift defects — `ConnectorContract` now asserts `isNotEmpty()` rather than `assertNotEmpty()` on a collection, and a queue test reads the job row through `get_object_vars()` — fixed for both extremes rather than suppressed on one.

- **The test database driver is selectable.** `Laraflow\Tests\TestCase` builds the suite's connection from `LARAFLOW_TEST_DB_*` environment variables — driver, host, port, database, username, password — defaulting to the in-memory SQLite the suite has always used. Any driver the installed Laravel resolves is accepted; `mysql`, `mariadb`, `pgsql`, and `sqlsrv` get per-driver defaults (port, charset, strict mode, `search_path`). This is the seam the CI engine matrix runs through. SQL Server 2019+ joins `docs/compatibility.md` as *expected to work*; the same document now states explicitly that MongoDB is not a supported persistence backend and why, with a document-store driver recorded as Milestone 7 scope. A test that can only be staged on one engine skips elsewhere with a reason — the retention orphan test needs SQLite's `PRAGMA foreign_keys = OFF`, which no other engine lets a session do.

- **Static analysis covers the tests and the playground.** `composer analyse` runs PHPStan level 8 over `tests/` and `workbench/` as well as `src/` and `database/` — 260 files rather than 145. The 367 findings this surfaced are fixed rather than recorded: there is no baseline file, so a type error in a new test fails CI the same way one in the package does.

  Two thirds of them were a single upstream declaration. Testbench types `$app` as `Application|null` because it is null before the application is created; `Laraflow\Tests\TestCase` narrows it, which is true by the time any test method runs and avoids putting a null check in front of several hundred ordinary container calls. Most of the rest were nullable Eloquent lookups read straight through — `steps[0]->status` — which die with a PHP error about null instead of naming the missing row; the base test case grew `stepAt()`, `row()`, and `command()`, which assert first. That is 39 assertions the suite was not previously making.

  Six lines keep a `@phpstan-ignore`, each naming one identifier and carrying a comment: tests that deliberately pass a value the declared type forbids, to prove the runtime rejects it. `CONTRIBUTING.md` states that as the only accepted use.

- **Breaking:** `TransportException::$attempts` is no longer a public property; read it with `attempts()`. It stays settable only through `afterAttempts()`, which the retrying transport calls. (In-place rather than returning a copy: PHP exceptions cannot be cloned, and rebuilding one would move the throw site and lose the stack trace.)
- **Breaking:** a page budget below one is now `PaginationException` rather than `InvalidArgumentException`, consistent with every other pagination refusal. `pages()` is also no longer a generator itself, so that refusal — and a connector with no paginator — is raised when `pages()` is called rather than when a caller first begins iterating.
- A connection may set `rate_limit: false` to lift a ceiling configured under `laraflow.http.rate_limit`. Previously an inherited ceiling could be raised but never removed, so an account with its own quota was held to the fleet's. `RateLimitPolicy::fromArray()` accepts `false` alongside an array and `null`.
- `ConnectorContract` now asserts up front that it can actually intercept the connector under test. It works by stubbing Laravel's HTTP client, so a connector with a transport of its own was never reached by the fake and every assertion that followed passed without testing anything — or reached the real network. `assertHeldBy()` sends one probe first and fails with what to do instead.
- The bundled-connector internals check reads inline `\Laraflow\…` references as well as `use` statements; an internal class was reachable by writing it out in full.

#### Documentation

- `docs/connectors.md` attributed the "no Laraflow object in a connector's graph holds a credential" invariant to `ProjectContractsTest`; it is held by `SecretExposureTest`.
- The client-side rate limit is documented as **best effort**: its check and its count are not one atomic cache operation and workers waiting out a window wake together, so enough concurrency can run a window slightly over. The provider's own `429` and the durable retry behind it remain the backstop. Stated in `docs/connectors.md`, `config/laraflow.php`, and on `ThrottlingTransport`.
- `ConnectorContract`'s credential search is documented as stopping at the Laraflow namespace, and why, so what it does not catch is stated rather than implied.
- `CONTRIBUTING.md` records the analysis scope, the no-baseline rule, the single accepted use of `@phpstan-ignore`, and the test-case helpers.

#### Playground

- `playground:watch` gains `--frames=N`, stopping after N frames; `0` keeps the existing behaviour of drawing until interrupted. The watch loop needed a condition that was actually a condition, and a bounded one is what lets a script capture a fixed number of frames without `--once`'s single-frame layout.
- The three playground commands share a `ReadsInput` trait (`stringArgument()`, `stringOption()`) instead of casting console input — typed `array|bool|float|int|string|null` — straight to string.

### Milestone 5 — integration framework hardening

Contract in `docs/connectors.md`; the retry interplay in `docs/retry-and-failure-policy.md`; provider API expectations in `docs/compatibility.md`.

#### Added

- **Named connections.** A connector is registered once and resolved per connection: `connector('github')` for the configured default, `connector('github', 'enterprise')` for another account served by the same class. Connections are configured under `laraflow.integrations.{connector}.connections.{name}`; `laraflow.integrations.{connector}.default` names the one used when a caller names none. `LaraflowManager` gains `connectors()`, `connections(name)`, and `forget(?name, ?connection)`.
- **Configuration-driven registration.** A class declared as `laraflow.integrations.{connector}.connector` is registered at boot and built through the container with its `Laraflow\Integration\Connection` (public) passed as `$connection`, so a connector declares its other dependencies as ordinary constructor parameters. The bundled GitHub connector is registered this way — one `integrations` entry among any the application adds, with no privileged path. Closures still work and now receive the `Connection`. A misnamed class fails at boot with `InvalidConnectorException`.
- **A strict configuration shape.** A connector section holds `connector`, `default`, and `connections`, nothing else. A setting left at the connector level — the Milestone 0 `integrations.github.token` — is refused with `ConnectorConfigurationException` (public) naming the path it belongs at, rather than being silently read by nothing. An unknown connection raises `ConnectionNotConfiguredException` (public) naming the configured ones. `Connection::require()` treats a blank value as missing and names the configuration path and, when given, the environment variable.
- **Credentials resolved per request** through the `CredentialProvider` contract (public), bound by interface so an application can read a vault or a per-tenant store. The default reads `…connections.{name}.credentials` from the config repository on every call. Rotation therefore needs no rebuild and no restart: the next request uses the new value. The `credentials` key is stripped from the `Connection` a connector holds, so the object a connector keeps for its lifetime carries settings only.
- **`Laraflow\Support\Secret`** (public): a credential that renders as `[redacted]` in string context, `json_encode`, `print_r`, `var_dump`, `var_export`, the array cast, and `serialize`, and yields its value only to `reveal()`. The value is held in a `WeakMap` rather than a property because `var_export` and the array cast read properties directly and ignore `__debugInfo`. An unserialized `Secret` has no value — a credential that rode through a queue payload or a cache would otherwise sit there in clear text — and `reveal()` on it throws `SecretRedactedException` (public). `Credentials` (public) is the bag of them for one connection.
- **`Laraflow\Integration\HttpConnector`** (public): the base class for connectors that speak HTTP. A subclass declares its provider — `baseUrl()`, optionally `headers()` and `authenticator()` — and inherits `request()`: resolve this request's credentials, authenticate, send. The constructor is satisfied by the container when the registry builds the connector. `GithubConnector` is now twenty lines on it.
- **A transport seam.** `HttpTransport` (public contract) puts the authenticated request on the wire; `LaravelHttpTransport` (internal, the default binding) does so through Laravel's HTTP client, so `Http::fake()` and the client's middleware keep working. Bind another implementation to replace the wire for every connector, or override `transport()` on one. The transport merges connection headers under request headers itself, because the client's own merge is recursive and turns two values for one header into a list. Its `$request` parameter is `#[\SensitiveParameter]`: the authenticated options are in it.
- **Configurable HTTP behaviour**, resolved connector class → connection → `laraflow.http` defaults: `HttpOptions` (public) carries `baseUrl`, `timeoutSeconds`, `connectTimeoutSeconds`, and default `headers`. A connection sets `base_url`, `timeout`, `connect_timeout`, `headers` to point the same class at a sandbox host or give one account a longer wait. New config section `laraflow.http` with `timeout` (30) and `connect_timeout` (10). Timeouts must be positive and the base URL a URL, checked at construction and reported with the connection's path.
- **Responses keep the body as received.** `ConnectorResponse` is built from the raw body and decodes explicitly and lazily: `json()` decodes whatever the server declared and refuses malformed JSON with `ResponseDecodingException` (public; names status and content type, never the body), `body()` gives the decoded value when the server declared JSON and the raw string otherwise, `raw()` the bytes, `header()` a case-insensitive lookup. An HTML maintenance page and a JSON `null` were both `null` before and could not be told apart. `ConnectorResponse::fake()` builds one for tests and replacement transports; `toArray()` is a durable form for step output.
- **Typed errors, mapped per provider.** `ErrorMapper` (public contract) decides whether a response is an error and which kind; `StatusErrorMapper` (public, the default) goes by status — 401/403 `AuthenticationFailedException`, 404 `NotFoundException`, 429 `RateLimitedException`, other 4xx `ClientErrorException`, 5xx `ServerErrorException`, all under `Laraflow\Exceptions\Connector` and extending `RequestFailedException`, which carries the response. A connector supplies its own via `errorMapper()`: the bundled `GithubErrorMapper` reads a 403 with `X-RateLimit-Remaining: 0` as rate limiting, which by status alone would be an authentication failure and so never retried. `RateLimitedException::retryAfterSeconds(now)` reads delay-seconds or an HTTP-date against the caller's clock.
- **Errors are returned, not thrown.** `request()` attaches the mapped exception to the response: `failed()` is then true even for a `200` the mapper rejected, `error()` returns it, `throw()` raises it (or a generic `RequestFailedException` for an unmapped error status). A connection sets `throw_on_error` to make `request()` throw instead. The default preserves the Milestone 0 contract that an error status is a result to inspect.
- **A safe-reporting chokepoint.** `RequestFailedException::fromResponse()` is the one place a provider error becomes a message, and it is given the request *as the caller made it*, before authentication — so nothing an authenticator added can reach a message — and names the path alone, because a query string may carry a token. The provider's detail is taken from the usual JSON fields and truncated.
- **In-attempt transport retries, off by default.** `TransportPolicy` (public; `laraflow.http.retries`, overridable per connection) repeats one wire request inside a single step attempt — for a dropped connection or a momentary 503 — with millisecond backoff and deterministic jitter. It is the *inner* loop to the step policy's durable *outer* one, and three rules keep them from multiplying: it ships with `max_attempts` = 1; it never waits in-process for a `Retry-After` longer than `max_retry_after` (5 s) but returns the response so the step can fail and retry durably on the provider's schedule; and a non-idempotent request is repeated only on 429 — never processed — or when the caller marked it `asIdempotent()`. `ConnectorRequest` gains the `idempotent` flag and `isIdempotent()`; `ConnectorResponse` gains `attempts()` and `retryAfterSeconds(now)`. Applied by `RetryingTransport` (internal), assembled by `TransportPipeline` (internal) only when enabled, waiting through a `Sleeper` (internal) so tests record the waits instead of serving them. Specified in `docs/retry-and-failure-policy.md`.
- **A provider's `Retry-After` drives the durable retry.** `Laraflow\Exceptions\SuggestsRetryDelay` (public contract): an exception that knows when another attempt could succeed. When a step fails with one and its policy allows a retry, `OutcomeRecorder` schedules the retry no sooner than the suggestion — up to the new `laraflow.retry.max_suggested_delay` (3600 s) — and never sooner than the policy's own backoff. `RateLimitedException` implements it with the provider's `Retry-After`, so a 429 that says "wait 600 seconds" becomes a `retrying` execution due in 600 seconds, with the worker released. Any application exception may implement it. This is a deliberate extension of the Milestone 3 retry contract, recorded in `docs/retry-and-failure-policy.md`.
- **Client-side rate limiting, off by default.** `RateLimitPolicy` (public; `laraflow.http.rate_limit`, or a connection's `rate_limit` with `max`, `per`, `max_wait`) is a ceiling Laraflow holds itself to per connection, counted through Laravel's cache-backed `RateLimiter` so every worker shares the budget and keyed per connection so one tenant's account never throttles another's. A wait up to `max_wait` seconds is served in-process; a longer one fails the request *before it reaches the provider* with `ThrottledException` (public), which suggests the wait — so with a step policy the execution comes back when a slot is due. Applied by `ThrottlingTransport` (internal), inside the retry decorator so a retried attempt is counted like any other. Dependency: `illuminate/cache`, already present transitively and now declared.
- **Lazy, bounded pagination.** `HttpConnector::pages()` yields responses and `::items()` yields the items across them, both generators — a long result set never exists in memory at once, and a caller that stops early fetches nothing more. The `Paginator` contract (public) is supplied per connector by `paginator()`; three shapes ship: `LinkHeaderPaginator` (RFC 8288, GitHub's shape, now used by the bundled connector), `CursorPaginator` (Slack's shape), and `PagePaginator`. Four things are refused rather than tolerated, all as `PaginationException` (public): reaching the page budget (`laraflow.http.pagination.max_pages`, 100, overridable per connection and per call) is **an error, not a quiet stop**, because a short list that looks complete is the worst thing a paginator can hand back; a provider that repeats a page is caught rather than looped until the budget; a connector with no paginator says so; and a next-page link to a host the connection never named is refused, because the transport sends an absolute URL as given and the request carries an `Authorization` header. A failed page throws rather than ending the iteration quietly. `docs/retry-and-failure-policy.md` and the README state that pages must not be accumulated into step output, which `max_payload_bytes` would reject.
- **Connector events and log context.** `ConnectorRequestSent` (every response the provider gave; `successful` is false for an error status *or* a 200 the mapper rejected) and `ConnectorRequestFailed` (no response at all — a connection failure, or Laraflow's own throttle refusing to send) carry connector, connection, method, **path without the query string**, status, `durationMs` for the whole call including transport retries and throttle waits, and `attempts`. No headers, options, or bodies; the failure message passes the configured `ErrorRedactor` and honours `events.include_error_messages`. They carry no correlation id by design — a connector may be called outside any workflow, and inside one the log context already has it. While a request is in flight, `laraflow.connector` and `laraflow.connection` join Laravel's log context, restored afterwards including on failure. Applied by `ObservingTransport` as the outermost pipeline layer, so one logical call is one event measuring what the caller actually waited.
- **`laraflow:connectors {connector?} {--check}`** (experimental): every registered connector, its connections, base URL, timeout, retry and rate-limit settings, and the **names** of the credentials each connection resolves — never their values, because the point is to tell an operator a credential is present without putting it on a shared terminal. `--check` resolves every connector, reports what will not build, and exits non-zero so it can gate a deploy; it sends no requests. Without `--check`, one broken connection does not stop the listing.
- `LaraflowManager::connection()` and `HttpConnector::options()` expose a connection's resolved settings (never its credentials), which is what the command reads.
- **A second real connector: Slack** (`SlackConnector`, `SlackErrorMapper`, both experimental), added only after the generic contracts were tested and chosen because it behaves nothing like the first. It exercises what GitHub does not: a provider that reports failure inside a `200` (`{"ok": false, "error": "channel_not_found"}`), cursor pagination whose result key differs per endpoint, and methods that are mostly non-idempotent POSTs. Its error codes map onto the **shared** exception types, so an application catches `AuthenticationFailedException` without knowing which provider raised it. `read()`, `write()`, and `listing()` build its requests and paginators.
- **The exit criterion is now a test.** `ProjectContractsTest` reads every bundled connector's imports and fails if one depends on a class marked `@internal`: if Laraflow's own connectors needed something a third-party package cannot reach, the extension points would not be finished. Both bundled connectors pass on the public contracts alone.
- `HttpConnector::pages()` and `::items()` take an optional `Paginator`, overriding the connector's own for providers whose result shape differs per endpoint.
- **A published contract test** (`Laraflow\Testing\ConnectorContract`, public): the assertions a connector should satisfy, shipped so connectors Laraflow does not ship can be held to the same standard as the ones it does. It checks that a connector holds no credential, classifies every error status into the shared exception types, returns errors rather than throwing them, and keeps both the credential and the query string out of every message. A plain object rather than a base test case or a trait — it collides with nothing in the host test and works from PHPUnit, Pest, or Testbench. It fakes HTTP with stray requests prevented, so it needs no credential and no network. Both bundled connectors are tested through it, and two deliberately broken fixtures prove it fails when it should.
- **A connector contribution recipe** in `CONTRIBUTING.md`: six steps, none of which involves editing a Laraflow file — and if a contributor finds themselves wanting to, that is recorded as a bug in the extension points rather than a normal step.
- **Provider API versions.** A connector declares the version it was written against (`apiVersion()`) and the header it travels in (`apiVersionHeader()`); a connection pins another with `api_version`. The GitHub connector pins REST `2022-11-28` as `X-GitHub-Api-Version`; Slack declares none, because its API has no versions, and `laraflow:connectors` shows it as *unversioned* rather than blank. `docs/compatibility.md` gains a *Provider APIs* section stating what a pinned version promises — handling the shapes the provider documented for it, proven against fakes — and what it cannot: that the provider still sends them.
- **The playground gains connectors.** `laraflow:connectors` joins the walkthrough, and the workbench-only `playground:call {connector} {uri}` sends one real request through a connector and shows what the framework did with it — the mapped error type, the wire attempts, the duration, and the events announced. It lives in `workbench/` because a command that fires an arbitrary request at a production API has no business being installable into an application.
- **The closing audit** extends `tests/Feature/ProjectContractsTest.php` with the milestone's invariants: every connector authority ships off (transport retries, rate limit) and every bundled connector ships without a credential; every connector exception an application can catch is in `public-api.md`; every `HttpTransport::send()` marks its request `#[\SensitiveParameter]`; no connector event carries a parameter that could hold request or response content.
- `TransportException::connecting(host, previous)`: the message names the host alone — not the URL, whose query string may carry a token, and not the options.
- **`BearerTokenAuthenticator`** (public) replaces `GithubTokenAuthenticator`: `Authorization: Bearer` from a named credential, reading it from the `Credentials` passed to every call.
- `tests/Feature/Integration/SecretExposureTest.php`: the milestone's secrecy exit criterion as a sweep. Every value object is rendered every way PHP offers, every property of every Laraflow object reachable from the connector and the manager is walked, and every Laraflow stack frame of every exception the layer raises is checked — none may contain the token.

#### Decisions

- **Errors are returned, not thrown.** An error status stays a result to inspect; the response carries the mapped exception, `throw()` raises it, and `throw_on_error` opts a connection into throwing. The Milestone 0 contract that `failed()` is a normal outcome is preserved.
- **Credentials are resolved per request, never captured at construction.** This is what makes rotation a configuration change and lets a cached connector carry nothing worth stealing.
- **`Secret` keeps its value in a `WeakMap`, not a property.** `var_export` and the array cast ignore `__debugInfo`; a property would leak through them. The cost — a `Secret` cannot be cloned — is stated.
- **A provider's `Retry-After` drives the durable retry, capped.** `SuggestsRetryDelay` extends the Milestone 3 contract deliberately: believed up to `retry.max_suggested_delay`, never below the policy's own backoff. Sleeping a worker for the provider's wait is what durable retries exist to avoid.
- **Transport retries are the inner loop and ship off.** Milliseconds, never waiting for a `Retry-After` beyond `max_retry_after`, never repeating a non-idempotent request except on 429 or when marked safe. Two retry systems again, kept from multiplying by construction.
- **A page budget is an error, not a quiet stop.** A short list that looks complete is the worst thing a paginator can produce.
- **A next-page link to a foreign host is refused.** The transport sends absolute URLs as given and the request carries credentials.
- **Connector events carry no correlation id.** A connector may run outside any workflow; inside one, the log context already has the identifiers.
- **The contract test is a plain object using PHPUnit's static `Assert`.** A trait in `src` used only from `tests` is invisible to static analysis of `src`, and analysing `tests` surfaced 344 findings that belong to Milestone 6.
- **Slack is the second connector** because it behaves nothing like GitHub. Both are held to the same published contract, and a test fails if either depends on anything internal.

#### Changed

- **Fixed, found reviewing the milestone:** a transport failure on a connector with no base URL named the full request URI — query string included — instead of the host; Guzzle's own transfer failures (too many redirects, a malformed response) surfaced untyped with the URL in their message, and are now `TransportException` too; a `ConnectorRequestFailed` event after exhausted transport retries reported one attempt, and `TransportException` now carries `attempts`; the `Link` header parser split on commas, which a URL may legitimately contain (`?ids=1,2`); Slack's mapper threw `ResponseDecodingException` on a malformed `200` body rather than deciding — a mapper decides, `body()` reports; `pages()` accepted a page budget of zero and returned one page as "the limit". Each is pinned in `tests/Feature/Integration/ReviewFindingsTest.php`.
- **Breaking:** `laraflow.integrations.github.token` moved to `laraflow.integrations.github.connections.default.credentials.token`. The old key is refused with the new path.
- **Breaking:** `Authenticator::authenticate()` gained a `Credentials` parameter; authenticators receive credentials rather than holding them. `GithubTokenAuthenticator` is removed.
- **Breaking:** `ConnectorResponse` is constructed from the raw body (`new ConnectorResponse(status, headers, raw)`); the `body` constructor argument is gone, and a non-JSON body is returned as received rather than as `null`. `successful()` is now 2xx *and* no error attached.
- **Breaking:** `LaraflowManager::connector()` gained an optional connection name, and closures passed to `register()` receive a `Connection`. A missing GitHub token is now reported on the first request rather than when the connector is resolved, because the resolved connector holds no credential to check.
- `GithubConnector` extends `HttpConnector` and sends `Accept: application/vnd.github+json`. `ConnectorFactory` and `ConnectorManager` (internal) are replaced by `ConnectorRegistry`. `ConnectorRequest` gains `withOptions()` and `withHeaders()`.
- **Fixed:** the README's custom-connector example registered an authenticator class the package does not ship.

### Milestone 4 — querying, observability, and lifecycle management

Contracts in `docs/inspection-and-observability.md` and `docs/retention.md`.

#### Added

- **Schema for correlation, queue lag, and retention** (existing migration edited in place, per the pre-release policy). `laraflow_workflow_executions` gains:
  - `correlation_id` and `tenant_id` — application-supplied identifiers tying an execution to the request, job, tenant, or external operation that caused it. Indexed columns rather than a metadata blob, because listing by them must stay a bounded indexed query on every supported engine.
  - `dispatched_at` and `available_at` — when the execution was handed to the queue, and when the queue was asked to make it runnable. These differ for a delayed retry, and queue lag (`claimed_at − available_at`) is meaningless without the distinction.
  - `finished_at` — one terminal timestamp written by `completed`, `failed`, and `cancelled` alike, and cleared when an execution runs again. Retention and "finished between" filters would otherwise need a three-way coalesce over `completed_at`/`failed_at`/`cancelled_at` that no index can serve.
  - `payloads_scrubbed_at` — when retention removed the execution's payloads, so a scrubbed record stays distinguishable from one that never carried any.
  - Indexes on `correlation_id`, `tenant_id`, `created_at`, `(workflow, status)`, and `(status, finished_at)`: every listing and retention filter the milestone will expose has an index behind it.
- **`Laraflow\Workflow\ExecutionOptions`** (public): the correlation and tenant identifiers an application records on an execution, supplied as an optional trailing argument to `WorkflowRunner::start()`, `WorkflowRunner::run()`, and `WorkflowDispatcher::dispatch()`. An options object rather than extra parameters so that recording more later does not change four signatures again. Validated at construction, before anything is persisted: trimmed, blank treated as absent (passing a missing request header is safe), rejected over 255 characters (silent truncation leaves an identifier that correlates with nothing), and rejected when containing control characters (these values reach log records, where a newline would let a crafted identifier forge a second line). Violations raise the new public `InvalidExecutionOptionsException`.
- **Identifiers reach every sink.** `WorkflowContext::correlationId()` and `::tenantId()` expose them to steps — read from durable state, so a step re-run by a recovering worker sees the originals rather than whatever ambient context that worker is in — and **all ten lifecycle events** carry them as trailing `correlationId`/`tenantId` properties. They are set at creation and never rewritten; `execute()` has no options parameter, so an execution's identity cannot change under recovery.
- **A stable listing API** on `ExecutionRepository`, so applications and consoles no longer need the internal Eloquent models: `list(ExecutionFilter, $limit, $cursor): ExecutionPage` and `count(ExecutionFilter): int`. `ExecutionFilter` (public) covers workflow(s), status(es), correlation id, tenant id, half-open creation and finish windows (inclusive start, exclusive end, so consecutive windows neither overlap nor leave a gap), and sort direction — and **every criterion is served by an index**, enforced by the migration test; a filter Laraflow cannot bound is a filter it does not offer. Pagination is **keyset**, not offset: the cursor identifies the last row of a page and the next page continues strictly past it, so a listing stays correct while rows are being inserted and costs the same on page 1000 as on page 1. Page size is clamped to `ExecutionRepository::MAX_PAGE_SIZE` (500), a constant on the contract so no implementation can forget the bound; the page reports the limit actually applied. A malformed cursor is rejected rather than guessed at.
- `ExecutionRepository::attemptHistory(WorkflowExecution)`: the attempt history of every step in one query, ordered by step position then attempt, using the execution id the attempts table has denormalised since Milestone 3 for exactly this purpose. `laraflow:show --attempts` moves onto it in step 5.
- **`laraflow:summary`** (experimental): execution counts by status for a scope (`--workflow`, `--correlation`, `--tenant`, `--since`, `--until`), followed by the three conditions worth attention — retries that are due, running steps past their deadline, and the oldest unfinished execution. **Exits non-zero when anything needs attention**, so a scheduler or deploy gate can use it as a health check. Not a per-workflow breakdown: that needs a `GROUP BY` the repository contract does not expose and should not gain for a console view, so `--workflow=` scopes the same numbers through an indexed filter instead.
- **`laraflow:prune`** (experimental): applies the retention policy, with every bound overridable per run (`--scrub-after`, `--prune-attempts-after`, `--delete-after`, `--delete-failed-after`, `--limit`, `--chunk`) and scopable by `--workflow` or `--tenant`. `--dry-run` reports what would go without touching anything. The command **exits non-zero when no bound is configured** rather than reporting a successful no-op — a scheduled prune that silently does nothing is indistinguishable from one that is working, until someone looks at the size of the attempt table. Because deletion is irreversible it uses Laravel's standard production confirmation, as `migrate` and `db:wipe` do, so schedule it as `laraflow:prune --force`; a dry run changes nothing and never asks. Policy warnings are surfaced before acting, a completed run logs its counts (deletions an operator cannot later account for are the ones they will want to account for), and only tiers the operator actually configured appear in the report.
- **Retention engine** (`laraflow.retention.*`, every bound `null` by default), applied by `laraflow:prune` — Laraflow never prunes on its own. Three tiers over finished work, measured from `finished_at` so a long-running execution is never pruned for having *started* long ago:
  - **Scrub** (`scrub_after_days`) clears input, context, and step outputs of `completed` and `cancelled` executions, keeping the record as an audit trail of what ran and when. **Never applied to `failed` executions**, which need their input and context to be re-executable; clearing them would leave a record that still advertises itself as recoverable and is not.
  - **Prune attempts** (`prune_attempts_after_days`) deletes the append-only history that grows without bound under retry policies. Applies to `failed` executions too: the step row keeps the latest attempt's status, error, and counter, and the retry budget reads that counter rather than this table, so nothing becomes unrecoverable.
  - **Delete** (`delete_after_days`) removes `completed` and `cancelled` executions outright; `failed` ones have their own `delete_failed_after_days`, kept separate because discarding recoverable work should be a decision rather than a side effect of configuring general retention.
- Retention guarantees, each covered by test: **only finished work is eligible** — `pending`, `running`, and `retrying` are invisible, since a retry waiting out its backoff is future work, not old work; **the guard is re-applied at every write**, so an execution claimed between scan and write (claiming sets `status = running` and clears `finished_at`) is silently spared, and its steps and attempts are spared with it; **every tier is bounded and self-limiting**, so a scheduled run cannot spend its limit rescanning work it has already done — delete removes the row, scrub requires `payloads_scrubbed_at IS NULL`, and attempt pruning requires that attempt rows still exist. Deletion leaves no orphaned steps or attempts **whether or not the engine enforces the declared cascade**, which SQLite does only when the connection asks. Tiers run delete → prune → scrub so the gentler ones never work on rows about to disappear, and a **dry run predicts the real run exactly**, carrying would-be-deleted ids forward so later tiers do not count work that would never happen.
- `Laraflow\Workflow\RetentionPolicy` (public) validates its bounds at construction — a bound below one day would act on work that finished seconds ago — and `warnings()` reports valid-but-probably-wrong combinations, such as deleting completed work before it would have been scrubbed, or discarding recoverable failed work sooner than completed work.
- **Execution duration is captured at the finishing transition and persisted** (`laraflow_workflow_executions.duration_ms`). It was recomputed from the reloaded timestamps, which hold whole seconds, so `durationMs()` reported 0 ms for any execution that took less than a second — most of them. The attempt history has stored its duration for the same reason since Milestone 3. The claim's compare-and-set clears the recorded duration alongside `finished_at`, so a reclaimed execution does not report a duration for the run it is superseding. `laraflow:show` now displays it.
- **Payload size policy** (`laraflow.execution.max_payload_bytes`, default `null` — no limit), the item `docs/execution-lifecycle.md` deferred to this milestone. Bounds a single durable payload — workflow input, one step's output, or the context snapshot — measured as the JSON that reaches the column, and enforced at the same three boundaries as the type contract: input at `start()` (nothing persisted on rejection), output and context after `handle()` returns and before the checkpoint. Setting it does not turn a success into a failure; it changes where the failure is reported. Without it an oversized payload still fails, but as a driver error about a column or packet size raised from inside the checkpoint transaction; with it, the step fails with the new public `PayloadTooLargeException` naming the path, the actual size, and the limit. Added to `StepPolicy::NEVER_RETRY`: the same step produces the same size, so another attempt could only repeat the outcome. A blank environment value means "no limit", and a limit below 1 is rejected at construction rather than silently rejecting every payload.
- **Structured logging context** (`laraflow.logging.context`, default on). While a step runs, Laravel's log context carries `laraflow.execution_id`, `laraflow.workflow`, `laraflow.step`, `laraflow.position`, `laraflow.attempt`, and — when supplied — `laraflow.correlation_id` and `laraflow.tenant_id`. Every log record the *application* writes from inside a step therefore carries them, with no Laraflow API involved, and because Laravel dehydrates the context into queue payloads, a job a step dispatches inherits them too: one correlation id follows the work across processes. Keys are namespaced so nothing of the application's is clobbered, absent identifiers are omitted rather than written as null, and the context is restored in a `finally` — so a throw, a scheduled retry, or a cancellation all leave it exactly as it was found, and an in-process run cannot leak its execution id into the surrounding request. Nested executions (a step running another workflow synchronously) push and pop frames, restoring the outer execution's keys rather than deleting them.
- **Optional lifecycle log** (`laraflow.logging.lifecycle`, default off): one record per lifecycle event, registered as a wildcard listener on `Laraflow\Events\*` so an event class added later is logged without code changes. Terminal failures log at `error`, failed attempts and scheduled retries at `warning`, everything else at `info` — matching the guidance to alert on `WorkflowExecutionFailed` rather than on every attempt. The record's context is the event's own public properties, which is safe by construction: events carry identifiers and metadata only, and any error message has already passed the configured redactor.
- Dependency: `illuminate/log` (the context repository), already present transitively and now declared.
- **Durations on lifecycle events.** `WorkflowStepCompleted` and `WorkflowStepFailed` carry `durationMs` for the attempt — the same `StepAttempt` record that goes to history feeds the event, so telemetry and history can never disagree about how long a step took. `WorkflowExecutionCompleted`, `WorkflowExecutionFailed`, and `WorkflowExecutionCancelled` carry `durationMs` from the execution's **first** start to this finish: end-to-end latency, deliberately including time spent failed or backing off between retries, which is what an SLA measures. Null when the execution never started (a `pending` execution cancelled outright); zero is a measured zero, not an absence. `WorkflowExecution::durationMs()` exposes the arithmetic.
- **`ExecutionStatus::isFinished()`** and `WorkflowExecution::isFinished()`: true for `completed`, `failed`, and `cancelled` — the states that record `finished_at`. Named for "has stopped", **not** `isTerminal()`: in Laraflow "terminal" means never claimable again (`completed`, `cancelled`) and `failed` is re-executable by design, so conflating them would let the retention work in step 10 either skip failed executions forever or delete work a worker still owns.
- **Queue lag.** Every dispatch records `dispatched_at` and `available_at` on the execution (the same instant for an ordinary push; the due time for a delayed retry), and `WorkflowExecutionStarted` gains `queueLagSeconds`: the wait from availability to the claim. Measured from *availability*, not dispatch, so a retry's own backoff is never counted as time waiting for a worker. Null when the execution was never dispatched or was claimed ahead of availability — running early is not a wait of zero. `laraflow:show` reports *Dispatched*, *Available* (only when it differs — a delayed retry), and *Queue wait*, open-ended while pending and exact once claimed. The dispatch is recorded before the job is pushed, so the `sync` driver sees it too. `WorkflowExecution::queueLagSeconds(DateTimeImmutable $claimedAt)` exposes the arithmetic. Specified in `docs/queue-and-recovery.md`.
- `WorkflowExecution` gains `correlationId`, `tenantId`, `dispatchedAt`, `availableAt`, `finishedAt`, and `payloadsScrubbedAt`. `markCompleted()`, `markFailed()`, and `markCancelled()` set `finishedAt`; `markRunning()` clears it, so a re-executed failure cannot look eligible to retention while a worker is running it. The claim and the compare-and-set cancellation path make the same writes directly.

- **`tests/Feature/ProjectContractsTest.php`**: holds the documentation and the code to each other. Every class, configuration key, command, command option, publish tag, and cross-reference the documentation names must exist, and the invariants it promises must hold — no console command reaching past the public contract, every lifecycle event carrying the correlation identifiers, every never-retried exception named in the retry contract, every shipped default being the documented one.

#### Decisions

- **Correlation is two indexed columns, not a metadata blob.** A JSON column cannot be indexed portably across the four supported engines, and bounded listing was an exit criterion.
- **Metrics are enriched events, not a metrics contract.** Durations and queue lag ride on the lifecycle events; the documentation gives Prometheus, StatsD, and Pulse recipes. Shipping no vendor integration is how "assumes no particular monitoring vendor" was met.
- **Queue lag is measured from availability, not dispatch.** A delayed retry's backoff is not time spent waiting for a worker.
- **`isFinished()`, not `isTerminal()`.** "Terminal" already means never-claimable (`completed`, `cancelled`); `failed` is re-executable yet has finished. Conflating them would let retention either skip failed work forever or delete work a worker owns.
- **No write-time payload redaction.** Input seeds the context on every `execute()` and context is restored on recovery, so rewriting either would corrupt re-runs. Post-finish scrubbing is offered instead.
- **Retention never scrubs failed executions, and deletes them only under their own bound.** Re-executing one needs its input and context. Attempt pruning does cover them, because the retry budget reads the step row's counter rather than the history table; the diagnostics that costs are stated as a trade-off in `docs/retention.md`.
- **Every console command runs on the public contract.** No command touches an Eloquent model, and a test reads each one's source to keep it that way. Where the contract lacked a read a command needed — step counts for a page — the contract gained it rather than the command reaching around it.
- **`ExecutionRepository` stays one interface.** Splitting it into persistence, query, recovery, and retention interfaces would widen what a custom implementation must know about for the benefit of three internal consumers; the Eloquent implementation is organised by concern instead.
- **The dispatch is recorded before the queue push.** Required for the sync driver to measure its own wait; the consequence — a failed push leaves dispatch timestamps for a job that never existed — is documented in `docs/queue-and-recovery.md`, and is the case the recovery scan's `pending_after` option covers.

#### Changed

- **Internal structure, following a milestone-wide review:** `WorkflowRunner` (894 lines, twelve constructor arguments) was split — `StepResolver` for definition validation and step construction, `OutcomeRecorder` for the four outcome-persistence paths and the error-redaction chokepoint, `RunnerOptions` for its configured settings — leaving 512 lines with one job. `RetentionService` carries its per-run state in `RetentionRun`. `EloquentExecutionRepository` is organised into `QueriesExecutions`, `ScansForRecovery`, and `AppliesRetention` concerns. `Support\Duration` holds the arithmetic `StepAttempt` and `WorkflowExecution` shared. No behaviour changed; the suite that pinned every property passed untouched through each step.
- **Fixed:** `laraflow:summary --tenant=` reported every tenant's due retries alongside one tenant's counts, and failed its health check because of them. **Fixed:** `laraflow:prune` rejected a malformed `--limit` or `--chunk` as "a number of days".
- **Breaking:** `ExecutionRepository::create()` gained a trailing optional `?ExecutionOptions $options`. Custom implementations must accept and persist it; implementations that ignore it silently drop the identifiers an application supplied.
- **`laraflow:list` runs on the public query API** and no longer touches the internal Eloquent models, gaining `--workflow`, `--correlation`, `--tenant`, `--since`, `--until`, `--cursor`, and `--oldest`; `--status` and `--workflow` are repeatable. It reports how many of the matching set the page showed — a bounded page that does not say so looks like the whole truth — and prints the command that continues it, carrying the current filter forward so following the hint cannot silently widen the query. A malformed cursor and an unparseable time are both refused with guidance rather than guessed at. `laraflow:show` gains the correlation and tenant identifiers, reads its "Finished" row from `finished_at` (so cancellation is reported like completion and failure), and reads attempt history in one query instead of one per step.
- **Breaking:** `ExecutionRepository::dueForRetry()` gained a trailing optional `?string $tenantId`. Without it `laraflow:summary --tenant=acme` reported every tenant's due retries alongside acme's counts, and failed its health check for another tenant's work.
- **Breaking:** `ExecutionRepository::stepProgress(array $ids)` was added: step counts for many executions in one query. `laraflow:list` showed per-execution progress with one `steps()` call per row; a listing must not cost a query per row, and adding the method now folds it into this milestone's contract change instead of making it a fresh one later.
- **Breaking:** `ExecutionRepository` gained four retention methods — `retentionCandidates()`, `scrubPayloads()`, `pruneAttempts()`, `deleteExecutions()`. Custom implementations must add them and honour three contract obligations: each scan must apply its tier's self-limiting predicate, every write must re-apply the status and `finished_at` guard in the same statement, and `deleteExecutions()` must leave no orphaned child rows without relying on database cascades.
- **Breaking:** `ExecutionRepository` gained `recordDispatch(id, dispatchedAt, ?availableAt)`. Custom implementations must add it; an implementation that ignores it leaves `queueLagSeconds` permanently null and `laraflow:show` silent about queue timing. It must not be claim-guarded, and must treat an availability earlier than the dispatch time as the dispatch time.
- **Breaking:** `ExecutionRepository` gained three methods — `list()`, `count()`, `attemptHistory()` — and the `MAX_PAGE_SIZE` constant. Custom implementations must add them. Each must honour the contract's bounds: `list()` may never return more than `MAX_PAGE_SIZE` rows and must paginate by keyset in the filter's direction; `count()` counts the whole matching set regardless of pagination.
- **Fixed:** documentation that had drifted behind Milestone 3 — the README described two tables (there are three) and listed only the four original execution statuses; `SECURITY.md` still cited "there is currently no retry limit" as unimplemented hardening and promised that "future" events and logging would redact step data, both of which shipped; `CONTRIBUTING.md` still gated contributions on Milestone 1; and `docs/queue-and-recovery.md` disagreed with `docs/public-api.md` about which events fire once per execution.

### Milestone 3 — retry, timeout, and failure policy

#### Added

- **Per-step retry policy** (`Laraflow\Workflow\Policy\StepPolicy`, public): total attempt budget, exponential backoff capped at `max_delay`, `retryOn`/`dontRetryOn` matched by `instanceof`, and a per-attempt timeout. Declared on a step via the optional `HasStepPolicy` interface, on a workflow via `defaultStepPolicy()`, or globally via `laraflow.retry.*` — resolved in that order, **per step**, so one slow step can out-declare its siblings. **Retries ship disabled** (`retry.max_attempts` = 1), consistent with `queue.tries` and `recovery.pending_after`.
- **`retrying` state** on executions and steps, carrying a durable `next_retry_at`. A retryable failure persists the failed attempt, schedules the next one, releases the claim, and **returns** from `execute()` — nothing is thrown, nothing reaches `failed_jobs`, and `WorkflowExecutionFailed` does not fire, so alerting built on failures stays meaningful. Terminal failures keep the Milestone 1/2 contract unchanged.
- **Deterministic schedules.** Backoff jitter is derived by hashing the execution id and step position with the attempt number rather than drawn from randomness, so one logical retry always lands on the same instant. When the jitter window would cross `max_delay` it slides down to fit rather than being clipped — clipping bunched roughly half of all executions onto exactly the ceiling, in precisely the case jitter exists to prevent.
- **PSR-20 clock** (`psr/clock`, already a transitive dependency) injected through the runner, repository, and recovery service; the default binding wraps Laravel's `Date` facade, so `Date::setTestNow()` still governs every timestamp.
- **Two delivery paths for a due retry.** `ExecuteWorkflowJob` queues a delayed redelivery for `next_retry_at` (`retry.dispatch_delayed`, skipped on the `sync` driver where `delay()` is ignored and backoff would become immediate recursion), and `laraflow:recover` gains a due-retry scan — the *contractual* pickup, needing no queue and catching anything the fast path loses.
- **Append-only attempt history** (`laraflow_step_attempts`): every finished attempt keeps its outcome (`completed`, `failed`, `timed_out`, `interrupted`), error, timestamps, duration, and scheduled retry. Rows are written in the same transaction as the step state change they describe, so history can never disagree with it — including rolling back together on claim loss — and a unique `(step_execution_id, attempt)` index stops a duplicate delivery double-counting an attempt. Read via `ExecutionRepository::attempts()` or `laraflow:show --attempts`.
- **Step deadlines.** A policy's `timeoutSeconds` is persisted as `timeout_at` *before* `handle()` runs (a dying worker writes nothing, so the deadline must already exist) and exposed via `WorkflowContext::deadline()`/`remainingSeconds()`. Laraflow does not preempt running PHP; classification happens at the recovery boundary, giving the three-way distinction the roadmap asked for: a thrown failure, worker loss before the deadline (free re-run, recorded `interrupted`), and an overrun attempt (recorded `timed_out` with `StepTimeoutException`, charged to the retry budget).
- **Cancellation.** `WorkflowRunner::cancel()` and `laraflow:cancel {execution} {--reason=}`. Immediate and atomic for `pending`/`failed`/`retrying` — using the same compare-and-set predicate as claiming, so it cannot race a worker — voiding any scheduled retry. Cooperative for `running`: the owning worker stops at its next step boundary, so the step in flight finishes and checkpoints. `cancelled` is terminal and refused by `claim()`, `execute()`, `dispatchExecution()`, and recovery; repeat cancellations are idempotent no-ops.
- **Error redaction.** `laraflow.errors.redactor` names an `ErrorRedactor` applied at one chokepoint before any exception message is persisted, logged (the failed-job hook included, which previously logged raw messages), or emitted. The exception the application catches is untouched; a misconfigured class fails loudly rather than silently leaking.
- **Continue-on-failure.** `Workflow::failurePolicy()` returning `FailurePolicy::Continue` runs the remaining steps after a terminal step failure; the execution still ends `failed` and rethrows the first exception. Retry policy takes precedence over continuing. For independent steps only — later steps see no contribution from the failed one.
- **Events:** `WorkflowStepRetryScheduled` (attempt, budget, error class and message, due time, delay) and `WorkflowExecutionCancelled`; `WorkflowExecutionRetryScheduled` gains `retry_due` and `step_timeout` reasons.
- **Console:** `laraflow:execute --now`; `laraflow:show --attempts` plus retry schedule, cancellation detail, per-step next-retry, and an `(overdue)` marker on a running step past its deadline; `retrying`/`cancelled` colours and `laraflow:list` filtering.
- `docs/retry-and-failure-policy.md` specifying all of the above, and behavioural suites covering scheduling, due-gated claiming, queue delivery (against a real driver and `queue:work` worker), timeouts, cancellation, failure policy, redaction, and console output.
- Schema (existing migrations edited in place, per the pre-release policy): executions gain `next_retry_at` with a `(status, next_retry_at)` index, `cancel_requested_at`, `cancelled_at`, `cancel_reason`; steps gain `failed_at` and `timeout_at`; new `laraflow_step_attempts` table.

#### Changed

- **Breaking:** `ExecutionRepository` — `claim()` gains `$ignoreRetrySchedule` and refuses a not-due `retrying` execution with `RetryNotDueException`; `saveStep()`/`checkpoint()` take an optional `StepAttempt`; `attempts()`, `dueForRetry()`, and `requestCancellation()` added; `release()` now also covers the `retrying` and `cancelled` transitions.
- **Breaking:** `laraflow.recovery.max_attempts` renamed `laraflow.recovery.abandon_after_attempts` (`--max-attempts` → `--abandon-after`). With `retry.max_attempts` now existing as the failure budget, two same-named knobs with different scopes invited operators to confuse crash-loop protection with retry policy. The bounds are deliberately independent: due retries are exempt from the abandonment bound, whose job is interruption recovery.
- **Breaking (behavioural, opt-in):** with a retry policy enabled, `execute()`/`run()` can return a non-terminal `retrying` execution instead of throwing. Under the shipped defaults, behaviour is unchanged.
- **Fixed:** `StepExecution::markFailed()` accepted a timestamp and discarded it, so a failed step had no record of when it failed; it is now persisted to `failed_at`.
- **Fixed:** a declared-but-empty environment variable (`LARAFLOW_RETRY_MAX_ATTEMPTS=`) cast to `0` and was rejected by policy validation, turning a stray blank line in `.env` into an application that could not resolve the runner. Blank now means "use the default".
- **Fixed:** `laraflow:list --status` help text listed only the four original statuses. It and the invalid-status error now derive from the enum.
- `composer playground` runs `migrate:fresh`. Because migrations are edited in place before the schema freeze, an existing playground database silently missed new columns.
- The test suite enforces SQLite foreign keys, which the schema has declared since Milestone 0 but no test had exercised.

### Milestone 2 — queue execution and operational recovery

#### Added

- `Laraflow\Queue\WorkflowDispatcher` (public): `dispatch(Workflow, $input, ?connection, ?queue)` creates an execution and queues it; `dispatchExecution(id, ...)` queues an existing one for retry or recovery. Queue concerns live here rather than on `WorkflowRunner`, which keeps no queue dependency.
- `Laraflow\Queue\ExecuteWorkflowJob` (public): the queued job. Its payload carries **only the execution id** — the workflow class is read from the execution record, so a job can never disagree with durable state, and no workflow input reaches the queue backend.
- Eight lifecycle events in `Laraflow\Events` (public, `readonly`): `WorkflowExecutionDispatched`, `WorkflowExecutionStarted`, `WorkflowStepStarted`, `WorkflowStepCompleted`, `WorkflowStepFailed`, `WorkflowExecutionCompleted`, `WorkflowExecutionFailed`, `WorkflowExecutionRetryScheduled`. Each fires strictly after the durable write it describes.
- `laraflow:recover` command: finds interrupted executions (stale claims, and optionally never-dispatched pendings) and retries them, with `--dry-run`, `--sync`, `--limit`, `--max-attempts`, `--stale-after`, `--pending-after`, and `--workflow`. Exits non-zero when work was abandoned or an action failed, so a scheduled run surfaces stuck work through existing alerting.
- `--queue` on `laraflow:execute` and `laraflow:demo`.
- `ExecutionRepository::stale()` and `::pendingBefore()`: bounded, clock-free scans for recoverable work. `stale()` uses the same `claimed_at <= cutoff` comparison as `claim()`, so scanning and claiming cannot disagree about staleness.
- Configuration: `queue.*` (`connection`, `queue`, `tries`, `backoff`, `timeout`, `after_commit`), `recovery.*` (`limit`, `max_attempts`, `pending_after`), and `events.include_error_messages`.
- `docs/queue-and-recovery.md` specifying dispatch, the retry decision, duplicate-delivery semantics, recovery policy and bounds, and event payload safety.
- End-to-end coverage in `tests/Feature/Queue/QueueRecoveryTest.php` using a real database queue driver and a real `queue:work` worker, rather than `Queue::fake()`: async completion, crash-to-recovery from a checkpoint, duplicate deliveries, the abandonment bound, and the absence of retry multiplication.
- Dependencies: `illuminate/bus`, `illuminate/queue`, `illuminate/events`, and `illuminate/console` (the last was already used by the existing commands but never declared).

#### Decisions

- **The queue does not retry by default** (`queue.tries` defaults to 1). Queue retries and Laraflow step attempts would otherwise multiply on two unrelated schedules. Re-running a failed execution is an explicit operation until per-step retry policy arrives in Milestone 3.
- **Duplicate deliveries are no-ops, not failures.** The existing compare-and-set claim is the only authority; `ExecutionAlreadyClaimedException`, `ExecutionNotRunnableException`, and `ClaimLostException` are caught and logged so the job succeeds. No cache lock or `ShouldBeUnique` is involved.
- **Recovery is bounded by step attempts.** An execution whose steps reached `recovery.max_attempts` is reported as abandoned rather than re-dispatched, so a crash-looping workflow cannot be retried forever by the scheduler. The bound reuses durable `attempts`, so Milestone 2 required **no migration**.
- **Recovery refuses executions whose workflow class is gone** (reported as *unrecoverable*, exit code 1). A retry of a missing class fails before any step runs, so attempts never increment and the attempt bound alone could never stop a scheduled re-dispatch loop.
- **Recovery of `pending` executions is opt-in** (`recovery.pending_after` defaults to null). `pending` is also the state of work created with `start()` and deliberately not yet run; recovery must not start that behind the application's back.
- **Events never carry input, output, or context**, with no opt-in. Failure events carry the exception class and, unless `events.include_error_messages` is disabled, the truncated message — data the execution record already holds.
- **Event listeners are observational**: a throwing listener is logged and swallowed rather than altering execution state, aborting a dispatch, or masking a step's exception. Listeners needing retry semantics should be queued listeners.

#### Changed

- `WorkflowRunner` takes two optional trailing constructor arguments (an internal event emitter and an error-message flag). Construction is internal wiring; resolve the runner from the container.
- `laraflow:execute` now resolves the recorded workflow class through a shared resolver and, with `--queue`, validates it *before* queueing, so a missing class fails at the console rather than minutes later on a worker.
- README gained a "Running on a queue" section; its configuration sample now reflects every shipped key, and "Current limitations" has been rewritten for the post-Milestone-2 state.

### Milestone 1 — execution lifecycle and recovery

#### Added

- `WorkflowRunner::start()` creates an execution and its **full step plan** up front, atomically, without running anything; `WorkflowRunner::execute()` claims an execution and runs every non-completed step, serving both first execution and recovery through a single code path.
- Compare-and-set execution claiming with per-worker claim tokens: only one worker can own an execution; `running` executions with a claim older than `laraflow.execution.stale_after` (default 300s) can be reclaimed after worker loss. Checkpoints and terminal writes verify the claim, so a superseded worker gets `ClaimLostException` instead of corrupting state.
- Transactional checkpoints: each completed step's output and the full context snapshot commit together; the context is restored from durable state on recovery, so later steps see earlier results without re-running them.
- Enforced execution and step state machines via `mark*()` transition methods (`InvalidStateTransitionException` otherwise), documented in `docs/execution-lifecycle.md` together with the full crash-boundary and at-least-once contract.
- Workflow-definition validation on `execute()`: a changed workflow class or step list raises `WorkflowDefinitionMismatchException` instead of silently reinterpreting durable state.
- Serialization contract enforcement: workflow input, step outputs, and context values must be JSON-serializable; violations raise `UnserializableValueException` naming the offending key. Input is validated before anything is persisted.
- Idempotency hooks on `WorkflowContext`: `executionId()`, `stepPosition()`, `attempt()`, and `idempotencyKey()` (stable across retries of the same logical step).
- Robust failure persistence: step failures store the exception class and truncated message (`laraflow.execution.max_error_length`) on both step and execution; if persisting the failure itself fails, the storage error is logged and the original exception still propagates.
- Workflow exception hierarchy under `Laraflow\Exceptions\Workflow`.
- Schema: executions gained `context`, `error`, `error_class`, `claim_token`, `claimed_at`, and status indexes; steps gained `error_class`. (Existing migrations edited in place per the pre-release schema policy.)
- Recovery test suite simulating worker death at every persistence boundary, claim contention, stale takeover, definition drift, serialization violations, and failure-persistence failure.

#### Changed

- **Breaking:** `WorkflowRunner::run()` now returns the `WorkflowExecution` handle instead of the `WorkflowContext`, and accepts workflow input that seeds the context (rationale in `docs/public-api.md`).
- **Breaking:** `WorkflowRunner::resume()` is removed; call `execute()`.
- **Breaking:** `ExecutionRepository` contract reworked: `create()` now takes the step plan; `claim()`, `checkpoint()`, and `release()` added; `save()` and `createStep()` removed. `find()` throws `ExecutionNotFoundException` instead of Eloquent's `ModelNotFoundException`.
- A step found `running` during recovery is treated as interrupted and re-runs (the documented at-least-once boundary); `started_at` now records the first start and survives re-execution; completing clears a previous error.

### Milestone 0 — contracts and packaging

#### Added

- Package migrations are now loaded automatically by the service provider, with an opt-out via `laraflow.migrations.load` / `LARAFLOW_LOAD_MIGRATIONS`.
- `laraflow-migrations` publish tag for applications that want to manage the migrations themselves.
- Package metadata: license, keywords, support links, `illuminate/database` dependency, `composer test` script.
- Documentation: installation and usage README, public API and stability levels (`docs/public-api.md`), compatibility and support policy (`docs/compatibility.md`), contributing guide, security policy, this changelog.
- `.gitattributes` enforcing LF line endings.

#### Changed

- The service provider now merges the package configuration (`mergeConfigFrom`), so `config('laraflow.*')` has defaults without publishing.
- The GitHub connector token is cast to a string when the configuration value is missing, so resolving the connector no longer raises a `TypeError`; requests without a token will fail at the GitHub API instead.
