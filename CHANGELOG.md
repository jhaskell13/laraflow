# Changelog

All notable changes to Laraflow are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as specified in [docs/compatibility.md](docs/compatibility.md). Until 1.0, a minor release may carry breaking changes; each is marked **Breaking** under the release that makes it, and changes merged since the last tag are recorded under *Unreleased*.

Cutting a release renames *Unreleased* to the version and date, starts a fresh *Unreleased* above it, and updates the compare links at the end of this file. Releases are tagged (`v0.1.0` onwards). 0.1.0 and 0.2.0 kept the milestone groupings of the work they shipped; later releases use the Keep-a-Changelog headings in this order — *Added*, *Changed*, *Deprecated*, **Breaking** (or *Removed*), *Fixed*, *Security* — with **Breaking** a heading of this project's own for changes a 0.x minor may make.

## [Unreleased]

Milestone 12, in progress: production validation and 1.0.

### Added

- **Milestone 12's contracts, written before its code.** [docs/threat-model.md](docs/threat-model.md) is what the milestone's security review is conducted *against*: the eight trust boundaries with what crosses each, what Laraflow checks there and what remains; the attacker models the review works through; and the nine invariants a finding would falsify. `SECURITY.md` keeps its scope list and now points at the reasoning behind it. [docs/soak.md](docs/soak.md) fixes the soak and benchmark suite before it exists — the mixed workload, the four injected faults, the nine invariants asserted after every round, the benchmark numbers published rather than gated, and what the suite does *not* cover.

- **Two decision records.** [0012](docs/decisions/0012-what-1.0-freezes.md) decides what 1.0 freezes: Public becomes semver-covered and is held by a committed API signature baseline rather than by care; the console's command names and `--json` envelope, the dashboard, the triggers, the metrics snapshot, the tracing hook, and both bundled connectors are promoted to Public; `ExecutionStore` stays Experimental deliberately, which is [0006](docs/decisions/0006-a-small-final-public-surface.md) holding rather than an oversight; and the bundled connectors stay in this repository, because calling an external service is the package's job in a way running an application's monitoring was not ([0011](docs/decisions/0011-one-optional-package.md)). [0013](docs/decisions/0013-what-the-soak-proves.md) replaces the soak's calendar-shaped exit criterion with a stated budget, and records that the injected database fault is container loss and recovery — not a promoted replica.

- **The post-1.0 compatibility and support policy.** [docs/releases.md](docs/releases.md) gains the versioning rules, cadence, and removal path that take effect at 1.0, and the **long-term-support window**: the last minor of an outgoing major receives security fixes for 12 months after the next major is published, so an application has a year to make the changes a major asks for without running unpatched. `SECURITY.md` carries the same window and remains its authority. `docs/compatibility.md` records why the deprecation marker stays a `@deprecated` docblock rather than PHP 8.4's `#[\Deprecated]` attribute: the supported floor is 8.2, and the attribute emits exactly the runtime notice this project declines to emit.

- **The soak and benchmark suite ([docs/soak.md](docs/soak.md)).** A family of `soak:*` console commands under `workbench/` — dev-only, never installed — with one orchestrator that resets the database, starts a stub provider, and spawns queue workers, three schedulers with skewed clocks, a recovery loop, a retention loop two days in the future, a signaller, and a load generator producing the mixed workload the contract names: linear, retrying, overrunning, remembering, waiting, nested, fanned-out, compensating, connector-calling, scheduled, tenant-bounded, cancelled, and probing reserved signal names. While the load runs it kills workers at random and, where it is given the container ids, stops and restarts the database and the queue backend; when the load ends it drains the waits, lets recovery settle the records, and checks ten invariants directly against the tables and the captured logs — nothing unfinished, attempts contiguous, fan-outs coherent, one execution per tick, remembered work settled once and agreeing with its step, no orphans, every plan matching its definition, `finished_at` exactly on terminal rows, no sentinel in any log, every reserved-signal probe refused. The repository is wrapped in a timing decorator for the run, so claim contention and checkpoint latency are measured around the calls themselves. A nightly `Soak` workflow runs it on all six engine cells against a Redis queue, publishes the report as the job summary and an artifact, and compares the numbers to a per-engine baseline in `workbench/soak/baseline.json` — advisory, by [decision 0013](docs/decisions/0013-what-the-soak-proves.md). `composer soak` is the local smoke run on SQLite.

### Added

- **The 1.0 API freeze, held by a machine.** `tests/api-baseline.json` records the shape of every Public class — what it extends and implements, the signatures it declares, its constants *and their values*, its properties, and its enum cases with their backing strings — and `ApiSignatureTest` fails on any difference, naming the class that moved. Changing the surface is now a reviewable diff that has to argue for itself in a pull request, the way `SchemaFreezeTest` already makes a schema change argue for itself ([decision 0012](docs/decisions/0012-what-1.0-freezes.md)). Regenerate deliberately with `LARAFLOW_UPDATE_API_BASELINE=1`. The baseline records only what this package declares: a method reached through a third-party trait reports the *using* class as its declarer, so `ExecuteWorkflowJob` appeared to declare twenty-seven of Laravel's queue methods, and freezing those would have made the next framework release fail this test.

### Changed

- **Stability levels settled for 1.0 ([decision 0012](docs/decisions/0012-what-1.0-freezes.md)).** Promoted to **Public**: the dashboard, the whole trigger surface, the metrics snapshot, the tracing hook, `SignalReceipt`, and both bundled connectors with their error mappers — each has shipped at least a minor, is contract-tested, and in several cases is already named in `SECURITY.md`'s scope, which "may change or be removed without notice" never squared with. Also Public: every console command's **name**, its options, its exit codes, and the envelope of its `--json` document; the fields inside that document are Public but **additive-only**. Demoted to **Internal**: the command *classes* themselves, which are implementation — the command is the contract — and the `Laraflow\Demo` classes, where Experimental implied someone might reasonably build on them. `ExecutionStore` and the store half of `ExecutionRepository` remain **Experimental**, deliberately and as the only such surface: every milestone has widened it and it has been proved against exactly one driver. One Experimental interface is what lets the rest of the promise mean something.

- **Members a Public class never promised are marked `@internal` rather than frozen.** `Wait` is the clearest case: beside the four methods the documentation describes it carried ten more that build and read the reserved `laraflow.child.*` and `laraflow.join.*` signals, called only by the runner, the resolver, and the notifier — freezing them would have meant carrying them to 2.0. The same applies to the engine-only members of `StepPolicy`, `ExecutionOptions`, `PlanDraft`, `Schedule`, `ChildWorkflows`, `FanOutWorkflows`, `ScheduleRegistry`, and `Dashboard`, several of which the document already disclaimed in words ("its methods beyond construction are not a contract") without the code saying so. Interface methods were left alone: on an interface every method is an implementer's obligation, so `ScheduleRepository::countTicksBefore()` and `pruneTicks()` were **documented** instead — a gap the freeze found.

### Fixed

- **Two holes in the stability enforcement itself.** `ProjectContractsTest` read the documented level with a pattern that only matched a bare `Public`/`Experimental`/`Internal` cell, so the twenty rows written `Public (contract)` were skipped and their classes' levels went unchecked. And it detected a code marker by searching the docblock for the *substring* `@experimental`, so `ExecutionRepository` — whose docblock explains that `ExecutionStore` is `@experimental` — was read as experimental itself. Levels are now parsed with the qualifier allowed and markers matched as docblock *tags*; the one real disagreement the fix surfaced is corrected.

### Security

- **A database exception's bound values no longer reach any sink Laraflow retains.** Laravel formats a `QueryException` as the driver's error followed by the SQL with every binding substituted in. When the failing statement was a checkpoint, a child execution's creation, or a step's own query, those bindings are the workflow's input, output, and context — so one locked table or lost connection put payloads into the `error` columns, the attempt history, `WorkflowStepFailed` and `WorkflowExecutionFailed`, the lifecycle log, the failed-job log, and the dashboard's flashed outcome, where the contract says payloads never go and where retention's scrub tier, which clears payload columns and not error text, would never reach them. The soak suite found it on its first run. Every retained message now passes through `Laraflow\Support\ErrorMessage` (internal) before the configured redactor: a database exception keeps the driver's message and the statement with its `?` placeholders and loses the values, unconditionally — the protection does not depend on a redactor being configured. The exception the application catches is untouched. Regression tests cover every sink.

### Breaking

- **The pre-0.6.0 generator names are removed.** `make:workflow`, `make:step`, and `make:connector` have been hidden deprecated forwarders since 0.6.0, which announced their removal; use `laraflow:make-workflow`, `laraflow:make-step`, and `laraflow:make-connector`. 1.0 is the last release allowed to remove them — after it, a removal waits for a major. The contract test that held them now holds something more durable: every command Laraflow registers is named under the `laraflow:` prefix, so the package can never again collide with Laravel's own namespace or another package's.

### Fixed

- **Release hygiene a 1.0 cannot carry.** `v0.6.0` was never tagged, so the changelog's `[0.6.0]` compare link pointed at nothing and `SECURITY.md`'s support table promised fixes for a "previous minor" that had no tag; the tag now exists and the table names the versions. `CONTRIBUTING.md` states that release tags are annotated — `v0.2.0` is the one lightweight tag in the history, left as it is rather than moved — and that they are signed once the maintainer has a key configured. The empty, unreferenced `.env.example` is gone, with the `.gitignore` entry that preserved it, and `.gitattributes` no longer export-ignores a file that does not exist; its comment now names `MAINTAINERS.md`, which has shipped in the dist archive since 0.7.0 without being listed.

## [0.7.0] - 2026-11-05

Milestone 11: what an application needs to observe Laraflow, without Laraflow running the application's monitoring. An exact metrics snapshot for gauges, beside the lifecycle events for counters; a tracing hook in the core and one optional package, `laraflow/opentelemetry`, that joins an execution's runs into one trace across workers and days; a documentation site built from `docs/` with the README cut to a page; connector packages published and listed with the contract test as the review; issue forms, a maintainers file, and a release and support policy; and Horizon and Octane guidance held by tests. The milestone was narrowed partway ([decision 0011](docs/decisions/0011-one-optional-package.md)): metrics packages for Prometheus, StatsD, and Pulse were built and removed before release. Everything new is Experimental until 1.0. One additive migration, safe against live workers.

### Added

- **Milestone 11's contracts, written before its code.** `docs/metrics.md` describes the metrics snapshot and how an application builds its own metrics from it and from the lifecycle events — Laraflow records none itself. `docs/tracing.md` fixes the spans, their nesting and attributes, what never appears on one, and how one execution's runs are joined across processes and days. Both are Experimental until 1.0, so real use decides what is frozen. `docs/community-connectors.md` says how a connector package is published and listed, with the contract test as the reviewer. `docs/decisions/` starts a decision record: six records backfilled from the changelog and contracts, and five for this milestone — including [0011](docs/decisions/0011-one-optional-package.md), which narrowed it: metrics bridges for Prometheus, StatsD, and Laravel Pulse, and a core metrics model they shared, were built and removed before release, because an application's monitoring is the application's to run.

- **The metrics snapshot: `Laraflow\Observability\Snapshots` and `MetricsSnapshot` (Experimental until 1.0).** `Snapshots::take($now, ?$scope)` returns what is true of the executions at one instant — unfinished and failed executions counted by workflow and status, the oldest unfinished execution's age, retries and waits due, executions with a step past its deadline, executions a tenant ceiling is holding, and stalled schedules. Every field is exact, where the attention scan behind `laraflow:summary` stops at `MAX_PAGE_SIZE`; the cost is a fixed number of queries however many executions or workflows exist; and each field shares its predicate, in code, with the list the summary prints, so a gauge and the console cannot disagree about what needs attention. An application sets its own gauges from it ([docs/metrics.md](docs/metrics.md)).

- **Tracing: the contract and the core hook (Milestone 11).** `docs/tracing.md` fixes the spans — a run, a step attempt, a connector call — their names, nesting, attributes, and what never appears on one, and how one execution's runs are joined across processes and days: an execution remembers the W3C `traceparent` active when it was created, in the **fifteenth post-freeze migration** (`2026_11_05_000000`, a nullable `trace_context` column, safe against live workers), and each run is parented by the active span in its process, else by that origin while it is recent, else starts a new trace linked to it. `ExecutionOptions::$traceContext` lets an application name the origin itself (validated; invalid values refused). The core reports boundaries to `Laraflow\Observability\Tracing\Tracer` (Experimental), bound to a `NullTracer`, always through a guard that logs and swallows a throwing tracer.

- **`laraflow/opentelemetry`, the one optional package ([decision 0011](docs/decisions/0011-one-optional-package.md)).** Tracing: docs/tracing.md's spans through the OpenTelemetry API, depending on `open-telemetry/api` only — the application's SDK, sampler, and exporter decide what is recorded and where it goes, and without one nothing is. Each span is activated, so the application's own spans and other instrumentation started inside a step are that step's children; step ends and run outcomes are read from the lifecycle events, and error messages on spans are the events' own — redacted, and absent when withheld. A tracer provider bound in the container is used before the global one. Tested against the real SDK with an in-memory exporter: span names, kinds, parents, links, attributes, and that no payload or undocumented attribute ever appears.

- **`ConnectorRequestSent` and `ConnectorRequestFailed` carry `tenantId`** — the running execution's, read from its durable record as the tenant-scoped rate limit reads it, and null for a call made outside any execution. A trailing optional constructor argument; listeners are unaffected. The correlation id stays off both: it is unbounded, and the log context already carries it.

- **The documentation site.** VitePress over `docs/`, unchanged, so the contract tests, GitHub, and the site read the same files: a sidebar over the contracts, local search, and links out of `docs/` — to the changelog, CONTRIBUTING, SECURITY — rewritten to their GitHub pages rather than copied in. The `Docs` workflow builds it on every change, failing on a dead internal link, and deploys it to GitHub Pages from `main` once a maintainer enables Pages and sets the `DOCS_DEPLOY` variable. One version, from `main`, until a second is needed ([decision 0008](docs/decisions/0008-documentation-site-on-vitepress.md)). The build toolchain is not in the dist archive.

- **The documentation, restructured.** The README is a page or two — what Laraflow is, its status, requirements, install, and where to read next — and the rest of it moved, nearly unchanged, into guides under `docs/`: Getting started, a playground tutorial, Configuration, Using Laraflow, Your first connector, and Limitations and design principles. The contract documents are untouched and remain the authority each guide links to. A broken anchor in `docs/compatibility.md` found on the way is fixed.

- **Contributing a connector, as a package.** `docs/community-connectors.md` shows the shape of a connector package — the connector, a provider registering it with `LaraflowManager::register()`, and a Testbench test running `ConnectorContract` — and how one is listed by pull request with its passing CI run as the review. CONTRIBUTING points there for any service Laraflow does not ship.

- **Open-source practice.** Issue forms for bugs and features, with blank issues off, vulnerabilities routed to private reporting, and questions to Discussions; `MAINTAINERS.md`; and `docs/releases.md`, the release cadence and support window in one place, agreeing with SECURITY.md.

- **Long-lived processes: Horizon and Octane.** `docs/queue-and-recovery.md` says how Horizon's settings meet Laraflow's — the job's own `tries` and `timeout` win over a supervisor's, and the connection's `retry_after` belongs between `laraflow.queue.timeout` and `stale_after`. For Octane and every queue worker, new tests hold that nothing in the package keeps mutable static state and that a run, however it ends — a child run inline included — leaves no execution current and no Laraflow keys in the log context; `docs/compatibility.md` states both. No runtime change: nothing leaked.

### Breaking

- **A custom `ExecutionStore` gains four methods and the trace context.** `retriesDue()` and `waitsDue()` — the attention scan's due retries and waits, scoped by a whole `ExecutionFilter` — and `countAttention()` and `countByWorkflowAndStatus()`, the snapshot's exact counts. Each count must share its predicate with the list it counts, as `docs/public-api.md` specifies. The store is experimental; the reader half of the repository is unchanged. It must also persist `ExecutionOptions::$traceContext` in `create()` and return it on `WorkflowExecution::$traceContext`.

### Fixed

- **The closing audit, scoped to Milestone 11, found documentation drift and no code defect.** The README still pointed at installation sections that had moved; `docs/limitations.md` still dated itself to Milestone 10 and said there were no per-workflow counts, which the metrics snapshot now provides, as did a note in `docs/inspection-and-observability.md`; the moved guides kept `docs/`-prefixed link labels. All fixed. One pre-existing cost is recorded rather than changed: the attention scan's overdue-step list reads each running execution's steps (up to one page), where the snapshot's count is one query.

- **`laraflow:summary` and the dashboard overview ignored `--correlation`, `--since`, and `--until` for due retries and waits.** Those two lists came from the recovery scans, which take a workflow and a tenant and nothing else, so a correlation's or a time window's health check reported — and exited non-zero for — retries and waits outside its scope. They now come from `retriesDue()` and `waitsDue()`, scoped by the whole filter like every other number on the page. The per-workflow loop the old scans needed is gone with them.

## [0.6.0] - 2026-11-03

Milestone 10: schedules, triggers, and the operator's edge. A workflow declares a cron cadence and Laraflow starts exactly one execution per tick across any number of schedulers, with missed ticks a stated policy; approvals and webhooks reach `signal()` over HTTP through signed, opt-in endpoints the package ships; tenants get concurrency and rate ceilings enforced at the claim, with the fairness rule written down; and the console gains `laraflow:signal`, `laraflow:children`, bulk cancel and re-run by filter, and `--json` on every operating command. The milestone also closed the per-tenant rate-limit bucket deferred from Milestone 8, and ended with a hostile audit over the dashboard and Milestones 9–10 whose findings are under *Fixed*. **Breaking** changes are listed under their own heading. Five post-freeze migrations ride the upgrade harness — four additive, and one, the UTC timestamp conversion, that must run with workers stopped in an application whose `app.timezone` is not UTC; `docs/upgrading.md`, "Upgrading to 0.6", has the sequence.

### Added

- **`ExecutionReader` and `ExecutionStore`: the repository contract, split by what 1.0 will freeze.** `Laraflow\Workflow\ExecutionReader` (Public) holds the queries — `find`, `steps`, `attempts`, `attemptHistory`, `list`, `count`, `stepProgress`, `childProgress`, `MAX_PAGE_SIZE`; `Laraflow\Workflow\ExecutionStore` (`@experimental`) holds the storage-driver protocol — `create`, `rewritePlan`, `claim`, `saveStep`, `checkpoint`, `checkpointStatus`, `appendCompensation`, `park`, `release`, `requestCancellation`, `recordDispatch`, `recordSignal`, `childOfStep`, `createMember`, `deferred`, the four recovery scans, and the four retention methods. Both resolve from the container to the `ExecutionRepository` binding, so one instance serves all three names and rebinding the repository rebinds them. See [docs/compatibility.md](docs/compatibility.md#alternative-persistence-drivers).

- **The operator's edge: `laraflow:signal`, `laraflow:children`, bulk cancel and re-run, and `--json` on every operating command.** `laraflow:signal {execution} {signal} {--payload=} {--deliver}` is the console form of the dashboard's signal action and of a trigger request, through the same `signal()` and `Handoff`. `laraflow:children {execution}` lists a sub-workflow's child or a fan-out's members as the page `laraflow:list` prints, through the parent filter the dashboard already reads. `laraflow:cancel` and `laraflow:execute` without an id act on every execution the listing's filter options match, oldest first, up to `--limit` (default 100): a filter is required — there is no form that acts on everything — the production confirmation applies unless `--force`, `--dry-run` names and changes nothing, and each row is its own attempt, so a refusal or a repeat failure never stops the rest and the exit is non-zero only when a row failed. Every operating command (not `laraflow:install` or the generators) takes `--json`: one document, one envelope (`command`, `ok`, and `error` on a refusal), the human form's exit code, nothing else on the stream, serialised through one class so no field is spelled two ways; in production, a bulk operation or a prune under `--json` must pass `--force` or `--dry-run`, because a machine cannot answer a prompt and skipping the question because nobody could hear it is not an answer. The listing's table and the next-page hint moved into a shared concern so `list` and `children` cannot disagree about what a page looks like. The shapes are in `docs/inspection-and-observability.md`.

- **Per-tenant ceilings, enforced at the claim.** An execution created with a tenant id is held to its tenant's ceilings on every claim — a fresh dispatch, a due retry, a resumed wait, a heartbeat, recovery — because every run begins at `ExecutionRepository::claim()` and a ceiling checked there is checked everywhere. `laraflow.tenants.max_concurrent` bounds how many of a tenant's executions may hold a worker at once (running or compensating with a fresh claim; parked, pending, and stale executions hold nothing), `max_claims_per_minute` bounds churn through the same cache-backed limiter the connector throttle uses, and `overrides` replaces either per tenant; a `TenantPolicy` binding answers from a tenant table instead. A claim a ceiling turns away is **deferred, not failed**: the execution's status does not move, no attempt is recorded, and the row gains `deferred_until` and a `deferrals` count (the twelfth post-freeze migration, `2026_11_04_000000`, with the `(tenant_id, status, claimed_at)` index behind the count and a `deferred_until` index behind the summary — both build on a populated table; see `docs/upgrading.md`). The queue job re-pushes itself for that instant without spending a try; an in-process caller is told with `TenantThrottledException`, which suggests the delay; the pending scan skips an execution whose timer has not fired; `laraflow:show`, the execution page, `laraflow:summary`, and the overview all say *deferred ×N, next at …*, and `WorkflowExecutionDeferred` fires after the write. Every value ships off, an execution without a tenant is never bounded, and there is no operator override: raising the ceiling is the override, at the right scope. The ceiling is honest about the instant — two claimants for one tenant in the same instant can both count below it — and exact in the steady state; the fairness rule is stated as a sizing rule in `docs/tenancy.md` and held by a test in which a flooding tenant held to two of four workers cannot delay the other tenant by one round more whether its backlog is twenty executions or two hundred. **Breaking** for a custom `ExecutionRepository` (see *Breaking*).

- **Triggers: signals over HTTP, opt-in and signed.** `Laraflow\Triggers\Triggers::routes()` mounts two endpoints behind the application's own path and middleware, and nothing exists until it is called. The signed endpoint, `POST {path}/executions/{id}/signals/{signal}`, verifies every request before it reads a thing — HMAC-SHA256 over the timestamp, execution id, signal name, and body hash, under `laraflow.triggers.key` or any key still accepted in `previous_keys`, within `tolerance` seconds of the server's clock — and answers every verification failure with the same `401 {"status":"refused"}`, logging the reason and firing `TriggerRefused` with it rather than telling the caller. A verified request records the signal through the same `WorkflowRunner::signal()` and `WorkflowDispatcher` the console and dashboard use and answers in `Handoff`'s terms: `202 recorded` with `delivery` queued, ran (with the execution's resulting status), or pending; `404` for an execution that does not exist (checked only after verification, so an unsigned caller cannot enumerate), `409` when the execution can never take that signal (one not yet parked on it is kept in its signal inbox, below), `413` past the payload limit, `422` for a body that is not a JSON object or a signal name that breaks a rule. There is no environment bypass, and a mount with no key — or one shorter than 32 bytes — refuses at the mount, by name. **Named triggers** (`Triggers::register($name, $verifier, $resolver)`) mount `POST {path}/{name}` for a provider's webhooks behind the provider's own verification (a `TriggerVerifier` the application writes, resolved from the container) and the application's mapping of the event to one `SignalIntent` or `null` to acknowledge and ignore; everything after resolution is the signed endpoint's path. `TriggerSignature::sign()` produces the headers for a PHP caller, and the same primitives verify, so signer and verifier cannot drift; `docs/triggers.md` gives the `openssl` recipe for everything else. No schema change and no store of seen signatures: replay is bounded by the signal contract and the tolerance, and the residual window is documented with its defences. The exit criterion — an unsigned request refused with the execution still waiting, a signed one resuming it — is held in the suite and over real HTTP in the install walk, where `curl` and `openssl` do the signing.

- **The scheduling console: `laraflow:schedule` and `laraflow:schedules`.** The tick run is one command, scheduled every minute — `Schedule::command('laraflow:schedule')->everyMinute()` — printing one row per schedule decision (started, caught up, skipped for overlap, taken by another scheduler, paused, not due, failed) and exiting non-zero when a person is needed: a declaration is unusable, a start failed, or a row is orphaned, including under `--dry-run`, which names the ticks it would claim and claims none; `--sync` runs started executions in-process for the application with no queue. The listing shows every schedule's cadence, last tick with the lag it was claimed at, next due instant, and state, and exits non-zero when any schedule is orphaned or **stalled** — due ticks standing unclaimed, the signature of a scheduler that stopped running; `--pause`, `--resume` (never catching the paused interval up), and `--forget` (orphans only — a live schedule's history must not be deletable by typo) each take the class. The same stalled condition is one new attention line in `laraflow:summary` and the dashboard overview, computed by the one `AttentionScan` both read — and `laraflow:summary` no longer returns early on an empty table when something *is* wrong, because a stalled schedule with no executions yet is exactly the state a dead scheduler leaves. `laraflow:show` and the dashboard's execution page now say what started a tick-started execution — the tick instant, caught-up marker, and missed count — through the repository's new origin lookup. The once-per-tick guarantee is held two ways: a suite test in which two claimants read the same high-water mark and the loser's whole transaction — execution, plan rows, all of it — rolls back with its refused tick, and an install-walk stage in which three real `laraflow:schedule` processes race one due tick against each engine and must produce one tick, one execution, and three zero exits, because losing the insert is the designed outcome.

- **Scheduled workflows: the declaration, the registry, and the scheduler.** A workflow declares its cadence by returning a `Schedule` from the new optional `Workflow::schedule()` — `Schedule::cron('0 2 * * *')`, then `timezone()`, `input()` (given the tick instant, so a caught-up nightly job knows which night it is for), `onMissedTicks()`, `withoutOverlapping()`, `tenant()` — and the application activates it by listing the class under `laraflow.schedules.workflows` (a package calls `ScheduleRegistry::register()` from its provider; both paths end in the same registry). One tick run per minute, from the application's scheduler: declarations are synchronised to their rows, the due tick is claimed by inserting its row under the unique `(schedule, instant)` index — exactly one of any number of racing schedulers wins, and the loser's transaction rolls back whole, execution included — the execution is created in the claiming transaction with a `schedule:{Class}@{tick}` correlation id, and the push follows the commit. Missed ticks follow the declared policy (`skip` counts the gap on the tick that runs; `catch_up` runs them oldest first, each told its own tick, bounded per run and by a window); `withoutOverlapping()` claims the tick and records what it declined to run beside; a lost queue push is healed by the next run, which may re-dispatch what its own ticks started because a scheduled execution is never work the application was holding. Two events (`WorkflowScheduleTicked`, `WorkflowScheduleSkipped`), three exceptions, a `laraflow.schedules` configuration section, and the `ScheduleRepository` contract, swappable through the container. The contract is `docs/schedules.md`.

- **Two new tables for scheduled workflows** — the tenth and eleventh post-freeze migrations, `2026_11_03_000000` and `2026_11_03_000001`: `laraflow_schedules`, one row per registered schedule synchronised from the class that declares it, and `laraflow_schedule_ticks`, one insert-only row per tick, whose unique `(schedule_id, tick_at)` index is the "exactly one execution per tick across any number of schedulers" guarantee (`docs/schedules.md`). Both are new tables touching nothing existing, so the migrations are safe against live workers. Operationally nil: two empty tables, no index builds on populated tables.

- **A client-side rate limit may be scoped per tenant.** `rate_limit` gains `scope`: `connection` (the default, one budget per account, exactly as before) or `tenant`, one budget per connection *per tenant of the running execution*, read from the execution's durable `tenant_id` rather than from anything ambient to the worker. For an account many tenants share, one tenant's burst now spends its own ceiling instead of the one every other tenant is held to. A call made outside any execution, or from one created without a tenant, draws on the connection's budget: the scope narrows a budget, it never invents one. The per-tenant bucket was the one Milestone 7 audit finding Milestone 8 deferred, because the connector layer had no view of the executing tenant; it has one now (below). `RateLimitScope` is the new public enum; `laraflow:connectors` prints `per tenant` beside a ceiling scoped this way. See `docs/connectors.md`.

- **Three contract documents, written before their code.** `docs/schedules.md`, `docs/triggers.md`, and `docs/tenancy.md` fix the semantics of Milestone 10's schedules, signed triggers, and per-tenant ceilings — what is persisted, what is refused and why, what every caller sees — as every milestone since the seventh has done, before any of it was implemented; each names the suite that enforces it.

- **A durable signal inbox: a signal that arrives before its step parks is kept, not refused.** A signal for an unfinished execution not parked on that name *yet* — pending, an earlier step still running, a claim holding it, retrying, or waiting on another name — is recorded in the new `laraflow_signal_inbox` table (the thirteenth post-freeze migration, `2026_11_04_000001`: a new table touching nothing existing), one row per execution and name, latest delivery wins, the name matched byte for byte through a SHA-256 unique key so case-insensitive collations cannot merge two names. When a step parks on that name the park consumes the row in the same transaction and the wait resolves at once under the same claim; a claim that re-parks a signal wait consumes it too. Reserved `laraflow.` names are never buffered. Rows nothing consumed go with their execution — deleted by the scrub tier (they are payload) and with the execution by the delete tier. The one consequence to design for, stated in `docs/advanced-workflows.md`: a late duplicate is indistinguishable from an early signal, and answers the next wait on the same name in that execution.

- **The fourteenth post-freeze migration, `2026_11_04_000002_store_laraflow_timestamps_in_utc`.** Converts every existing Laraflow timestamp from `app.timezone` wall-clock to UTC — a no-op when `app.timezone` is UTC, otherwise a chunked PHP rewrite in one transaction that **must run with workers and the scheduler stopped** — and, on MySQL and MariaDB only, retypes every Laraflow `timestamp` column to `datetime` (precision 0 kept), ending the 2038 overflow and the session-time-zone conversion. Columns and indexes are unchanged; the rollback is the exact reverse. Sequence and caveats in `docs/upgrading.md`, "The UTC timestamp migration".

- **`laraflow.recovery.redispatch_after`** (seconds, default 60; `LARAFLOW_RECOVERY_REDISPATCH_AFTER`): how long a queue push counts as in flight for `laraflow:recover`'s due-retry, due-wait, and pending scans. `0` re-pushes everything due on every run, as before.

- **A separate rule for who may act on the dashboard.** `Dashboard::authActions()` or `laraflow.dashboard.action_gate` narrows the four actions beyond the view rule; with neither, behaviour is unchanged. A named gate that is never defined denies.

- **`laraflow:prune` gained the tick tier `docs/schedules.md` had promised.** `retention.prune_ticks_after_days` (and `--prune-ticks-after`) delete schedule tick history by the instant each tick was claimed, bounded by the run's limit, never touching the executions the ticks started. The `deferred_until`-shaped index for it shipped with the tables.

- **`WorkflowRunner::recordSignal()` and `SignalReceipt`: what recording a signal did.** `recordSignal()` is `signal()` returning a `SignalReceipt` — the execution, and `buffered`: false when a step parked on the name took the payload and the execution is due now, true when the signal inbox kept it for the step that will wait on it. `laraflow:signal`, the dashboard's signal action, and the trigger endpoint read it, so none of them calls a buffered signal "due now" or hands an execution nothing became due for to the queue: the console says *buffered* (and its `--json` document gains `recorded`: `resumed` or `buffered`), the dashboard says so instead of dispatching, and the trigger's `202` carries `delivery: buffered`. `signal()` is unchanged. Experimental.

### Changed

- **`ExecutionRepository` is now `ExecutionReader` plus `ExecutionStore`, and declares nothing of its own.** The split itself is non-breaking — it moved no method and changed no signature, so existing bindings and type-hints work unchanged (the release's other changes to the contract are under *Breaking*). What changed is the promise — only the reader half is Public; the store half is experimental and will not be frozen at 1.0. The console, the dashboard, `Handoff`, and the trigger endpoint now type-hint `ExecutionReader`, since they only read.

- **The runner records which execution it is running, for the layers beneath it.** `Laraflow\Support\ExecutionScope` (internal) is entered under the claim and left from a `finally`, nests the way the log context does, and drives the log context itself so the two cannot disagree about what is running. `WorkflowRunner`, `TransportPipeline`, and `ThrottlingTransport` take it as a collaborator — internal wiring, resolved from the container, but a test or an application constructing any of the three by hand supplies it now where it supplied a `LoggingContext` before.

- **Database engine floors raised, per the drop policy.** `docs/compatibility.md` drops an engine version when its vendor ends general support, in a minor release before 1.0. Four floors had passed that point, so this release raises them: MySQL 8.0 to **8.4** (the LTS line; 8.0 reached end of life in April 2026), MariaDB 10.6 to **10.11** (10.6's community support ended in July 2026), PostgreSQL 13 to **14** (13 ended in November 2025), and SQL Server 2019 to **2022** (2019's mainstream support ended in February 2025). CI now runs each floor and, where the vendor has a newer supported release, that too — MariaDB 11.4 and PostgreSQL 17 — on both Laravel majors. Nothing in the schema or the queries changed: an application on an older engine is not refused, it is no longer tested, and its bug reports are no longer treated as defects.

- **`dragonmantank/cron-expression` is a declared dependency.** Milestone 10's schedules read cron expressions through it; `illuminate/console` only suggests it, and every Laravel application already has it through `laravel/framework`, so nothing new installs. Required at `^3.4`, the constraint both supported Laravel majors share (`docs/compatibility.md`).

- **Four passages had not followed the code.** `CONTRIBUTING.md` still named fan-out and compensation as deferred work two milestones after they shipped; `docs/retry-and-failure-policy.md` said compensation was out of scope and now points at its contract; the README said the bundled connectors stay experimental "until the first release", which 0.1.0 was, and now says until 1.0; the runner table in `docs/execution-lifecycle.md` had never listed `signal()`. `SECURITY.md`'s supported-versions table named `0.1.x` as the latest minor.

- **Documented: the connector host guard covers the links Laraflow follows, not the URIs an application passes it.** `pages()` refuses a next-page link to a foreign host because Laraflow chose to follow it; `request()` sends the URI the caller gave, and an absolute one reaches that host with the connection's credentials on it — deliberately, since a connector legitimately calls a signed upload endpoint elsewhere. `docs/connectors.md` and `SECURITY.md` now say so, and say that a URI built from a provider's response or from workflow input is the case to check before handing it to `request()`. Also: `WorkflowCompensationStarted` is documented as firing once per pass *attempt*, matching its `WorkflowCompensated` counterpart.

### Deprecated

- **`make:workflow`, `make:step`, and `make:connector` are now `laraflow:make-workflow`, `laraflow:make-step`, and `laraflow:make-connector`.** The old names sat in Laravel's own namespace, where other workflow packages ship the same commands and whichever provider boots last wins. They remain as hidden commands that forward to the new names — arguments and options alike — print a deprecation warning, and appear in no `artisan list`; they will be removed in a future minor release.

### Breaking

- **Public concrete classes are final unless designed for extension.** Value objects, services, events, `WorkflowRunner`, `WorkflowDispatcher`, `ExecuteWorkflowJob`, `LaraflowManager`, `LaraflowServiceProvider`, the paginators, `BearerTokenAuthenticator`, and every leaf exception are now `final`; so are the console commands and every internal class nothing subclasses. Left open on purpose: the abstract bases, `StatusErrorMapper`, the exception bases, and the five classified provider errors (`AuthenticationFailedException`, `NotFoundException`, `RateLimitedException`, `ClientErrorException`, `ServerErrorException`), which a connector may narrow. Code that subclassed a now-final class should implement or decorate the documented interface instead and bind it in the container; `ProjectContractsTest` enforces the policy. `ThrottledException` and `TenantThrottledException` narrowed `suggestedRetryDelaySeconds()` to `int`, which they always returned.

- **A custom `ExecutionRepository` gains new obligations.** `claim()` consults the execution's tenant ceilings before its compare-and-set — for rows the claim could actually take, and never for one it would refuse — recording a refused claim's deferral on the row (`docs/tenancy.md`), and gained a trailing `bool $reexecuteFailed = false` (below). Added: `deferred()`, the attention scan's read of what a ceiling is holding; `park()`, which writes a step's park and the execution's release in one claim-guarded transaction, consuming a buffered signal instead of parking when one is there; `childOfStep()`, a parent step's child by the parent-step index; and `createMember()`, which creates a fan-out member exactly once per index under the step row's lock. `recordSignal()` buffers rather than refuses a signal for an unfinished execution not yet parked on the name — `SignalRefusedException` now means the execution can never park on it (completed, cancelled, failed, compensating, missing, or a reserved name) — and returns a `SignalReceipt` saying which it did, where it returned the execution. The four recovery scans take a trailing `?DateTimeImmutable $availableBefore = null`, keeping their one shape. A custom implementation must provide all of them (`docs/public-api.md`).

- **Constructor collaborators, for anything built by hand rather than resolved.** `WorkflowRunner` takes an `ExecutionScope` where it took a `LoggingContext` (the scope drives the context); `TransportPipeline` and `ThrottlingTransport` take the scope too, for the tenant-scoped rate-limit bucket; `EloquentExecutionRepository` takes `TenantCeilings`; `RetentionService` takes the `ScheduleRepository` for the tick tier; `AttentionScan` takes it for the stalled line, and `AttentionReport` carries two new collections. All are container-resolved in any ordinary application.

- **Console JSON shapes, tightened by the operator-edge audit.** The queue handoff outcomes are `push_failed` and `step_failed` (were `push-failed`, `step-failed`), matching every other snake_case outcome word. A bulk `laraflow:cancel` or `laraflow:execute` selects only what it can act on — completed and cancelled rows are never selected, `matched` counts the actionable set, a `--status` naming only terminal statuses is refused, and the document gains `ignored_statuses`. Under `--dry-run`, `actions[].outcome` is a prediction from status (`would_cancel`, `would_request`, `already_cancelled`, `would_refuse`; `would_run`, `would_queue`, `would_refuse`) and `counts` holds the predicted tallies. A bulk re-run's `counts` gains `cancelled`, and a row's outcome is bucketed by what it came to — a cancellation honoured mid-run is `cancelled`, anything but completed, retrying, or waiting is `failed`, never `ran`. `laraflow:schedules --pause/--resume/--forget` exits on the action's own result, not the listing's health, and the document carries `action`. Oldest-first execution cursors carry an `a` prefix; newest-first cursors are unchanged.

- **Laraflow's stored timestamp convention is UTC, independent of `app.timezone`.** Every timestamp column on every Laraflow table — `created_at` and `updated_at` included — is written, compared, and read as UTC at the model boundary; it was the application's wall-clock, Eloquent's default. Values handed to application code (`WorkflowExecution`, `StepExecution`, `StepAttempt`, `ScheduleTick`, events, the dashboard, `--json`) are the same instants as before, still rendered in the application's zone. A custom `ExecutionRepository`, `ScheduleRepository`, or `IdempotencyStore` writing Laraflow's tables, and any report or query reading them directly, must treat the columns as UTC. Nothing changes for an application whose `app.timezone` is UTC, beyond MySQL/MariaDB column types. See `docs/compatibility.md`, "Stored timestamps".

- **Re-running a `failed` execution is an explicit opt-in.** `ExecutionRepository::claim()` gained a trailing `bool $reexecuteFailed = false` and refuses `failed` without it, with `ExecutionNotRunnableException`; `WorkflowRunner::execute()` gained `bool $reexecuteFailed = true` (calling it is the operator's act) and `WorkflowDispatcher::dispatchExecution()` gained `bool $reexecuteFailed = false`, carried on the new `ExecuteWorkflowJob::$reexecuteFailedAt`. An application that re-ran failures by calling `dispatchExecution()` itself must now pass `reexecuteFailed: true`; `laraflow:execute`, the dashboard, and `Handoff` already do.

- **Trigger routes are throttled and size-bounded by default.** `laraflow.triggers.middleware` defaults to `['api', 'throttle:60,1']`, and the new `laraflow.triggers.max_body_bytes` (65536) refuses a larger body with `413` before it is hashed, on the signed endpoint and ahead of named triggers' verifiers; the refusal reason is the new `TriggerRefusalReason::BodyTooLarge`. An application that published its config keeps its own middleware list, and should add a throttle to it.

### Fixed

- **The closing audit, scoped to the dashboard and Milestones 9–10, found and fixed twelve defects — three of crash or wrong-schedule grade.** Four hostile reviews (concurrency and durability, security on the trigger boundary, contract alignment, code and test quality) produced the findings; each fix landed with the regression test that would have caught it, and roughly thirty stale document sentences were realigned. The worst three:
  - **Schedules kept UTC wall-clock in columns the rest of the package reads in the application's timezone.** Eloquent stored the wall-clock of the value it was given and read columns back in `app.timezone`, so in any non-UTC application an hourly schedule fired once per hour *plus the offset*, and the lost-dispatch heal re-pushed a duplicate on every run. The audit's first fix — carrying ticks on the application's wall-clock like every other column — closed that, but left the repeated autumn hour ambiguous: 05:00Z and 06:00Z are both 01:00 in New York, so the second of two hourly ticks met the unique `(schedule_id, tick_at)` key and was reported *taken*, a lost tick misreported; and `next_retry_at`, `deferred_until`, `available_at`, and wait due-times compared ambiguously for that hour. Resolved in the v0.6.0 audit by storing every Laraflow timestamp as UTC at the model boundary (see *Breaking*), whatever zone the instant arrives in; the New-York end-to-end test still holds hourly firing, and new tests hold both ticks of the repeated hour starting and a retry not due early across it.
  - **Tenant ceilings were consulted before claimability, so refusals became deferrals.** A duplicate delivery for a running, finished, or not-yet-due execution at a pinned tenant was *deferred* — stamping `deferred_until` on rows whose claim could never land, including an every-fifteen-seconds re-queue loop for a completed execution. Ceilings now apply only to a row the claim could take, the deferral write is compare-and-set on the status the ceiling counted under, and `deferred()` excludes terminal rows.
  - **An impossible-but-parseable cron expression (February 30th) crashed the scheduler run, the listing, the summary, and the overview at once.** `Schedule::cron()` now proves the expression matches a real date at the declaration site; the tick run isolates any per-schedule `Throwable` as that schedule's failed row; and the health math treats a row whose expression no longer computes as simply not stalled.
  Also fixed: every recovery scan and the scheduler's re-dispatch now wait out `deferred_until`, so a pinned tenant no longer accumulates one re-queued job per scan per run; a repeated DST hour fires once (and the skipped spring hour fires once, at the next valid time); a child workflow's tenant deferral on the sync driver parks the parent on the child instead of failing the step; `laraflow:recover` reports a ceiling refusal as `deferred (tenant at ceiling)` and never as a failure; the dashboard overview no longer hides a stalled schedule behind an empty executions table; `laraflow:schedule --sync` runs its lost-dispatch heal in-process and exits non-zero when an inline delivery's step fails, as `laraflow:recover --sync` does; `laraflow:recover --json` keeps its document shape on an empty day; and a malformed `laraflow.schedules.workflows` is a one-document `--json` refusal rather than a stack trace.

- **The trigger boundary, hardened by its review.** The 202 response no longer carries a step's or a broker's exception text — a provider keeps response bodies, and failures live on the record where the redactor governs; `execution_status` says what happened. Every key in `previous_keys` must now meet the 32-byte floor a short rotation leftover would have quietly waived. A refused request's signal — unverified URL input — is bounded to 255 bytes and stripped of control bytes before any log line or event repeats it. The body is hashed once per request rather than once per configured key. And execution identifiers that are not valid UTF-8 are refused outright: `preg_match` returns false, not zero, on bytes it cannot read, and the old guard read that as a pass.

- **The dashboard and trigger boundaries, hardened by a further review.** A step's exception flashed by a dashboard action (`A step failed: …`, and the sync-driver handoff's step failure) now passes through the configured `ErrorRedactor` and `execution.max_error_length`, as `SECURITY.md` promised. The action routes check the CSRF token themselves (`_token` or `X-CSRF-TOKEN` against the session, `hash_equals`, `419`), so a custom stack with a session but no `VerifyCsrfToken` no longer leaves them forgeable. A delivered signal goes through the shared queue handoff, so an inline step failure on a `sync` connection is reported as one rather than as a failed dispatch. The overview's status cards intersect with a status filter instead of replacing it — statuses the filter excludes show 0, shares no longer exceed 100% — and each card links to its own status alone.

- **A compensated execution's failure event named the wrong class.** `failRecorded()` rests an execution on the failure recorded when its compensation pass began, and wrote the real class to `error_class` — then announced it with a bare `WorkflowException`. A listener on `WorkflowExecutionFailed` therefore saw every *stopped* or *resumed* saga fail as `WorkflowException` while the row beside it said otherwise, which is alerting on the wrong cause. `RecordedFailure`, which exists for exactly this and reports the class it stands for, is used for the event and the log line as well as the column.

- **A live compensation pass was refused as a finished execution.** `docs/execution-lifecycle.md` has specified since the contract was written that a fresh claim on a `compensating` execution yields `ExecutionAlreadyClaimedException`, "as for `running`". The claim predicate learned the status in the Milestone 9 audit; the refusal *explanation* did not, so it fell through to `ExecutionNotRunnableException` — which `docs/public-api.md` defines as "a terminal status" and which `ExecuteWorkflowJob` logs as "already finished (completed or cancelled)". A duplicate delivery arriving while a worker was undoing an execution reported the opposite of the truth. Both statuses now route to the claimed refusal, whose message names which of the two it is.

- **A second fan-out under one parent summarised no members at all.** `FanOutGroup::memberIds()` read a single page of the parent's children, oldest first, and narrowed to the step in PHP — so for any fan-out whose members are all newer than one page of an earlier group's, the filter matched nothing and the step's output carried `members: []` beside correct counts. It walks pages until the sample is full now, which costs nothing for the single-group case and is the only way to be right for the rest. `FanOutGroup`'s join policy also lost its default: the park path asked the step for its policy and the resume path — where nearly every join actually decides — took the default, so a second policy would have been honoured on the way in and ignored on the way out.

- **Retention could separate a live fan-out.** `docs/retention.md` has promised since Milestone 4 that retention "can never separate a live pair", reasoning that a parent waits only on an unfinished child. That is true of a sub-workflow and false of a fan-out: a parent parked on a join waits for the whole group, so a member that completed early is finished, and ageable, while its siblings run. The delete tier would take it — and because the join decides from `childProgress()`, which counts the rows that exist, pruning away the members that *failed* turned a group that should fail into one that completes with a summary. Deletion now skips any execution whose parent has not finished, asked in the scan and again inside the delete transaction; scrub and attempt pruning are unaffected, since both leave the identity and status a parent reads.

- **The operator's edge, hardened by its audit.** An unexpected exception under `--json` is one `{"command", "ok": false, "error", "exception"}` document and exit 1, not a stack trace on a stream bound for `jq`; the human form is unchanged. Console error messages — that catch-all, a failed run's `error`, and a bulk row's `message` — pass through the configured `ErrorRedactor`, as the execution row's copy already did. Bulk cancel and re-run no longer loop: "run the same command again" is said only when a second run would make progress, and a batch that left rows in place (refused, or a cancellation merely requested) says so and names the way past them. `matched` is counted before the page is read, so `selected` can never exceed it. `--limit`, `laraflow:prune`'s day and size options, and `laraflow:recover`'s seconds accept digits only — `1.5` and `1e2` were read as 1 and 100. An empty time window names `--since`/`--until` on the console and `since`/`until` on the dashboard instead of `createdAfter`/`createdBefore`. The console and the dashboard now read a filter the same way through `FilterInput`: comma-separated lists, a leading backslash on a workflow class stripped, and one 20-value cap — past which the console refuses and the dashboard drops and says so, as each already did for an unknown status. A newest-first cursor handed back with `--oldest` is refused instead of silently skipping rows. `laraflow:schedules --forget` asks in production unless `--force`, and refuses `--json` there without it. `laraflow:summary` and `laraflow:schedules` add `"reason": "needs_attention"` beside an `ok: false` that is health, not an error.

- **A duplicate queue delivery re-ran a terminally failed execution.** The claim accepted `failed` unconditionally, so the broker's second copy of the delivery that failed an execution — at-least-once delivery is every backend's right — ran it again, side effects included, with nobody having asked. A plain delivery now finds a failed execution not runnable and is a logged no-op, as for completed; only an operator's action re-runs one — `laraflow:execute` and the dashboard in-process, or queued through `Handoff`, whose job names the failure it was issued for (`failed_at`), so a duplicate of the operator's own job cannot re-run the *next* failure either. Recovery, inline or queued, and the scheduler's heal never opt in. `docs/queue-and-recovery.md` has the table.

- **`laraflow:recover` re-pushed, on every run, work already on the queue.** The due-retry, due-wait, and pending scans ignored the dispatch record, so a backlogged queue gained one more copy of each due job per run for as long as the backlog lasted. They now skip a row whose last push became deliverable (`available_at` — the push, or a delayed delivery's due time) within `recovery.redispatch_after`, the shape the scheduler's own heal already had; a push that really was lost is re-pushed once the window passes.

- **Pruning tick history broke `withoutOverlapping()`.** The tick tier deleted by age alone and could take a schedule's most recent fired tick — the row the overlap check reads to find the execution to wait on — so the next tick started beside a run still going. The tier, and its `--dry-run` count, now keep each schedule's latest fired tick and any tick whose execution still exists unfinished.

- **A stored step class was built before it was checked.** `StepResolver::make()` resolved the class a persisted plan named from the container and only then asked whether it was a `Step`, running an arbitrary constructor (and resolving its dependencies) for a row naming something else. It asks `is_subclass_of()` first, as plan validation and `WorkflowResolver` already did.

- **A signal arriving while its step parked was refused.** The park was two commits — the step `waiting`, then the execution — and a signal between them found the step parked on an execution still `running` and was refused by the compare-and-set that requires `waiting`. The park is one transaction now, ordered against `recordSignal()` on the execution row, and a signal that arrives early is kept in the new inbox (*Added*).

- **Finding a sub-workflow step's child paged through every child of the parent.** `ChildWorkflows` read the parent's children a page at a time and narrowed to the step in PHP — a thousand-row read on every claim for a parent that also fans out. It reads by `parent_step_execution_id`, one indexed query.

- **Two workers could create the same fan-out member.** Members were created at the index the existing count implied, with nothing holding the count still, so a stale reclaim racing the original worker through a partial creation made member *k* twice. Each creation is now guarded in one transaction under the parent step row's lock: a second creator finds member *k* already made and makes nothing.

- **An idempotent value whose marker vanished was silently dropped.** `EloquentIdempotencyStore::settle()` ignored its affected rows; a settle that matched no row because the pending marker had gone left nothing behind, and the next attempt read "never ran" and repeated the side effect. A settle with no record now writes the settled record back (unless another attempt has begun the key since, whose record stands); a settle on a record that is merely no longer pending keeps the first outcome, as the contract says, and a `fail()` with no record needs nothing.

- **`recordSignal()` claimed a serialisation SQLite does not give.** `lockForUpdate()` compiles to nothing on SQLite; the comment now says what does keep it correct there — the compare-and-set in each write, the inbox's unique key, and the single writer turning a race into a retryable `database is locked` error — and `docs/advanced-workflows.md` says the same.

- **`docs/tenancy.md` now says the rate ceiling needs a shared cache store**: the counter is Laravel's fixed-window `RateLimiter`, in the `cache.limiter` store, and under the `array` store each worker counts alone.

## [0.5.0] - 2026-11-02

Milestone 9: parallelism and compensation — the two capabilities Milestone 7 deferred, each specified in `docs/advanced-workflows.md` before a line of it was written. Both are additive and opt-in by declaration: a workflow that fans out nothing and undoes nothing behaves exactly as it did under 0.4.0. Two additive migrations and one new `ExecutionStatus` case; **breaking** for a custom `ExecutionRepository`, which gains three methods.

### Removed

- **The five `WorkflowExecutionRetryScheduled::REASON_*` constants.** Deprecated in 0.3.0 in favour of the `RecoveryReason` cases, announced there for removal in 0.4.0, and overdue by one minor — the removal was missed when 0.4.0 was cut and is taken here rather than left to drift further. Nothing in the package read them. Every string they carried is still the backing value of exactly one case, so a listener comparing `$event->reason->value` to the literal `'stale_claim'` is unaffected; one that referenced the constant by name uses `RecoveryReason::StaleClaim` (and `->value` for the string). A test now holds the class to carrying no `REASON_*` constant, since one reintroduced would be born deprecated.

### Added

- **The semantics of fan-out/fan-in and compensation, decided before either is built.** `docs/advanced-workflows.md` — which specified Milestone 7's three capabilities before they existed and is now their shipped contract — gains both, written the same way. A fan-out is **one plan step** whose members are child executions: the plan stays a flat validated list, graph branching stays out of scope, and the member list is read once, recorded, and created in resumable chunks. The join waits for every member (`WaitAll` is the only policy that ships; cancelling siblings on a failure is a destructive reaction nothing has asked for, and the enum is shaped so adding it later is additive), heartbeats like a single child's park, and asks for the group's progress in one indexed aggregate rather than by reading a thousand rows. A compensation is **an ordinary step row** appended after the plan with a link to what it undoes, so it is retryable, attempt-tracked, and inspectable without new machinery; it is opt-in by declaring it, runs only on terminal failure, skips the step that failed, and stops at the first compensation whose retries are exhausted rather than reaching past it. Neither a fan-out nor a sub-workflow compensates its children — acting at a distance on executions a parent does not own is the hidden authority the shared principles forbid.

- **`ExecutionRepository::childProgress()`: the children of one parent step, counted by status, in one indexed query.** A fan-out's join asks how its members are doing on every heartbeat, and a group may be a thousand wide; reading the members to count them would make the heartbeat cost what it exists to avoid. The method returns a `ChildProgress` (Public) — counts and nothing else — and is served by the **eighth post-freeze migration** (`2026_11_02_000000`), an index on `parent_step_execution_id`, which Milestone 7 had left unindexed because it was only ever read for one known child. Additive and reversible; the upgrade harness rolls it back and forward with the rest; an index build is not online on PostgreSQL or SQL Server — see `docs/upgrading.md`. **Breaking** for a custom `ExecutionRepository`, which must implement it. A deliberate addition to the public contract under the Milestone 4 rule, not a shortcut for the dashboard or the join.

- **Fan-out/fan-in: a step runs many workflows in parallel as child executions and parks until all of them finish.** `FanOutStep::members()` yields a `FanOut` — a workflow and its input — per member. Composition widened, not a new mechanism: a member is a child execution with the same linkage, depth bound, cancellation cascade, and retention predicates a sub-workflow's child has, and the plan is untouched — the fan-out is one class at one position. `members()` is read **once**, and what it yielded is recorded on the step row's `input` (written once, never erased) *before* any member is created, so a worker that dies part-way through leaves a remainder the next claim computes from the count that exists; a test kills the delivery mid-group and proves the remainder is made and `members()` is not read again. Members are delivered as they are created; the step then parks on the reserved `laraflow.join.{stepRowId}` signal, heartbeating on `stale_after` like a single child's park, and the **last member to rest** records the join with the group's counts. On the sync driver the group runs inline and the step completes without parking. The step's output is the group's shape — total, completed, member ids — never a member's context. Width is bounded by **`laraflow.workflows.max_members`** (default 1000), refused with `FanOutTooWideException` before anything is created.

  **The join waits for every member** — `JoinPolicy::WaitAll`, the only policy that ships. A member that fails does not fail the step while its siblings are still going; when the whole group has rested, every member completed means the step completes with the summary, and anything else fails it with `FanOutFailedException`, which names how many ended in each state and the first five that did not complete. That failure is an ordinary step failure under the step's retry policy, and **a retry resumes the members that did not complete rather than charging them twice or creating siblings**: a member whose failure predates the attempt is the attempt's work, not its answer, so it is handed back to a worker and the step parks again until it rests; a cancelled member cannot be resumed and the group reports the same outcome on every retry until an operator intervenes. On the sync driver a member's own failure surfaces inside the parent's delivery call and is contained — it is already the member's durable record, and the group decides from the record — as is a push that fails on any driver, which leaves the member pending for the heartbeat and is logged rather than failing the fan-out. New: `FanOutStep`, `FanOut`, `JoinPolicy` (one case, `WaitAll`), `FanOutWorkflows` (Public contract, for the reason `ChildWorkflows` is), `FanOutFailedException`, `FanOutTooWideException`, the `WorkflowFanOutStarted` event, and `Wait::forJoin()`. The depth walk a sub-workflow and a fan-out share moves to `Nesting` (internal) so the two cannot count differently. `StepExecution::$input` is writable through `declare()`, and the repository writes it only when the handle carries one.

- **Compensation: a step may declare how to undo itself, and a failing workflow undoes what completed, in reverse.** A step implementing `CompensatableStep::compensate(Compensation)` is compensated when the execution fails **terminally** — the failing step's retries exhausted, and under `FailurePolicy::Continue` the remaining steps run first. Opt-in by declaring it: a workflow whose steps none of them do behaves exactly as before, with no policy to set and no rows appended.

  **Each compensation is an ordinary step row**, appended after the plan and linked to what it undoes by the new `compensates_step_execution_id` (the **ninth post-freeze migration**, `2026_11_02_000001`, additive and indexed). That one decision buys attempts, retries, timeouts, the attempt history, `laraflow:show`, and the dashboard with no new machinery — the saga is inspectable because it *is* steps. The plan is then the rows that compensate nothing, which is how plan validation keeps comparing like with like. A compensation is retried under **the compensated step's own policy** — the step that declared the undo declared how hard to try it — and the pass **stops** at the first undo whose retries are exhausted rather than reaching past it to undo earlier work the failed one may have depended on. The step that failed is never compensated: it did not complete, and a step that threw is in a state only the application knows.

  The execution is `compensating` while a pass runs — a new `ExecutionStatus` case, the first since that enum promised more might be added, and one the playground's own status match did not handle until this milestone made it. An undo whose retry is scheduled rests the execution as `retrying`, accurately, and the existing due-retry scan delivers it with no new mechanism; an interrupted pass is resumed by the next claim, which continues undoing rather than re-running a plan that is finished with. The failure the execution will rest on is recorded when the pass begins, so a pass spanning claims still ends on the right error — and an undo's own failure never overwrites it. The resting state is `failed` either way: compensation changes what was left behind, not whether the execution failed. Neither a fan-out nor a sub-workflow compensates its children. New: `CompensatableStep`, `Compensation`, `CompensationFailedException`, the `WorkflowCompensationStarted` and `WorkflowCompensated` events, and `Compensator` (internal). **Breaking** for a custom `ExecutionRepository`: `appendCompensation()` and `checkpointStatus()` were added. Contract: `docs/advanced-workflows.md`.

- **CI proves both capabilities in a real application.** The install walk gains two stages: a hand-written `FanOutStep` whose three members run on the skeleton's database queue and whose join the last member signals, and a `CompensatableStep` whose undo runs when the workflow fails — asserted by the file the undo wrote, by `laraflow:show` marking the compensation row, and by the dashboard page saying the same. Written by hand rather than generated, so the walk also checks the classes an author writes against the published base class and interface.

  Rehearsing it found a real defect in Milestone 8's `laraflow:start`: a bare workflow name resolved against the **global** namespace before the application's, and Laravel registers class aliases for its facades — so `laraflow:start Broadcast` for an `App\Workflows\Broadcast` resolved to the `Broadcast` facade and was refused as "not a workflow", blaming the user's class for a collision it did not cause. The same would have hit `Queue`, `Log`, `Schema`, `Event`, and a dozen more. A bare name now means the application's `Workflows` namespace first.

### Changed

- **What became of handing an execution to the queue is decided once.** A sync queue connection runs the job *inside* the dispatch call, so a call that returns may mean "queued" or "already finished", and a call that throws may mean "the broker refused" or "a step failed" — a distinction the configured driver cannot make and the record can. That decision had been written out three times, and two of the copies disagreed (Milestone 8.5 audit). `Laraflow\Support\Handoff` now makes it once for `laraflow:start`, `laraflow:demo`, `laraflow:execute --queue`, and the dashboard's execute, start, and signal actions; each renders the result rather than re-deriving it, so the console and the browser report a handoff in the same words. `laraflow:execute --queue`'s "queued" message now names the execution and `queue:work`, as the other commands' already did.

## [0.3.0] - 2026-11-02

Milestone 8: the foundations for a stability promise — the design debt the Milestone 7 audit deferred, workflow versioning, a first-class idempotency store, the install and generator commands, and a CI matrix that proves all of it on every supported engine.

### Breaking

- **Execution and step ids are `int` on every signature.** `ExecutionRepository` (`find`, `claim`, `recordSignal`, `recordDispatch`, `requestCancellation`, and the id lists `stepProgress` and the retention methods take), `WorkflowRunner` (`execute`, `signal`, `cancel`), `WorkflowDispatcher::dispatchExecution()`, `ExecuteWorkflowJob`, `ChildDelivery`, `Wait::forChild()`, `WorkflowResolver`, the `WorkflowExecution`/`StepExecution`/`StepAttempt` handles, `WorkflowContext::executionId()`, `ExecutionOptions`, `ExecutionFilter::$parentId`, every lifecycle event's `executionId`, and the workflow exceptions' factories all previously accepted or carried `int|string`. The persistence has used `$table->id()` since Milestone 0 and cast every id to integer since Milestone 6, so no stored value changes; the union was a hedge for an alternative persistence that never came, and the Milestone 7 audit asked for a commitment. `laraflow:show`, `laraflow:execute`, and `laraflow:cancel` now validate the argument and refuse a non-integer id with a message naming the argument, instead of reporting it "not found". `ExecutionRepository::stepProgress()` is declared as keyed by `int` — PHP had always coerced its numeric-string keys to integers, so the declared `array<string, …>` shape was the one thing that changed — and `Wait::childIdFrom()` returns `int`, reading a signal `forChild()` did not write as `0`, an id no execution can have. A test holds every id-named parameter and property in the package to `int`.
- **The four recovery scans on `ExecutionRepository` share one signature.** `stale()` and `pendingBefore()` gain the trailing `?string $tenantId` that `dueForRetry()` and `waitingDue()` already took, so every scan is `(DateTimeImmutable $before, int $limit = 100, ?string $workflow = null, ?string $tenantId = null)`; a custom implementation must accept and honour the scope on all four. `RecoveryService::scan()` gains a trailing `?string $tenantId` and applies it to every scan it runs, and `laraflow:recover` gains `--tenant=`, so a tenant-scoped recovery run can no longer touch another tenant's work — before this, a `--tenant` on the recover command did not exist and the Milestone 7 audit found half the scans could not have honoured one. A reflection test holds the four scans to one shape, and a repository test proves each honours the tenant the same way.
- **`WorkflowExecutionRetryScheduled::$reason` is a backed enum rather than a string.** `Laraflow\Workflow\RecoveryReason`, with cases `StaleClaim`, `StepTimeout`, `RetryDue`, `WaitDue`, and `NeverDispatched` whose backing values are exactly the strings the event carried before. A listener comparing `$event->reason` to a string with `===` now needs `$event->reason->value`, or a match on the case. The enum also carries `isInterruption()` — the distinction the abandonment bound has always drawn between crash-loop kinds and scheduled work — and `label()`, the wording the recover report prints, so the command no longer spells it. `RecoveryCandidate::$reason` changes the same way.
- A custom `ExecutionRepository` must implement two new methods: `create()` gained a trailing `int $planVersion = 1`, and `rewritePlan()` was added for workflow versioning. The Eloquent implementation the package ships is unaffected.
- `WorkflowRunner`'s constructor takes a required `IdempotencyResolver`, and `WorkflowContext`'s a trailing optional one. Service constructors are documented as internal wiring and the service provider supplies both, so this breaks only code that built a runner by hand — which now passes what it wants explicitly. Listed here because it is a signature change, not because an application is expected to have depended on it.

### Changed

- **Every service takes every collaborator it needs; none has a nullable default any more.** `WorkflowRunner`, `RecoveryService`, `RetentionService`, `WorkflowDispatcher`, `OutcomeRecorder`, `ParentNotifier`, `EloquentExecutionRepository`, `ConnectorObserver`, `TransportPipeline`, and `ObservingTransport` previously accepted `null` for their clock, event emitter, redactor, policy resolver, runner options, log context, child delivery, or transactions manager and built a default in its place. Each such default was a second, silent configuration — a runner on the system clock while the application had bound another, an observer that emitted nothing — and the Milestone 7 audit asked for them to go. The service provider has always supplied every one of these; it is unchanged except that the dispatcher's transactions manager is now resolved unconditionally, since `illuminate/database` is a hard dependency and always binds it. Constructors are documented as internal wiring, so this is breaking only for code that constructed a service by hand; such code now passes what it wants explicitly, and the test suite does so through `TestCase::makeRunner()`, which fills whatever a test does not name from the container. A contract test holds eighteen service constructors to the rule, with the two documented "off" objects — a `LoggingContext` without a context repository, an `EventEmitter` without a dispatcher — as the only permitted nulls.
- **The wait state machine is its own class.** `WorkflowRunner` had grown past a thousand lines, a third of it the Milestone 7 wait machinery; the audit asked for the extraction. `Laraflow\Workflow\WaitResolver` (internal) now owns parking an execution on a `Wait` and deciding a parked step's fate on the next claim — resumed, timed out, parked again, or settled from a child's outcome — and `OutcomeRecorder` gains the two outcomes both the loop and the resolver need: `completeStep()`, the one completion checkpoint, and `settle()`, the one way every step failure is settled. The runner keeps the step loop, the claim, cancellation, and the cascade; a `StepResolution` (the renamed `WaitResolution`, since plain step failures return it too) now says whether it parked, so the runner honours a cancellation requested across a park exactly where it did before. No behaviour changed: the wait-state, sub-workflow, conditional-step, retry, timeout, and cancellation suites pass untouched.
- **Schema: index `(status, created_at)` on `laraflow_workflow_executions`** (fifth post-freeze migration, `2026_11_01_000000`), serving the opt-in pending scan the way `(status, claimed_at)` and `(status, next_retry_at)` serve its siblings. With only the single-column `created_at` index, an application holding many deliberately-pending executions paid for all of them on every scan for lost dispatches; the Milestone 7 audit recorded the gap. Additive and reversible, and the upgrade harness now rolls it back and forward with the rest; an index build is not online on PostgreSQL or SQL Server — see `docs/upgrading.md`. The schema record in `docs/compatibility.md` also gains the two index-only migrations its "every query is served by an index" table had omitted, and `docs/upgrading.md` now counts Milestone 7's migrations correctly (four, not three).
- **Fixed: the recovery limit is shared across every scan, as documented.** `RecoveryService::scan()` recomputed the budget left for each scan from a closure that had captured the candidate list *by value* when only the stale scan had run, so due retries, due waits, and lost pendings were each budgeted against the stale count alone: with no stale work and `--limit=2`, two retries, two waits, and two pendings returned six candidates. Present since Milestone 2; found by the Phase A audit reading the lines step 2 had just edited. The closure captures by reference now, and a test holds the three scheduled scans to the limit together. `RecoveryService` also reads `RecoveryReason::isInterruption()` for the abandonment-bound exemption instead of keeping its own copy of the distinction.
- **A child signal that names no child fails by name.** A `wait_signal` under the reserved child prefix that is not followed by digits — a row altered outside the package — used to read as child `0` and fail the step as "child execution [0] no longer exists"; it now fails with `ChildWorkflowFailedException::malformedSignal()` quoting the signal, and `laraflow:show` says so too.
- `laraflow:recover` reads `--workflow` and `--tenant` through the same parser as the listing commands; `WaitResolution` is `StepResolution`; `WaitResolver`'s members are private; the three id-taking commands report a bad id before, not around, the operation.

### Added

- **Workflow versioning: a deploy that changes a workflow no longer strands its in-flight executions.** A workflow declares `version(): int` (default 1, recorded as `plan_version` on every execution it creates) and `planMigrations(): array` — callables keyed by the version each one migrates *from*, receiving a `PlanDraft` and editing the step list by class name. When a claimed execution is behind, the declared hops are chained, the plan is rewritten, and the execution carries on. A workflow that changes `steps()` without declaring a version and a migration still fails with `WorkflowDefinitionMismatchException` exactly as before: the refusal is the default and silence means refuse.

  A migration may rewrite only the *undecided tail* of a plan — everything after the last step already decided. That rule is what makes the mechanism safe: a `pending` step row has no output, no attempt history, and no context contribution, so it can be renumbered, removed, or replaced without rewriting history, while every other row is the record of something that happened. Reaching further back is refused with `PlanMigrationRefusedException`, naming the step and the status that froze it, as are a missing hop and a step the plan does not contain.

  Migrations run lazily, under the existing claim, in one claim-guarded transaction, before the first step write — so a migration that throws is bounded by the `fruitless_claims` counter that already bounds every fault in that position, and needs no mechanism of its own. The migrated plan then faces the ordinary definition check: the migration proposes, `steps()` judges. A record *ahead* of the code (a rollback) is never migrated backwards. New: `PlanDraft` and `PlanMigrationRefusedException` (Public), `WorkflowPlanMigrated` (Public event, fired after the commit), `PlanMigrator` (internal), and a `plan_version` column (sixth post-freeze migration, `2026_11_01_000001`, additive with a default). `laraflow:show` prints the plan version once a workflow has versioned its plan. **Breaking** for a custom `ExecutionRepository`: `create()` gained a trailing `int $planVersion = 1` and `rewritePlan()` was added. Contract: `docs/workflow-versioning.md`.

- **The idempotency store: a side effect runs at most once per execution, and a crash inside the window is detected rather than repeated.** `$context->remember('charge', fn () => $payments->charge(...))` runs the work at most once across every retry, recovery, and worker — unless a reconciler asserts a run left nothing behind — and replays the stored value thereafter. The marker commits *before* the work runs and the value after, so a worker that dies between them leaves a `pending` record — positive evidence the work began, none that it finished — and the next attempt is raised `IdempotentOutcomeUncertainException` rather than silently re-running (how a customer is charged twice) or silently skipping (how they are never charged). An optional reconciler is asked first; a non-null answer is the outcome, null asserts the side effect never landed and the work runs again. A thrown exception is a known outcome — the record is marked `failed` and the next attempt starts over — unless it implements the new `IndicatesUncertainOutcome` marker, the counterpart of `SuggestsRetryDelay`, which leaves it pending.

  `(execution, key)` is unique, so two live workers in the same step cannot both perform the side effect: one insert wins and the other is told the outcome is uncertain — enforced by the database rather than by timing, which the claim check cannot help with because it runs after the side effect. Keys are stored as written and scoped to the step by the record — `(execution, step position, key)`, unique — validated (UTF-8, no control characters, no surrounding whitespace, 255 characters), refused by name when the database cannot tell them apart from a key already recorded, and capped per execution by `laraflow.idempotency.max_keys_per_execution` (default 100). Values obey the serialization contract and `max_payload_bytes`. The store follows payload through retention: scrub clears values for completed and cancelled executions and never touches a failed one's, delete removes the records through the orphan-safe path. `laraflow:show --attempts` lists remembered work and flags a pending record, never printing a value. New: `IdempotencyStore` (Public contract, default `EloquentIdempotencyStore`, held to the contract by `Laraflow\Testing\IdempotencyStoreContract`), `IdempotencyRecord`, `IdempotencyStatus`, four never-retried exceptions, `IdempotencyResolver` (Public contract, for the one reason `ChildWorkflows` is), `WorkflowContext::remember()`, and the `laraflow_idempotency_keys` table (seventh post-freeze migration, `2026_11_01_000002`). `WorkflowRunner` gains a required `IdempotencyResolver`; `WorkflowContext` a trailing optional one, nullable because a context built by hand has no execution behind it and `remember()` on it raises `IdempotencyStoreUnavailableException` rather than running the work. Contract: `docs/idempotency.md`.

- **Install and generators.** `php artisan laraflow:install` publishes the configuration, runs the migrations — `--skip-migrations` to do it yourself, `--publish-migrations` to copy them into the application first, with a warning that the package also loads them — and prints what to do next. `make:workflow`, `make:step` (`--conditional`, `--sub-workflow`), and `make:connector` scaffold the three kinds of class an application writes, into `app/Workflows`, `app/Workflows/Steps`, and `app/Connectors`; the connector's docblock carries the `laraflow.integrations` block that registers it, keyed from the class name. A test proves a generated workflow with a generated step passes the validation `start()` applies and runs to completion unedited. The stubs publish under `laraflow-stubs` and a published stub is preferred, as with Laravel's own generators.

  `php artisan laraflow:start {workflow} {--input=} {--queue} {--correlation=} {--tenant=}` starts an execution of any workflow class — fully qualified, with `/` accepted for `\\`, or by a bare name looked for under the application's `Workflows` namespace, where `make:workflow` writes — seeds the context from a JSON object, and runs it inline or dispatches it. A name that is not a `Workflow` and an input that is not an object are refused by name before anything is persisted; a run that ends `retrying` or `waiting` succeeds and says who owns what happens next; a step failure exits non-zero with the record and the `laraflow:execute` command that recovers it. Without it, no install story could be proved with the generators alone: nothing else ran a class that did not ship with the package without writing a caller first. `laraflow:demo` is now this command's start-and-report path with the demo's input filled in — the one difference, a wait is reported as a wait rather than as done.

- **The engine matrix meets Laravel 12 and `prefer-lowest`, and every engine job ends with the install walk.** Each of MySQL 8.0, MariaDB 10.6, PostgreSQL 13, and SQL Server 2019 now runs the suite twice — Laravel 13 on the lock file on PHP 8.4, as before, and Laravel 12 resolved to the floor of every constraint on PHP 8.2, which until now ran on SQLite only — and then builds a fresh `laravel/laravel` application pointed at a second database on the same engine and walks the install story through it. The walk is one composite action (`.github/actions/install-walk`) shared with the SQLite install job, so the two cannot drift, and it is rewritten around what Milestone 8 shipped: `laraflow:install --publish-migrations` in place of `vendor:publish` and `migrate`, the three generators and three `sed` edits in place of the demo workflow, `laraflow:start` to run the result to a persisted failure and `laraflow:execute` to recover it, and the generated workflow dispatched through the skeleton's database queue and processed by `queue:work` — the third Milestone 8 exit criterion, held by a machine on every engine. The command and migration counts the walk asserts are taken from the package tree rather than written down. SQL Server's self-signed certificate is trusted through `DB_URL`, the documented way to pass a connection option the skeleton's `config/database.php` leaves commented out.

### Fixed (Phase C, before release)

- **`laraflow:install --publish-migrations` warned that the published and auto-loaded migrations run twice. They do not.** Laravel's migrator keys files by name, so the two sets collapse to one and the application's copy — read last — is the one that runs; an edit to a published copy takes effect with the package's loading still on. The warning now says that, and that disabling loading is what keeps it true if a copy is renamed, since a renamed copy runs beside the original and fails on a table that exists. Found building the install walk, which relies on exactly this; held by a test that resolves the files the way `migrate` does.

### Fixed (Phase B audit, before release)

- **The idempotency store could recurse until the worker died on MySQL, MariaDB, and SQL Server.** Those engines compare strings case-insensitively by default, so a second key differing from a recorded one only in case (or, on MariaDB, in trailing whitespace) violated the unique index, was read back with a byte-exact comparison that found nothing, and was inserted again — forever. Such a key is now refused by name (`InvalidIdempotencyKeyException::collides`), keys may not begin or end with whitespace, and the read-back is bounded.
- **On PostgreSQL a replay of a recorded key inside any transaction failed outright.** A failed statement aborts a PostgreSQL transaction, so the marker insert's unique violation left the read-back unable to run — in the test suite, and for any application calling `remember()` inside its own transaction. The insert now runs in its own savepoint.
- **Two attempts that both found a `failed` record could both run the work.** `release()` deleted whatever record was there, including the pending marker the other attempt had just written. It now removes only a `failed` record and reports whether it did; `settle()` and `fail()` likewise touch only a `pending` one.
- **A plan migration whose output was not the definition was committed, announced, and then refused.** The judge now rules before the write: a wrong migration is refused with nothing committed, so the closure can be fixed and the next claim tries again, instead of leaving a plan no code describes with an event that said otherwise.
- The store's table carries the caller's key as written, unique with its step position, rather than a scope baked into the string — so a key's length limit no longer shrinks as execution ids grow digits, and the format is known in one place. Its redundant second index is gone: the unique index leads with the execution id and serves every read.
- `PlanDraft` refuses an operation that would repeat a step class, as it already refused a plan that did; names the decided row that froze a pending one; journals its operations for the migration log; and offers `PlanDraft::of()` for a migration's own tests.

### Deprecated

- The five `WorkflowExecutionRetryScheduled::REASON_*` constants, in favour of the `RecoveryReason` cases. Each keeps its value and is `@deprecated` in its docblock; a unit test holds every constant to the value of exactly one case. Planned for removal in 0.4.0.

### Closing audit (full-project review, Milestone 0 foundations through Milestone 7)

Seven parallel hostile reviews — workflow-core concurrency, the connector and secrets layer, project-wide documentation alignment, code standards and design, test-suite quality, schema and query performance, and a branch security review — produced 190 findings. The defects among them are fixed below, each with a regression test; the documentation corrections are folded into the contracts; the design findings judged not worth the churn before 1.0 are recorded under *Deferred* in `ROADMAP.md`.

- **Fixed: a step returning a scalar crashed the checkpoint and left the execution claimed.** `Step::handle(): mixed` and `DurableValue` both allow scalars, but the repository's JSON encoder was typed `?array`; `return 'ok'` threw a `TypeError` inside the checkpoint, the failure path hit the same write, and nothing was persisted. A Milestone 1 defect no test had exercised.
- **Fixed: the reserved signal prefix was an authorization boundary that failed on three engines.** The `laraflow.` refusal was byte-wise in PHP while the waiting-step match ran in the database, which compares case-insensitively on MySQL, MariaDB, and SQL Server — so `Laraflow.child.42` passed the guard and could forge a sub-workflow's completion. `recordSignal()` now locks the row and compares the name byte for byte in PHP; the guard is case-insensitive; a late duplicate can no longer overwrite a *completed* step's output (the write is scoped to the still-waiting row under lock). Found by the security review; validated at medium severity.
- **Fixed: a checkpoint failure after the handle said "completed" masked the real error.** Every outcome path then ran into `InvalidStateTransitionException` from `Completed`, logged as a storage failure, with the execution left claimed. The handle is snapshotted and restored when the checkpoint throws, so the ordinary failure paths record the real error from a legal state.
- **Fixed: two `FailurePolicy::Continue` holes.** A step that failed terminally in an earlier claim was re-run — budget exceeded, side effects repeated — on every later resume after a retry or wait; it is now run again only when an operator re-executes the *failed* execution (`WorkflowExecution::resumedFrom`, set on claim), and otherwise decides the outcome as `StepPreviouslyFailedException`. And a failed step's in-memory context writes reached the next step and its checkpoint; the context is restored to its pre-step snapshot on failure.
- **Fixed: abandoned executions could starve recovery, and could not be cancelled.** Abandoned and unrecoverable candidates no longer consume the budget of the scans that follow, and `cancel()` treats a running execution with a stale claim as unclaimed — the claim's own test — so an abandoned execution is cancelled outright rather than left with a request no worker will honour. `requestCancellation()` gained an optional `$staleBefore` cutoff.
- **Fixed: a waiting step whose class disappeared hit an illegal transition** instead of the documented definition failure; definition faults now fail a waiting step from where it is.
- **Fixed: two retention scans cost the size of history, not the backlog.** The scrub tier walked every finished row under the cutoff (scrubbed rows included) on every run, and the prune-attempts tier probed every finished row for history. A fourth post-freeze migration adds `(payloads_scrubbed_at, status, finished_at)` so the index skips scrubbed rows, and the prune tier is driven from the attempts table's own index. `retention.md`'s cost claim is now true.
- **Fixed: a finished-window filter with no status filter was a full table scan** through the public `ExecutionFilter` — the one shape the filter design forbids. The window now carries the finished statuses in SQL, so `(status, finished_at)` serves it.
- **Fixed: a finished child's workflow class vanishing was re-delivered every heartbeat** forever (`ChildWorkflowFailedException::workflowMissing` now), a child finishing between the lookup and its delivery charged the parent with `ExecutionNotRunnableException`, a transient database error while signalling a parent failed a child that had already durably completed, a cancellation landing between the boundary check and the park sat on an unclaimable wait (`cancelIfRequested` after every park), and a heartbeat delivery failure was swallowed silently (logged now).
- **Fixed: engine and encoding hazards.** Anonymous exception class names (which carry a NUL byte and a file path) broke the failure write on PostgreSQL and overflowed `error_class` elsewhere — sanitised at the one place they are recorded; `max_error_length` counted characters while MySQL's `text` holds 65,535 bytes — capped in bytes too; signal names had no length check against a 255-character column; `Wait::until()` and `dispatchExecution()`'s caller-supplied instants were persisted without timezone normalisation; workflow input with integer or list keys was renumbered or duplicated by `array_merge` (now `array_replace`); the retention `chunk` had no upper bound against SQL Server's parameter limit (500 now).
- **Fixed in the connector layer:** `ConnectorObserver`'s frames carried the authenticated request without `#[SensitiveParameter]`; `BearerTokenAuthenticator` merged `Authorization` case-sensitively, the one layer step 5 missed; GitHub's secondary rate limit (403 with `Retry-After`) was classified as an authentication failure; Slack's server-side codes inside a 200 (`internal_error`, `fatal_error`, `service_unavailable`, `request_timeout`) were client errors; a root-relative next-page link was resolved against the base path rather than the origin, and an unparseable link was handed to the transport instead of refused; connector and connection names could contain `.` (breaking the credential path) and `:` (colliding in cache and rate-limit keys); `laraflow:connectors` printed a base URL's userinfo; the `ConnectorContract` demanded `name()` equal the registration key, which `HttpConnector` invites overriding.
- **Fixed in the console:** `laraflow:execute --queue` and `laraflow:demo` reported any dispatch failure as a sync-driver step failure; `laraflow:summary` ran its attention scans for the first `--workflow` only; `laraflow:list --limit` was clamped silently instead of validated; `--now`'s help text omitted waits.
- **Fixed in the suite itself:** `ProjectContractsTest` asserted the `Retry-After` cap backwards (`assertLessThanOrEqual` arguments swapped), passed any class whose basename appeared anywhere in the API document, and let console code reach the tables through `DB::table()` unnoticed; the retention "no cascades" test switched SQLite's foreign keys off inside a transaction, where the PRAGMA is a documented no-op (it now proves the orphan sweeps are issued); `PaginationTest` looped `Http::fake()` with one pattern, so only its first case ever ran; `SchemaFreezeTest` pinned names but not shapes (it now pins each migration file's hash); `UpgradePathTest` left rows behind on MySQL after its DDL committed the test transaction. New tests cover the sync-driver push deferral against the real database queue, `--skip-retries` withholding waits, `--dry-run` exiting non-zero on abandonment, `waiting` among retention's untouchables, a signal payload's size bound, `--now` resuming a timed wait, and the summary's per-workflow scans.
- **Changed:** `ExecutionRepository::requestCancellation()` gained `?DateTimeImmutable $staleBefore`; `WorkflowExecution` gained the unpersisted `resumedFrom`; `ChildWorkflows` and `TransportPipeline` are documented Public (contract) because every subclass constructor must forward them; `InvalidSignalException` replaces the SPL exception for bad signal names; `RetentionPolicy::MAX_CHUNK` is 500; `Wait::CHILD_PREFIX`, `isChildSignal()`, and `childIdFrom()` name the child-signal convention once.

### Phase B audit (full review of the milestone's capability work)

Three parallel hostile reviews over steps 6–9 — concurrency, code quality, and contract alignment — produced 48 findings; the defects among them are fixed below, each with a regression test, and the rest were documentation corrections folded into the contracts.

- **Fixed: healthy heartbeats counted toward abandonment.** Every claim of a parent waiting on a slow child bumped `fruitless_claims`, and nothing on the re-park path reset it — so after three heartbeats, one worker crash left the parent flagged abandoned and recovery refusing it forever. An orderly `release()` (a park, a scheduled retry, a terminal transition) now zeroes the counter; only a claim that dies before any orderly write counts.
- **Fixed: a stale child-failure payload could be charged twice.** The payload a failed child signalled onto the parent step's `output` survived the parent's retry re-park and short-circuited the next heartbeat as if it were the child's current outcome. `markWaiting()` now clears the output, and a child whose failure *predates* the current parent attempt is re-delivered and waited on rather than re-charged.
- **Fixed: a durable skip could be recorded against a context that was not final.** Under `FailurePolicy::Continue`, a conditional step after a failed step judged a context missing that step's contribution; the skip then replayed forever. A false answer while an earlier step has failed is no longer persisted — the condition votes again on re-execution, against the full context.
- **Fixed: after a throwing condition, re-execution ran the step unconditionally.** The condition is now consulted at the start of every attempt (pending, failed, or retrying), so a condition that threw once — and never answered — gets its real vote instead of being presumed true.
- **Fixed: a cancellation requested mid-step could park indefinitely.** The park is a step boundary and now honours a pending cancellation request instead of entering a wait nothing may ever resume; and a cancellation honoured cooperatively now cascades to children, catching a child created after `cancel()`'s own cascade swept past.
- **Fixed: benign deliveries to parked executions failed jobs and recovery runs.** `ExecutionStillWaitingException` is now absorbed as information by `ExecuteWorkflowJob` and `laraflow:recover`, like the not-due and already-claimed races before it; the cancel cascade likewise survives a child finishing concurrently.
- **Fixed: the parent heartbeat bypassed recovery's abandonment bound.** It re-delivered any unfinished child — including a stale, crash-looping one recovery had refused. It now delivers only a `pending` child (a lost dispatch) or a pre-attempt failure being resumed; running, retrying, and waiting children are left to their own machinery and its bounds.
- **Fixed: a duplicate signal was falsely refused on MySQL/MariaDB.** `recordSignal()` decided "is anything parked on this name" from the payload UPDATE's affected-row count, which is zero for an identical rewrite on engines that count rows *changed*. The check is now a read; a duplicate before the resume overwrites the payload — last delivery wins.
- **Fixed smaller defects:** `ExecutionFilter->withStatus()`/`withOldestFirst()`/`isEmpty()` dropped or ignored the new `parentId` (and `parentId` moved to the end of the constructor, un-breaking positional callers); `ExecutionOptions::isEmpty()` ignored `parentStepExecutionId`; the sub-workflow child lookup read only the newest 500 children; the depth walk crashed on a retention-pruned ancestor instead of treating it as the root; `laraflow:summary` omitted `waiting` from the oldest-unfinished scan and never surfaced due waits in its health check (`waitingDue()` gained tenant scoping for it); `laraflow:show` described a child wait as an indefinite wait on a leaked internal signal name; and `laraflow:recover --skip-retries` now says it also withholds due waits.

### Added

- **Schema: index `(payloads_scrubbed_at, status, finished_at)` on `laraflow_workflow_executions`** (fourth post-freeze migration, `2026_10_28_000003`), serving the scrub tier's scan so its cost is the backlog rather than the size of history. Additive and reversible; an index build is not online on PostgreSQL or SQL Server — see `docs/upgrading.md`.
- **Sub-workflows.** A step extending `SubWorkflowStep` runs another workflow as a child execution: created once and linked by two new columns (`parent_execution_id`, indexed, and `parent_step_execution_id` — plain columns, not foreign keys, so retention may prune a long-finished parent while the child's audit record lives on), inheriting the parent's correlation and tenant identifiers, delivered through the new `ChildDelivery` seam (default: Laraflow's queue dispatcher; the sync driver runs the child in-process), and waited on via the reserved `laraflow.child.{id}` signal. The child's resting outcome — identity and status, never its context — becomes the parent step's output, or fails it with `ChildWorkflowFailedException` under the step's retry policy; **a retry resumes the same child from its own checkpoints** rather than spawning a sibling. The parent's park heartbeats on `stale_after` and consults the child's record directly when claimed, so a signal lost to the park race, a lost child dispatch, or a pruned child (`ChildWorkflowFailedException::missing`) all heal or surface rather than hang. Cancelling a parent cascades to unfinished children, visibly and recursively; a cancelled child fails the parent step. Nesting is bounded by `laraflow.workflows.max_depth` (default 8), refused at creation with `WorkflowDepthExceededException`. `ExecutionFilter` gains `parentId`, `ExecutionOptions` the linkage ids (**breaking** for custom repositories), and `laraflow:show` names a child's parent. Contract: `docs/advanced-workflows.md`.
- **Delays, wait states, and signals.** A step may return a `Wait` from `handle()` instead of an output: `Wait::until()` / `Wait::untilSeconds()` parks the execution until an instant; `Wait::forSignal()` parks it until the application delivers a named signal (`WorkflowRunner::signal()`), with an optional `timeoutAfterSeconds()` deadline that fails the step with `WaitTimedOutException` under its own retry policy — retrying re-runs the step and re-posts its request. A wait is the step's outcome boundary: everything before it checkpoints with the park, the claim is released, and resuming completes the step with the signal payload (or null) as output, the payload also landing in the context under the signal's name. Recording a signal is not delivery: the queue fast path (delayed dispatch for known instants) and `laraflow:recover` (a new due-waiting candidate kind, `wait_due`, exempt from the abandonment bound like due retries) deliver, and an unbounded signal wait is claimable only by its signal. New statuses `waiting` on steps and executions (**breaking** for exhaustive matches), events `WorkflowStepWaiting` and `WorkflowExecutionSignalled`, exceptions `WaitTimedOutException`, `SignalRefusedException`, `ExecutionStillWaitingException`, and repository surface `recordSignal()` / `waitingDue()` (**breaking** for custom implementations). Schema: one additive migration, `laraflow_step_executions.wait_signal`; a timed wait's resume instant and a bounded wait's deadline reuse `next_retry_at` and `timeout_at`. Cancelling a waiting execution is immediate. Contract: `docs/advanced-workflows.md`.
- **Conditional steps.** A step may implement `ConditionalStep` (`shouldRun(WorkflowContext): bool`), consulted at the step's turn — after the cancellation check, before the step is marked running. A false answer durably marks the step `skipped` in a claim-guarded write: no attempt is counted, no history row is written, no output is recorded, and the context is untouched, with `completed_at` holding the instant the decision was recorded. Recovery replays the recorded decision rather than re-evaluating; conditions must be pure functions of the context (`docs/advanced-workflows.md`). A throwing condition fails the step like a step class that cannot be built. New `WorkflowStepSkipped` lifecycle event; `StepStatus` gains `Skipped` (**breaking** for exhaustive matches); `stepProgress()` gains a `skipped` count (**breaking** for strict shape readers), and `laraflow:list` counts completed-plus-skipped as done.
- **Schema: `laraflow_workflow_executions.fruitless_claims`**, the first migration since the freeze (`2026_10_28_000000_add_fruitless_claims_to_laraflow_workflow_executions`). Additive — one unsigned integer column, default `0`, no index — and safe to run while workers hold claims: old code never touches the column, and rows that predate it read as having made no fruitless claims. `php artisan migrate` applies it; `migrate:rollback --step=1` drops it and nothing else. It counts consecutive claims on an execution that ended before any step row was written: `claim()` increments it, and the first step write under the claim zeroes it inside the same guarded `UPDATE` that verifies the claim, so the ordinary path pays no extra query.
- **Recovery abandons a fault in the claim-to-first-step window.** `laraflow:recover` now holds `fruitless_claims` to the same bound as step attempts (`recovery.abandon_after_attempts`, default 3). A worker that fails after claiming but before its first step write — a listener throwing on `WorkflowExecutionStarted`, a workflow whose steps no longer match the persisted plan — never moves the step attempt counter, so such an execution was previously re-dispatched by every recovery run forever, each run occupying a claim for `stale_after`. It is now reported as `abandoned (was claimed N times without reaching a step)` and left for an operator, closing the second claim-discipline limit recorded at the Milestone 6 audit. The attempt-bound report line reads `abandoned (reached N step attempts)`; `laraflow:show` displays the count when an execution has been claimed more than once without progress. `WorkflowExecution` exposes it as `fruitlessClaims`; `RecoveryCandidate` carries it and names the measure that tripped in `abandonedBecause()`.

### Changed

- **Header names merge case-insensitively at every layer.** A connection configuring `accept` under a connector class declaring `Accept` previously sent both headers; so did a request's own `content-type` against an option's `Content-Type`. All four merge points — class headers under connection headers, the pinned API-version header, request headers over option headers in the transport, and `ConnectorRequest::withHeaders()` — now go through one rule (`Integration\Http\Headers::merge()`): names match case-insensitively, the overriding layer wins the value and the spelling, per RFC 9110 §5.1. Closes a known limit recorded at the Milestone 6 audit.
- **`ConnectorRequestSent.successful` is the connector's verdict, not the HTTP status's.** The connector's error mapper now runs inside the transport pipeline (a `MappingTransport` between the retry and observing layers) instead of after it, so the event announces a provider that rejected the call inside a `200` body — Slack's `ok: false` — as `successful: false`, agreeing with the response the caller gets. `TransportPipeline::through()` gains a trailing optional mapping closure; the mapper still sees the request as the caller made it, never the authenticated one. Closes a known limit recorded at the Milestone 6 audit.
- **`WorkflowExecutionDispatched` fires after the commit its push waits for.** With `laraflow.queue.after_commit` on (the default) and `dispatch()` called inside an application transaction, the event was emitted when `dispatch()` returned — before the commit the job push was correctly deferred to — so a listener reading the database could find nothing, and a rolled-back transaction had announced an execution that never existed. The dispatcher now registers the event with the same transaction manager the queue uses, after the push's own callback: on commit it fires once the job is on the queue, on rollback it never fires, and outside a transaction (or with `after_commit` off) it fires at once as before. `WorkflowDispatcher`'s constructor gains a trailing optional `DatabaseTransactionsManager`. Closes the last of the Milestone 6 audit's event-ordering limits; every lifecycle event now fires after its durable write.
- **Breaking:** `ExecutionRepository::saveStep()` now takes the claimed `WorkflowExecution` as its first argument and verifies the claim in the same transaction as the step and attempt-history writes, throwing `ClaimLostException` on loss exactly as `checkpoint()` and `release()` do. Custom implementations must adopt the new signature and the guarantee; callers other than the runner should not exist. Closes the first of the two claim-discipline limits recorded at the Milestone 6 audit: a worker stalled past `stale_after` whose execution was reclaimed could previously mark a step the new owner was running as `running` or `failed`, or append a stale attempt row, before its first checkpoint or release stopped it. Every step-row write by a dead worker now rolls back untouched.
- A `ClaimLostException` raised while recording a step's outcome is no longer logged as a storage failure with the step's exception rethrown over it; it propagates as itself, so a reclaimed worker exits through the same quiet path it already took when a checkpoint found the claim gone.

### Milestone 6 — compatibility, quality, and release readiness

#### Closing audit (full-project review)

- **Fixed: a retry's claim release could durably erase a concurrent cancellation request.** `release()` wrote the worker's in-memory cancellation columns — hydrated at claim time, so null — over whatever an operator's `cancel()` had written since, and the retry then ran against a request the contract says nothing clears. The cancellation columns are now written only when the worker's own handle carries them, with a regression test staging the exact race (request mid-step, step fails, retry scheduled).
- **Fixed: a blank environment value could grant the queue unlimited retries.** `(int) ''` is 0, and `$tries = 0` is Laravel for *unlimited*; the same blind cast made a blank `stale_after` treat every live execution as stale and a blank `pending_after` switch the pending scan on at zero seconds — the one value its own validator refuses. All queue and recovery settings now follow the blank-means-unset rule the provider already applied elsewhere.
- **Fixed: the attempts prune now re-checks eligibility inside the DELETE.** A worker could reclaim an execution between retention's eligibility read and its delete (invisibly, under REPEATABLE READ), losing a running execution's attempt history; the delete now carries the status/finished-at guard in the same statement, as `RetentionService`'s documentation already claimed.
- **Fixed: the pagination host guard now checks scheme and port.** A next-page link downgraded to `http`, or re-pointed at another port on the same hostname, was followed with the `Authorization` header attached.
- **Fixed: all four RFC 9110 `Retry-After` date forms parse, and a lying weekday no longer shifts the date.** The obsolete RFC 850 and asctime forms were silently dropped (losing the provider's requested wait), and PHP's parser turns a weekday that disagrees with the date into a *different date*; the weekday is now stripped before parsing.
- Documented rather than changed, each recorded as a known limit where its contract lives and queued for hardening in `ROADMAP.md`: step-row writes are last-writer-wins for a stale worker until its first checkpoint fails; a deterministic fault between claim and first step write recurs unbounded in recovery; `WorkflowExecutionDispatched` may fire before its durable write commits; `ConnectorRequestSent.successful` reflects HTTP status alone, not a rejected `200`; header merges are case-sensitive; `throw()` raises for an unmapped `304`; paginators replace a URI-embedded query string; Laravel's `failed_jobs` receives the one unredacted exception sink.

Any installation not running UTC retried hours early or late. The existing coverage passed only because the suite runs in UTC; the regression test now pins a non-UTC default timezone.
- **A next-page link was followed unchecked when a connector declared no base URL.** The same-host guard compared against the connection's host and returned early when there was none — so a connector built on absolute URIs would follow an absolute `Link` to any host with its `Authorization` header attached, which is exactly what the guard exists to prevent. This is the last in-place schema edit; the freeze follows.

- **The installation path is a CI check.** An install job creates a fresh `laravel/laravel` application — Laravel 12 on PHP 8.2 and Laravel 13 on PHP 8.4, the oldest and newest supported pairings — requires the package from a path repository, and asserts the documented first-run story step by step: auto-discovery registers the provider, `laraflow-config` and `laraflow-migrations` publish, the migrations run, `laraflow:demo` leaves a persisted completed execution that `laraflow:show` and `laraflow:list` can read, `laraflow:demo --fail` leaves a failed one that `laraflow:execute` recovers from its checkpoint, `laraflow:connectors --check` passes, and `migrate:rollback` removes the three tables. The Milestone 0 exit criterion — zero to a persisted execution by documented steps — is now held by a machine rather than by the README's good intentions.

- **Every database engine on the compatibility table is now tested, not "expected to work".** A CI matrix runs all 864 tests against MySQL 8.0, MariaDB 10.6, PostgreSQL 13, and SQL Server 2019 service containers through the `LARAFLOW_TEST_DB_*` seam. Getting each engine green surfaced and fixed real defects, several in shipped code rather than tests:

  - **Affected rows are not matched rows on MySQL and MariaDB.** Every compare-and-set guard — the claim, the checkpoint, `recordDispatch`, cancellation, release, the retention scrub — read "0 rows" as "lost the claim / no such row", but those engines count rows *changed*: a duplicate dispatch in the same second or a checkpoint whose context did not move reported zero and threw. The executions table gains a `version` column bumped by every repository write (`counted()`), making the two counts the same thing on every engine. Not optimistic locking; nothing reads the number.
  - **SQL Server's grammar does not JSON-encode array values in query-builder updates** (the others do), so the checkpoint's context array was flattened into bindings element by element and the write missed. The repository now encodes JSON columns explicitly at its boundary (`asJson()`), byte-identical on every engine.
  - **SQL Server refuses a second cascade path**, so `laraflow_step_attempts.workflow_execution_id` does not cascade there; deletion flows through the step row, which covers every attempt. Other engines are unchanged.
  - **pdo_sqlsrv returns every column as a string**; the models' foreign keys gain integer casts so handles expose the same types everywhere.
  - **Id generators do not rewind on rollback** anywhere but SQLite, so the base test case resets each table's auto-increment before every test's transaction — and SQL Server's `RESEED, 0` means "next is 0" on a table that never held rows, so the reseed is conditional on the identity having moved.
  - **DDL inside the test transaction** (queue-table creation, the migrate-rollback tests) implicitly commits on MySQL/MariaDB and destroyed savepoint isolation; schema work now happens before the transaction begins, and the rollback tests re-migrate themselves.

- **CI proves the dependency axis, not just the PHP one.** The workflow splits into a quality job — `composer validate --strict`, `composer audit` against the committed lock, Pint, PHPStan — and a test matrix of PHP 8.2/8.3/8.4 per supported Laravel major, pinned through Testbench so Laravel 13 becomes one matrix line. A `prefer-lowest` cell on PHP 8.2 resolves every constraint to its true floor (Testbench 10.0.0, Laravel 12.4.1, PHPUnit 11.5.3) and must pass the suite *and* static analysis there. Every leg was run locally before being committed; the floor surfaced two stub-drift defects — `ConnectorContract` now asserts `isNotEmpty()` rather than `assertNotEmpty()` on a collection, and a queue test reads the job row through `get_object_vars()` — fixed for both extremes rather than suppressed on one.

- **The test database driver is selectable.** `Laraflow\Tests\TestCase` builds the suite's connection from `LARAFLOW_TEST_DB_*` environment variables — driver, host, port, database, username, password — defaulting to the in-memory SQLite the suite has always used. Any driver the installed Laravel resolves is accepted; `mysql`, `mariadb`, `pgsql`, and `sqlsrv` get per-driver defaults (port, charset, strict mode, `search_path`). This is the seam the CI engine matrix runs through. SQL Server 2019+ joins `docs/compatibility.md` as *expected to work*; the same document now states explicitly that MongoDB is not a supported persistence backend and why, with a document-store driver recorded as Milestone 7 scope. A test that can only be staged on one engine skips elsewhere with a reason — the retention orphan test needs SQLite's `PRAGMA foreign_keys = OFF`, which no other engine lets a session do.

- **Static analysis covers the tests and the playground.** `composer analyse` runs PHPStan level 8 over `tests/` and `workbench/` as well as `src/` and `database/` — 260 files rather than 145. The 367 findings this surfaced are fixed rather than recorded: there is no baseline file, so a type error in a new test fails CI the same way one in the package does.

  Two thirds of them were a single upstream declaration. Testbench types `$app` as `Application|null` because it is null before the application is created; `Laraflow\Tests\TestCase` narrows it, which is true by the time any test method runs and avoids putting a null check in front of several hundred ordinary container calls. Most of the rest were nullable Eloquent lookups read straight through — `steps[0]->status` — which die with a PHP error about null instead of naming the missing row; the base test case grew `stepAt()`, `row()`, and `command()`, which assert first. That is 39 assertions the suite was not previously making.

  Six lines keep a `@phpstan-ignore`, each naming one identifier and carrying a comment: tests that deliberately pass a value the declared type forbids, to prove the runtime rejects it. `CONTRIBUTING.md` states that as the only accepted use.

- **Breaking:** `TransportException::$attempts` is no longer a public property; read it with `attempts()`. It stays settable only through `afterAttempts()`, which the retrying transport calls. (In-place rather than returning a copy: PHP exceptions cannot be cloned, and rebuilding one would move the throw site and lose the stack trace.)
- **Breaking:** a page budget below one is now `PaginationException` rather than `InvalidArgumentException`, consistent with every other pagination refusal. `pages()` is also no longer a generator itself, so that refusal — and a connector with no paginator — is raised when `pages()` is called rather than when a caller first begins iterating.
- A connection may set `rate_limit: false` to lift a ceiling configured under `laraflow.http.rate_limit`. Previously an inherited ceiling could be raised but never removed, so an account with its own quota was held to the fleet's. `RateLimitPolicy::fromArray()` accepts `false` alongside an array and `null`.
- `ConnectorContract` now asserts up front that it can actually intercept the connector under test. It works by stubbing Laravel's HTTP client, so a connector with a transport of its own was never reached by the fake and every assertion that followed passed without testing anything — or reached the real network. `assertHeldBy()` sends one probe first and fails with what to do instead.
- The bundled-connector internals check reads inline `\Laraflow\…` references as well as `use` statements; an internal class was reachable by writing it out in full.

#### Documentation

- `docs/connectors.md` attributed the "no Laraflow object in a connector's graph holds a credential" invariant to `ProjectContractsTest`; it is held by `SecretExposureTest`.
- The client-side rate limit is documented as **best effort**: its check and its count are not one atomic cache operation and workers waiting out a window wake together, so enough concurrency can run a window slightly over. The provider's own `429` and the durable retry behind it remain the backstop. Stated in `docs/connectors.md`, `config/laraflow.php`, and on `ThrottlingTransport`.
- `ConnectorContract`'s credential search is documented as stopping at the Laraflow namespace, and why, so what it does not catch is stated rather than implied.
- `CONTRIBUTING.md` records the analysis scope, the no-baseline rule, the single accepted use of `@phpstan-ignore`, and the test-case helpers.

#### Playground

- `playground:watch` gains `--frames=N`, stopping after N frames; `0` keeps the existing behaviour of drawing until interrupted. The watch loop needed a condition that was actually a condition, and a bounded one is what lets a script capture a fixed number of frames without `--once`'s single-frame layout.
- The three playground commands share a `ReadsInput` trait (`stringArgument()`, `stringOption()`) instead of casting console input — typed `array|bool|float|int|string|null` — straight to string.

### Milestone 5 — integration framework hardening

Contract in `docs/connectors.md`; the retry interplay in `docs/retry-and-failure-policy.md`; provider API expectations in `docs/compatibility.md`.

#### Added

- **Named connections.** A connector is registered once and resolved per connection: `connector('github')` for the configured default, `connector('github', 'enterprise')` for another account served by the same class. Connections are configured under `laraflow.integrations.{connector}.connections.{name}`; `laraflow.integrations.{connector}.default` names the one used when a caller names none. `LaraflowManager` gains `connectors()`, `connections(name)`, and `forget(?name, ?connection)`.
- **Configuration-driven registration.** A class declared as `laraflow.integrations.{connector}.connector` is registered at boot and built through the container with its `Laraflow\Integration\Connection` (public) passed as `$connection`, so a connector declares its other dependencies as ordinary constructor parameters. The bundled GitHub connector is registered this way — one `integrations` entry among any the application adds, with no privileged path. Closures still work and now receive the `Connection`. A misnamed class fails at boot with `InvalidConnectorException`.
- **A strict configuration shape.** A connector section holds `connector`, `default`, and `connections`, nothing else. A setting left at the connector level — the Milestone 0 `integrations.github.token` — is refused with `ConnectorConfigurationException` (public) naming the path it belongs at, rather than being silently read by nothing. An unknown connection raises `ConnectionNotConfiguredException` (public) naming the configured ones. `Connection::require()` treats a blank value as missing and names the configuration path and, when given, the environment variable.
- **Credentials resolved per request** through the `CredentialProvider` contract (public), bound by interface so an application can read a vault or a per-tenant store. The default reads `…connections.{name}.credentials` from the config repository on every call. Rotation therefore needs no rebuild and no restart: the next request uses the new value. The `credentials` key is stripped from the `Connection` a connector holds, so the object a connector keeps for its lifetime carries settings only.
- **`Laraflow\Support\Secret`** (public): a credential that renders as `[redacted]` in string context, `json_encode`, `print_r`, `var_dump`, `var_export`, the array cast, and `serialize`, and yields its value only to `reveal()`. The value is held in a `WeakMap` rather than a property because `var_export` and the array cast read properties directly and ignore `__debugInfo`. An unserialized `Secret` has no value — a credential that rode through a queue payload or a cache would otherwise sit there in clear text — and `reveal()` on it throws `SecretRedactedException` (public). `Credentials` (public) is the bag of them for one connection.
- **`Laraflow\Integration\HttpConnector`** (public): the base class for connectors that speak HTTP. A subclass declares its provider — `baseUrl()`, optionally `headers()` and `authenticator()` — and inherits `request()`: resolve this request's credentials, authenticate, send. The constructor is satisfied by the container when the registry builds the connector. `GithubConnector` is now twenty lines on it.
- **A transport seam.** `HttpTransport` (public contract) puts the authenticated request on the wire; `LaravelHttpTransport` (internal, the default binding) does so through Laravel's HTTP client, so `Http::fake()` and the client's middleware keep working. Bind another implementation to replace the wire for every connector, or override `transport()` on one. The transport merges connection headers under request headers itself, because the client's own merge is recursive and turns two values for one header into a list. Its `$request` parameter is `#[\SensitiveParameter]`: the authenticated options are in it.
- **Configurable HTTP behaviour**, resolved connector class → connection → `laraflow.http` defaults: `HttpOptions` (public) carries `baseUrl`, `timeoutSeconds`, `connectTimeoutSeconds`, and default `headers`. A connection sets `base_url`, `timeout`, `connect_timeout`, `headers` to point the same class at a sandbox host or give one account a longer wait. New config section `laraflow.http` with `timeout` (30) and `connect_timeout` (10). Timeouts must be positive and the base URL a URL, checked at construction and reported with the connection's path.
- **Responses keep the body as received.** `ConnectorResponse` is built from the raw body and decodes explicitly and lazily: `json()` decodes whatever the server declared and refuses malformed JSON with `ResponseDecodingException` (public; names status and content type, never the body), `body()` gives the decoded value when the server declared JSON and the raw string otherwise, `raw()` the bytes, `header()` a case-insensitive lookup. An HTML maintenance page and a JSON `null` were both `null` before and could not be told apart. `ConnectorResponse::fake()` builds one for tests and replacement transports; `toArray()` is a durable form for step output.
- **Typed errors, mapped per provider.** `ErrorMapper` (public contract) decides whether a response is an error and which kind; `StatusErrorMapper` (public, the default) goes by status — 401/403 `AuthenticationFailedException`, 404 `NotFoundException`, 429 `RateLimitedException`, other 4xx `ClientErrorException`, 5xx `ServerErrorException`, all under `Laraflow\Exceptions\Connector` and extending `RequestFailedException`, which carries the response. A connector supplies its own via `errorMapper()`: the bundled `GithubErrorMapper` reads a 403 with `X-RateLimit-Remaining: 0` as rate limiting, which by status alone would be an authentication failure and so never retried. `RateLimitedException::retryAfterSeconds(now)` reads delay-seconds or an HTTP-date against the caller's clock.
- **Errors are returned, not thrown.** `request()` attaches the mapped exception to the response: `failed()` is then true even for a `200` the mapper rejected, `error()` returns it, `throw()` raises it (or a generic `RequestFailedException` for an unmapped error status). A connection sets `throw_on_error` to make `request()` throw instead. The default preserves the Milestone 0 contract that an error status is a result to inspect.
- **A safe-reporting chokepoint.** `RequestFailedException::fromResponse()` is the one place a provider error becomes a message, and it is given the request *as the caller made it*, before authentication — so nothing an authenticator added can reach a message — and names the path alone, because a query string may carry a token. The provider's detail is taken from the usual JSON fields and truncated.
- **In-attempt transport retries, off by default.** `TransportPolicy` (public; `laraflow.http.retries`, overridable per connection) repeats one wire request inside a single step attempt — for a dropped connection or a momentary 503 — with millisecond backoff and deterministic jitter. It is the *inner* loop to the step policy's durable *outer* one, and three rules keep them from multiplying: it ships with `max_attempts` = 1; it never waits in-process for a `Retry-After` longer than `max_retry_after` (5 s) but returns the response so the step can fail and retry durably on the provider's schedule; and a non-idempotent request is repeated only on 429 — never processed — or when the caller marked it `asIdempotent()`. `ConnectorRequest` gains the `idempotent` flag and `isIdempotent()`; `ConnectorResponse` gains `attempts()` and `retryAfterSeconds(now)`. Applied by `RetryingTransport` (internal), assembled by `TransportPipeline` (internal) only when enabled, waiting through a `Sleeper` (internal) so tests record the waits instead of serving them. Specified in `docs/retry-and-failure-policy.md`.
- **A provider's `Retry-After` drives the durable retry.** `Laraflow\Exceptions\SuggestsRetryDelay` (public contract): an exception that knows when another attempt could succeed. When a step fails with one and its policy allows a retry, `OutcomeRecorder` schedules the retry no sooner than the suggestion — up to the new `laraflow.retry.max_suggested_delay` (3600 s) — and never sooner than the policy's own backoff. `RateLimitedException` implements it with the provider's `Retry-After`, so a 429 that says "wait 600 seconds" becomes a `retrying` execution due in 600 seconds, with the worker released. Any application exception may implement it. This is a deliberate extension of the Milestone 3 retry contract, recorded in `docs/retry-and-failure-policy.md`.
- **Client-side rate limiting, off by default.** `RateLimitPolicy` (public; `laraflow.http.rate_limit`, or a connection's `rate_limit` with `max`, `per`, `max_wait`) is a ceiling Laraflow holds itself to per connection, counted through Laravel's cache-backed `RateLimiter` so every worker shares the budget and keyed per connection so one tenant's account never throttles another's. A wait up to `max_wait` seconds is served in-process; a longer one fails the request *before it reaches the provider* with `ThrottledException` (public), which suggests the wait — so with a step policy the execution comes back when a slot is due. Applied by `ThrottlingTransport` (internal), inside the retry decorator so a retried attempt is counted like any other. Dependency: `illuminate/cache`, already present transitively and now declared.
- **Lazy, bounded pagination.** `HttpConnector::pages()` yields responses and `::items()` yields the items across them, both generators — a long result set never exists in memory at once, and a caller that stops early fetches nothing more. The `Paginator` contract (public) is supplied per connector by `paginator()`; three shapes ship: `LinkHeaderPaginator` (RFC 8288, GitHub's shape, now used by the bundled connector), `CursorPaginator` (Slack's shape), and `PagePaginator`. Four things are refused rather than tolerated, all as `PaginationException` (public): reaching the page budget (`laraflow.http.pagination.max_pages`, 100, overridable per connection and per call) is **an error, not a quiet stop**, because a short list that looks complete is the worst thing a paginator can hand back; a provider that repeats a page is caught rather than looped until the budget; a connector with no paginator says so; and a next-page link to a host the connection never named is refused, because the transport sends an absolute URL as given and the request carries an `Authorization` header. A failed page throws rather than ending the iteration quietly. `docs/retry-and-failure-policy.md` and the README state that pages must not be accumulated into step output, which `max_payload_bytes` would reject.
- **Connector events and log context.** `ConnectorRequestSent` (every response the provider gave; `successful` is false for an error status *or* a 200 the mapper rejected) and `ConnectorRequestFailed` (no response at all — a connection failure, or Laraflow's own throttle refusing to send) carry connector, connection, method, **path without the query string**, status, `durationMs` for the whole call including transport retries and throttle waits, and `attempts`. No headers, options, or bodies; the failure message passes the configured `ErrorRedactor` and honours `events.include_error_messages`. They carry no correlation id by design — a connector may be called outside any workflow, and inside one the log context already has it. While a request is in flight, `laraflow.connector` and `laraflow.connection` join Laravel's log context, restored afterwards including on failure. Applied by `ObservingTransport` as the outermost pipeline layer, so one logical call is one event measuring what the caller actually waited.
- **`laraflow:connectors {connector?} {--check}`** (experimental): every registered connector, its connections, base URL, timeout, retry and rate-limit settings, and the **names** of the credentials each connection resolves — never their values, because the point is to tell an operator a credential is present without putting it on a shared terminal. `--check` resolves every connector, reports what will not build, and exits non-zero so it can gate a deploy; it sends no requests. Without `--check`, one broken connection does not stop the listing.
- `LaraflowManager::connection()` and `HttpConnector::options()` expose a connection's resolved settings (never its credentials), which is what the command reads.
- **A second real connector: Slack** (`SlackConnector`, `SlackErrorMapper`, both experimental), added only after the generic contracts were tested and chosen because it behaves nothing like the first. It exercises what GitHub does not: a provider that reports failure inside a `200` (`{"ok": false, "error": "channel_not_found"}`), cursor pagination whose result key differs per endpoint, and methods that are mostly non-idempotent POSTs. Its error codes map onto the **shared** exception types, so an application catches `AuthenticationFailedException` without knowing which provider raised it. `read()`, `write()`, and `listing()` build its requests and paginators.
- **The exit criterion is now a test.** `ProjectContractsTest` reads every bundled connector's imports and fails if one depends on a class marked `@internal`: if Laraflow's own connectors needed something a third-party package cannot reach, the extension points would not be finished. Both bundled connectors pass on the public contracts alone.
- `HttpConnector::pages()` and `::items()` take an optional `Paginator`, overriding the connector's own for providers whose result shape differs per endpoint.
- **A published contract test** (`Laraflow\Testing\ConnectorContract`, public): the assertions a connector should satisfy, shipped so connectors Laraflow does not ship can be held to the same standard as the ones it does. It checks that a connector holds no credential, classifies every error status into the shared exception types, returns errors rather than throwing them, and keeps both the credential and the query string out of every message. A plain object rather than a base test case or a trait — it collides with nothing in the host test and works from PHPUnit, Pest, or Testbench. It fakes HTTP with stray requests prevented, so it needs no credential and no network. Both bundled connectors are tested through it, and two deliberately broken fixtures prove it fails when it should.
- **A connector contribution recipe** in `CONTRIBUTING.md`: six steps, none of which involves editing a Laraflow file — and if a contributor finds themselves wanting to, that is recorded as a bug in the extension points rather than a normal step.
- **Provider API versions.** A connector declares the version it was written against (`apiVersion()`) and the header it travels in (`apiVersionHeader()`); a connection pins another with `api_version`. The GitHub connector pins REST `2022-11-28` as `X-GitHub-Api-Version`; Slack declares none, because its API has no versions, and `laraflow:connectors` shows it as *unversioned* rather than blank. `docs/compatibility.md` gains a *Provider APIs* section stating what a pinned version promises — handling the shapes the provider documented for it, proven against fakes — and what it cannot: that the provider still sends them.
- **The playground gains connectors.** `laraflow:connectors` joins the walkthrough, and the workbench-only `playground:call {connector} {uri}` sends one real request through a connector and shows what the framework did with it — the mapped error type, the wire attempts, the duration, and the events announced. It lives in `workbench/` because a command that fires an arbitrary request at a production API has no business being installable into an application.
- **The closing audit** extends `tests/Feature/ProjectContractsTest.php` with the milestone's invariants: every connector authority ships off (transport retries, rate limit) and every bundled connector ships without a credential; every connector exception an application can catch is in `public-api.md`; every `HttpTransport::send()` marks its request `#[\SensitiveParameter]`; no connector event carries a parameter that could hold request or response content.
- `TransportException::connecting(host, previous)`: the message names the host alone — not the URL, whose query string may carry a token, and not the options.
- **`BearerTokenAuthenticator`** (public) replaces `GithubTokenAuthenticator`: `Authorization: Bearer` from a named credential, reading it from the `Credentials` passed to every call.
- `tests/Feature/Integration/SecretExposureTest.php`: the milestone's secrecy exit criterion as a sweep. Every value object is rendered every way PHP offers, every property of every Laraflow object reachable from the connector and the manager is walked, and every Laraflow stack frame of every exception the layer raises is checked — none may contain the token.

#### Decisions

- **Errors are returned, not thrown.** An error status stays a result to inspect; the response carries the mapped exception, `throw()` raises it, and `throw_on_error` opts a connection into throwing. The Milestone 0 contract that `failed()` is a normal outcome is preserved.
- **Credentials are resolved per request, never captured at construction.** This is what makes rotation a configuration change and lets a cached connector carry nothing worth stealing.
- **`Secret` keeps its value in a `WeakMap`, not a property.** `var_export` and the array cast ignore `__debugInfo`; a property would leak through them. The cost — a `Secret` cannot be cloned — is stated.
- **A provider's `Retry-After` drives the durable retry, capped.** `SuggestsRetryDelay` extends the Milestone 3 contract deliberately: believed up to `retry.max_suggested_delay`, never below the policy's own backoff. Sleeping a worker for the provider's wait is what durable retries exist to avoid.
- **Transport retries are the inner loop and ship off.** Milliseconds, never waiting for a `Retry-After` beyond `max_retry_after`, never repeating a non-idempotent request except on 429 or when marked safe. Two retry systems again, kept from multiplying by construction.
- **A page budget is an error, not a quiet stop.** A short list that looks complete is the worst thing a paginator can produce.
- **A next-page link to a foreign host is refused.** The transport sends absolute URLs as given and the request carries credentials.
- **Connector events carry no correlation id.** A connector may run outside any workflow; inside one, the log context already has the identifiers.
- **The contract test is a plain object using PHPUnit's static `Assert`.** A trait in `src` used only from `tests` is invisible to static analysis of `src`, and analysing `tests` surfaced 344 findings that belong to Milestone 6.
- **Slack is the second connector** because it behaves nothing like GitHub. Both are held to the same published contract, and a test fails if either depends on anything internal.

#### Changed

- **Fixed, found reviewing the milestone:** a transport failure on a connector with no base URL named the full request URI — query string included — instead of the host; Guzzle's own transfer failures (too many redirects, a malformed response) surfaced untyped with the URL in their message, and are now `TransportException` too; a `ConnectorRequestFailed` event after exhausted transport retries reported one attempt, and `TransportException` now carries `attempts`; the `Link` header parser split on commas, which a URL may legitimately contain (`?ids=1,2`); Slack's mapper threw `ResponseDecodingException` on a malformed `200` body rather than deciding — a mapper decides, `body()` reports; `pages()` accepted a page budget of zero and returned one page as "the limit". Each is pinned in `tests/Feature/Integration/ReviewFindingsTest.php`.
- **Breaking:** `laraflow.integrations.github.token` moved to `laraflow.integrations.github.connections.default.credentials.token`. The old key is refused with the new path.
- **Breaking:** `Authenticator::authenticate()` gained a `Credentials` parameter; authenticators receive credentials rather than holding them. `GithubTokenAuthenticator` is removed.
- **Breaking:** `ConnectorResponse` is constructed from the raw body (`new ConnectorResponse(status, headers, raw)`); the `body` constructor argument is gone, and a non-JSON body is returned as received rather than as `null`. `successful()` is now 2xx *and* no error attached.
- **Breaking:** `LaraflowManager::connector()` gained an optional connection name, and closures passed to `register()` receive a `Connection`. A missing GitHub token is now reported on the first request rather than when the connector is resolved, because the resolved connector holds no credential to check.
- `GithubConnector` extends `HttpConnector` and sends `Accept: application/vnd.github+json`. `ConnectorFactory` and `ConnectorManager` (internal) are replaced by `ConnectorRegistry`. `ConnectorRequest` gains `withOptions()` and `withHeaders()`.
- **Fixed:** the README's custom-connector example registered an authenticator class the package does not ship.

### Milestone 4 — querying, observability, and lifecycle management

Contracts in `docs/inspection-and-observability.md` and `docs/retention.md`.

#### Added

- **Schema for correlation, queue lag, and retention** (existing migration edited in place, per the pre-release policy). `laraflow_workflow_executions` gains:
  - `correlation_id` and `tenant_id` — application-supplied identifiers tying an execution to the request, job, tenant, or external operation that caused it. Indexed columns rather than a metadata blob, because listing by them must stay a bounded indexed query on every supported engine.
  - `dispatched_at` and `available_at` — when the execution was handed to the queue, and when the queue was asked to make it runnable. These differ for a delayed retry, and queue lag (`claimed_at − available_at`) is meaningless without the distinction.
  - `finished_at` — one terminal timestamp written by `completed`, `failed`, and `cancelled` alike, and cleared when an execution runs again. Retention and "finished between" filters would otherwise need a three-way coalesce over `completed_at`/`failed_at`/`cancelled_at` that no index can serve.
  - `payloads_scrubbed_at` — when retention removed the execution's payloads, so a scrubbed record stays distinguishable from one that never carried any.
  - Indexes on `correlation_id`, `tenant_id`, `created_at`, `(workflow, status)`, and `(status, finished_at)`: every listing and retention filter the milestone will expose has an index behind it.
- **`Laraflow\Workflow\ExecutionOptions`** (public): the correlation and tenant identifiers an application records on an execution, supplied as an optional trailing argument to `WorkflowRunner::start()`, `WorkflowRunner::run()`, and `WorkflowDispatcher::dispatch()`. An options object rather than extra parameters so that recording more later does not change four signatures again. Validated at construction, before anything is persisted: trimmed, blank treated as absent (passing a missing request header is safe), rejected over 255 characters (silent truncation leaves an identifier that correlates with nothing), and rejected when containing control characters (these values reach log records, where a newline would let a crafted identifier forge a second line). Violations raise the new public `InvalidExecutionOptionsException`.
- **Identifiers reach every sink.** `WorkflowContext::correlationId()` and `::tenantId()` expose them to steps — read from durable state, so a step re-run by a recovering worker sees the originals rather than whatever ambient context that worker is in — and **all ten lifecycle events** carry them as trailing `correlationId`/`tenantId` properties. They are set at creation and never rewritten; `execute()` has no options parameter, so an execution's identity cannot change under recovery.
- **A stable listing API** on `ExecutionRepository`, so applications and consoles no longer need the internal Eloquent models: `list(ExecutionFilter, $limit, $cursor): ExecutionPage` and `count(ExecutionFilter): int`. `ExecutionFilter` (public) covers workflow(s), status(es), correlation id, tenant id, half-open creation and finish windows (inclusive start, exclusive end, so consecutive windows neither overlap nor leave a gap), and sort direction — and **every criterion is served by an index**, enforced by the migration test; a filter Laraflow cannot bound is a filter it does not offer. Pagination is **keyset**, not offset: the cursor identifies the last row of a page and the next page continues strictly past it, so a listing stays correct while rows are being inserted and costs the same on page 1000 as on page 1. Page size is clamped to `ExecutionRepository::MAX_PAGE_SIZE` (500), a constant on the contract so no implementation can forget the bound; the page reports the limit actually applied. A malformed cursor is rejected rather than guessed at.
- `ExecutionRepository::attemptHistory(WorkflowExecution)`: the attempt history of every step in one query, ordered by step position then attempt, using the execution id the attempts table has denormalised since Milestone 3 for exactly this purpose. `laraflow:show --attempts` moves onto it in step 5.
- **`laraflow:summary`** (experimental): execution counts by status for a scope (`--workflow`, `--correlation`, `--tenant`, `--since`, `--until`), followed by the three conditions worth attention — retries that are due, running steps past their deadline, and the oldest unfinished execution. **Exits non-zero when anything needs attention**, so a scheduler or deploy gate can use it as a health check. Not a per-workflow breakdown: that needs a `GROUP BY` the repository contract does not expose and should not gain for a console view, so `--workflow=` scopes the same numbers through an indexed filter instead.
- **`laraflow:prune`** (experimental): applies the retention policy, with every bound overridable per run (`--scrub-after`, `--prune-attempts-after`, `--delete-after`, `--delete-failed-after`, `--limit`, `--chunk`) and scopable by `--workflow` or `--tenant`. `--dry-run` reports what would go without touching anything. The command **exits non-zero when no bound is configured** rather than reporting a successful no-op — a scheduled prune that silently does nothing is indistinguishable from one that is working, until someone looks at the size of the attempt table. Because deletion is irreversible it uses Laravel's standard production confirmation, as `migrate` and `db:wipe` do, so schedule it as `laraflow:prune --force`; a dry run changes nothing and never asks. Policy warnings are surfaced before acting, a completed run logs its counts (deletions an operator cannot later account for are the ones they will want to account for), and only tiers the operator actually configured appear in the report.
- **Retention engine** (`laraflow.retention.*`, every bound `null` by default), applied by `laraflow:prune` — Laraflow never prunes on its own. Three tiers over finished work, measured from `finished_at` so a long-running execution is never pruned for having *started* long ago:
  - **Scrub** (`scrub_after_days`) clears input, context, and step outputs of `completed` and `cancelled` executions, keeping the record as an audit trail of what ran and when. **Never applied to `failed` executions**, which need their input and context to be re-executable; clearing them would leave a record that still advertises itself as recoverable and is not.
  - **Prune attempts** (`prune_attempts_after_days`) deletes the append-only history that grows without bound under retry policies. Applies to `failed` executions too: the step row keeps the latest attempt's status, error, and counter, and the retry budget reads that counter rather than this table, so nothing becomes unrecoverable.
  - **Delete** (`delete_after_days`) removes `completed` and `cancelled` executions outright; `failed` ones have their own `delete_failed_after_days`, kept separate because discarding recoverable work should be a decision rather than a side effect of configuring general retention.
- Retention guarantees, each covered by test: **only finished work is eligible** — `pending`, `running`, and `retrying` are invisible, since a retry waiting out its backoff is future work, not old work; **the guard is re-applied at every write**, so an execution claimed between scan and write (claiming sets `status = running` and clears `finished_at`) is silently spared, and its steps and attempts are spared with it; **every tier is bounded and self-limiting**, so a scheduled run cannot spend its limit rescanning work it has already done — delete removes the row, scrub requires `payloads_scrubbed_at IS NULL`, and attempt pruning requires that attempt rows still exist. Deletion leaves no orphaned steps or attempts **whether or not the engine enforces the declared cascade**, which SQLite does only when the connection asks. Tiers run delete → prune → scrub so the gentler ones never work on rows about to disappear, and a **dry run predicts the real run exactly**, carrying would-be-deleted ids forward so later tiers do not count work that would never happen.
- `Laraflow\Workflow\RetentionPolicy` (public) validates its bounds at construction — a bound below one day would act on work that finished seconds ago — and `warnings()` reports valid-but-probably-wrong combinations, such as deleting completed work before it would have been scrubbed, or discarding recoverable failed work sooner than completed work.
- **Execution duration is captured at the finishing transition and persisted** (`laraflow_workflow_executions.duration_ms`). It was recomputed from the reloaded timestamps, which hold whole seconds, so `durationMs()` reported 0 ms for any execution that took less than a second — most of them. The attempt history has stored its duration for the same reason since Milestone 3. The claim's compare-and-set clears the recorded duration alongside `finished_at`, so a reclaimed execution does not report a duration for the run it is superseding. `laraflow:show` now displays it.
- **Payload size policy** (`laraflow.execution.max_payload_bytes`, default `null` — no limit), the item `docs/execution-lifecycle.md` deferred to this milestone. Bounds a single durable payload — workflow input, one step's output, or the context snapshot — measured as the JSON that reaches the column, and enforced at the same three boundaries as the type contract: input at `start()` (nothing persisted on rejection), output and context after `handle()` returns and before the checkpoint. Setting it does not turn a success into a failure; it changes where the failure is reported. Without it an oversized payload still fails, but as a driver error about a column or packet size raised from inside the checkpoint transaction; with it, the step fails with the new public `PayloadTooLargeException` naming the path, the actual size, and the limit. Added to `StepPolicy::NEVER_RETRY`: the same step produces the same size, so another attempt could only repeat the outcome. A blank environment value means "no limit", and a limit below 1 is rejected at construction rather than silently rejecting every payload.
- **Structured logging context** (`laraflow.logging.context`, default on). While a step runs, Laravel's log context carries `laraflow.execution_id`, `laraflow.workflow`, `laraflow.step`, `laraflow.position`, `laraflow.attempt`, and — when supplied — `laraflow.correlation_id` and `laraflow.tenant_id`. Every log record the *application* writes from inside a step therefore carries them, with no Laraflow API involved, and because Laravel dehydrates the context into queue payloads, a job a step dispatches inherits them too: one correlation id follows the work across processes. Keys are namespaced so nothing of the application's is clobbered, absent identifiers are omitted rather than written as null, and the context is restored in a `finally` — so a throw, a scheduled retry, or a cancellation all leave it exactly as it was found, and an in-process run cannot leak its execution id into the surrounding request. Nested executions (a step running another workflow synchronously) push and pop frames, restoring the outer execution's keys rather than deleting them.
- **Optional lifecycle log** (`laraflow.logging.lifecycle`, default off): one record per lifecycle event, registered as a wildcard listener on `Laraflow\Events\*` so an event class added later is logged without code changes. Terminal failures log at `error`, failed attempts and scheduled retries at `warning`, everything else at `info` — matching the guidance to alert on `WorkflowExecutionFailed` rather than on every attempt. The record's context is the event's own public properties, which is safe by construction: events carry identifiers and metadata only, and any error message has already passed the configured redactor.
- Dependency: `illuminate/log` (the context repository), already present transitively and now declared.
- **Durations on lifecycle events.** `WorkflowStepCompleted` and `WorkflowStepFailed` carry `durationMs` for the attempt — the same `StepAttempt` record that goes to history feeds the event, so telemetry and history can never disagree about how long a step took. `WorkflowExecutionCompleted`, `WorkflowExecutionFailed`, and `WorkflowExecutionCancelled` carry `durationMs` from the execution's **first** start to this finish: end-to-end latency, deliberately including time spent failed or backing off between retries, which is what an SLA measures. Null when the execution never started (a `pending` execution cancelled outright); zero is a measured zero, not an absence. `WorkflowExecution::durationMs()` exposes the arithmetic.
- **`ExecutionStatus::isFinished()`** and `WorkflowExecution::isFinished()`: true for `completed`, `failed`, and `cancelled` — the states that record `finished_at`. Named for "has stopped", **not** `isTerminal()`: in Laraflow "terminal" means never claimable again (`completed`, `cancelled`) and `failed` is re-executable by design, so conflating them would let the retention work in step 10 either skip failed executions forever or delete work a worker still owns.
- **Queue lag.** Every dispatch records `dispatched_at` and `available_at` on the execution (the same instant for an ordinary push; the due time for a delayed retry), and `WorkflowExecutionStarted` gains `queueLagSeconds`: the wait from availability to the claim. Measured from *availability*, not dispatch, so a retry's own backoff is never counted as time waiting for a worker. Null when the execution was never dispatched or was claimed ahead of availability — running early is not a wait of zero. `laraflow:show` reports *Dispatched*, *Available* (only when it differs — a delayed retry), and *Queue wait*, open-ended while pending and exact once claimed. The dispatch is recorded before the job is pushed, so the `sync` driver sees it too. `WorkflowExecution::queueLagSeconds(DateTimeImmutable $claimedAt)` exposes the arithmetic. Specified in `docs/queue-and-recovery.md`.
- `WorkflowExecution` gains `correlationId`, `tenantId`, `dispatchedAt`, `availableAt`, `finishedAt`, and `payloadsScrubbedAt`. `markCompleted()`, `markFailed()`, and `markCancelled()` set `finishedAt`; `markRunning()` clears it, so a re-executed failure cannot look eligible to retention while a worker is running it. The claim and the compare-and-set cancellation path make the same writes directly.

- **`tests/Feature/ProjectContractsTest.php`**: holds the documentation and the code to each other. Every class, configuration key, command, command option, publish tag, and cross-reference the documentation names must exist, and the invariants it promises must hold — no console command reaching past the public contract, every lifecycle event carrying the correlation identifiers, every never-retried exception named in the retry contract, every shipped default being the documented one.

#### Decisions

- **Correlation is two indexed columns, not a metadata blob.** A JSON column cannot be indexed portably across the four supported engines, and bounded listing was an exit criterion.
- **Metrics are enriched events, not a metrics contract.** Durations and queue lag ride on the lifecycle events; the documentation gives Prometheus, StatsD, and Pulse recipes. Shipping no vendor integration is how "assumes no particular monitoring vendor" was met.
- **Queue lag is measured from availability, not dispatch.** A delayed retry's backoff is not time spent waiting for a worker.
- **`isFinished()`, not `isTerminal()`.** "Terminal" already means never-claimable (`completed`, `cancelled`); `failed` is re-executable yet has finished. Conflating them would let retention either skip failed work forever or delete work a worker owns.
- **No write-time payload redaction.** Input seeds the context on every `execute()` and context is restored on recovery, so rewriting either would corrupt re-runs. Post-finish scrubbing is offered instead.
- **Retention never scrubs failed executions, and deletes them only under their own bound.** Re-executing one needs its input and context. Attempt pruning does cover them, because the retry budget reads the step row's counter rather than the history table; the diagnostics that costs are stated as a trade-off in `docs/retention.md`.
- **Every console command runs on the public contract.** No command touches an Eloquent model, and a test reads each one's source to keep it that way. Where the contract lacked a read a command needed — step counts for a page — the contract gained it rather than the command reaching around it.
- **`ExecutionRepository` stays one interface.** Splitting it into persistence, query, recovery, and retention interfaces would widen what a custom implementation must know about for the benefit of three internal consumers; the Eloquent implementation is organised by concern instead.
- **The dispatch is recorded before the queue push.** Required for the sync driver to measure its own wait; the consequence — a failed push leaves dispatch timestamps for a job that never existed — is documented in `docs/queue-and-recovery.md`, and is the case the recovery scan's `pending_after` option covers.

#### Changed

- **Internal structure, following a milestone-wide review:** `WorkflowRunner` (894 lines, twelve constructor arguments) was split — `StepResolver` for definition validation and step construction, `OutcomeRecorder` for the four outcome-persistence paths and the error-redaction chokepoint, `RunnerOptions` for its configured settings — leaving 512 lines with one job. `RetentionService` carries its per-run state in `RetentionRun`. `EloquentExecutionRepository` is organised into `QueriesExecutions`, `ScansForRecovery`, and `AppliesRetention` concerns. `Support\Duration` holds the arithmetic `StepAttempt` and `WorkflowExecution` shared. No behaviour changed; the suite that pinned every property passed untouched through each step.
- **Fixed:** `laraflow:summary --tenant=` reported every tenant's due retries alongside one tenant's counts, and failed its health check because of them. **Fixed:** `laraflow:prune` rejected a malformed `--limit` or `--chunk` as "a number of days".
- **Breaking:** `ExecutionRepository::create()` gained a trailing optional `?ExecutionOptions $options`. Custom implementations must accept and persist it; implementations that ignore it silently drop the identifiers an application supplied.
- **`laraflow:list` runs on the public query API** and no longer touches the internal Eloquent models, gaining `--workflow`, `--correlation`, `--tenant`, `--since`, `--until`, `--cursor`, and `--oldest`; `--status` and `--workflow` are repeatable. It reports how many of the matching set the page showed — a bounded page that does not say so looks like the whole truth — and prints the command that continues it, carrying the current filter forward so following the hint cannot silently widen the query. A malformed cursor and an unparseable time are both refused with guidance rather than guessed at. `laraflow:show` gains the correlation and tenant identifiers, reads its "Finished" row from `finished_at` (so cancellation is reported like completion and failure), and reads attempt history in one query instead of one per step.
- **Breaking:** `ExecutionRepository::dueForRetry()` gained a trailing optional `?string $tenantId`. Without it `laraflow:summary --tenant=acme` reported every tenant's due retries alongside acme's counts, and failed its health check for another tenant's work.
- **Breaking:** `ExecutionRepository::stepProgress(array $ids)` was added: step counts for many executions in one query. `laraflow:list` showed per-execution progress with one `steps()` call per row; a listing must not cost a query per row, and adding the method now folds it into this milestone's contract change instead of making it a fresh one later.
- **Breaking:** `ExecutionRepository` gained four retention methods — `retentionCandidates()`, `scrubPayloads()`, `pruneAttempts()`, `deleteExecutions()`. Custom implementations must add them and honour three contract obligations: each scan must apply its tier's self-limiting predicate, every write must re-apply the status and `finished_at` guard in the same statement, and `deleteExecutions()` must leave no orphaned child rows without relying on database cascades.
- **Breaking:** `ExecutionRepository` gained `recordDispatch(id, dispatchedAt, ?availableAt)`. Custom implementations must add it; an implementation that ignores it leaves `queueLagSeconds` permanently null and `laraflow:show` silent about queue timing. It must not be claim-guarded, and must treat an availability earlier than the dispatch time as the dispatch time.
- **Breaking:** `ExecutionRepository` gained three methods — `list()`, `count()`, `attemptHistory()` — and the `MAX_PAGE_SIZE` constant. Custom implementations must add them. Each must honour the contract's bounds: `list()` may never return more than `MAX_PAGE_SIZE` rows and must paginate by keyset in the filter's direction; `count()` counts the whole matching set regardless of pagination.
- **Fixed:** documentation that had drifted behind Milestone 3 — the README described two tables (there are three) and listed only the four original execution statuses; `SECURITY.md` still cited "there is currently no retry limit" as unimplemented hardening and promised that "future" events and logging would redact step data, both of which shipped; `CONTRIBUTING.md` still gated contributions on Milestone 1; and `docs/queue-and-recovery.md` disagreed with `docs/public-api.md` about which events fire once per execution.

### Milestone 3 — retry, timeout, and failure policy

#### Added

- **Per-step retry policy** (`Laraflow\Workflow\Policy\StepPolicy`, public): total attempt budget, exponential backoff capped at `max_delay`, `retryOn`/`dontRetryOn` matched by `instanceof`, and a per-attempt timeout. Declared on a step via the optional `HasStepPolicy` interface, on a workflow via `defaultStepPolicy()`, or globally via `laraflow.retry.*` — resolved in that order, **per step**, so one slow step can out-declare its siblings. **Retries ship disabled** (`retry.max_attempts` = 1), consistent with `queue.tries` and `recovery.pending_after`.
- **`retrying` state** on executions and steps, carrying a durable `next_retry_at`. A retryable failure persists the failed attempt, schedules the next one, releases the claim, and **returns** from `execute()` — nothing is thrown, nothing reaches `failed_jobs`, and `WorkflowExecutionFailed` does not fire, so alerting built on failures stays meaningful. Terminal failures keep the Milestone 1/2 contract unchanged.
- **Deterministic schedules.** Backoff jitter is derived by hashing the execution id and step position with the attempt number rather than drawn from randomness, so one logical retry always lands on the same instant. When the jitter window would cross `max_delay` it slides down to fit rather than being clipped — clipping bunched roughly half of all executions onto exactly the ceiling, in precisely the case jitter exists to prevent.
- **PSR-20 clock** (`psr/clock`, already a transitive dependency) injected through the runner, repository, and recovery service; the default binding wraps Laravel's `Date` facade, so `Date::setTestNow()` still governs every timestamp.
- **Two delivery paths for a due retry.** `ExecuteWorkflowJob` queues a delayed redelivery for `next_retry_at` (`retry.dispatch_delayed`, skipped on the `sync` driver where `delay()` is ignored and backoff would become immediate recursion), and `laraflow:recover` gains a due-retry scan — the *contractual* pickup, needing no queue and catching anything the fast path loses.
- **Append-only attempt history** (`laraflow_step_attempts`): every finished attempt keeps its outcome (`completed`, `failed`, `timed_out`, `interrupted`), error, timestamps, duration, and scheduled retry. Rows are written in the same transaction as the step state change they describe, so history can never disagree with it — including rolling back together on claim loss — and a unique `(step_execution_id, attempt)` index stops a duplicate delivery double-counting an attempt. Read via `ExecutionRepository::attempts()` or `laraflow:show --attempts`.
- **Step deadlines.** A policy's `timeoutSeconds` is persisted as `timeout_at` *before* `handle()` runs (a dying worker writes nothing, so the deadline must already exist) and exposed via `WorkflowContext::deadline()`/`remainingSeconds()`. Laraflow does not preempt running PHP; classification happens at the recovery boundary, giving the three-way distinction the roadmap asked for: a thrown failure, worker loss before the deadline (free re-run, recorded `interrupted`), and an overrun attempt (recorded `timed_out` with `StepTimeoutException`, charged to the retry budget).
- **Cancellation.** `WorkflowRunner::cancel()` and `laraflow:cancel {execution} {--reason=}`. Immediate and atomic for `pending`/`failed`/`retrying` — using the same compare-and-set predicate as claiming, so it cannot race a worker — voiding any scheduled retry. Cooperative for `running`: the owning worker stops at its next step boundary, so the step in flight finishes and checkpoints. `cancelled` is terminal and refused by `claim()`, `execute()`, `dispatchExecution()`, and recovery; repeat cancellations are idempotent no-ops.
- **Error redaction.** `laraflow.errors.redactor` names an `ErrorRedactor` applied at one chokepoint before any exception message is persisted, logged (the failed-job hook included, which previously logged raw messages), or emitted. The exception the application catches is untouched; a misconfigured class fails loudly rather than silently leaking.
- **Continue-on-failure.** `Workflow::failurePolicy()` returning `FailurePolicy::Continue` runs the remaining steps after a terminal step failure; the execution still ends `failed` and rethrows the first exception. Retry policy takes precedence over continuing. For independent steps only — later steps see no contribution from the failed one.
- **Events:** `WorkflowStepRetryScheduled` (attempt, budget, error class and message, due time, delay) and `WorkflowExecutionCancelled`; `WorkflowExecutionRetryScheduled` gains `retry_due` and `step_timeout` reasons.
- **Console:** `laraflow:execute --now`; `laraflow:show --attempts` plus retry schedule, cancellation detail, per-step next-retry, and an `(overdue)` marker on a running step past its deadline; `retrying`/`cancelled` colours and `laraflow:list` filtering.
- `docs/retry-and-failure-policy.md` specifying all of the above, and behavioural suites covering scheduling, due-gated claiming, queue delivery (against a real driver and `queue:work` worker), timeouts, cancellation, failure policy, redaction, and console output.
- Schema (existing migrations edited in place, per the pre-release policy): executions gain `next_retry_at` with a `(status, next_retry_at)` index, `cancel_requested_at`, `cancelled_at`, `cancel_reason`; steps gain `failed_at` and `timeout_at`; new `laraflow_step_attempts` table.

#### Changed

- **Breaking:** `ExecutionRepository` — `claim()` gains `$ignoreRetrySchedule` and refuses a not-due `retrying` execution with `RetryNotDueException`; `saveStep()`/`checkpoint()` take an optional `StepAttempt`; `attempts()`, `dueForRetry()`, and `requestCancellation()` added; `release()` now also covers the `retrying` and `cancelled` transitions.
- **Breaking:** `laraflow.recovery.max_attempts` renamed `laraflow.recovery.abandon_after_attempts` (`--max-attempts` → `--abandon-after`). With `retry.max_attempts` now existing as the failure budget, two same-named knobs with different scopes invited operators to confuse crash-loop protection with retry policy. The bounds are deliberately independent: due retries are exempt from the abandonment bound, whose job is interruption recovery.
- **Breaking (behavioural, opt-in):** with a retry policy enabled, `execute()`/`run()` can return a non-terminal `retrying` execution instead of throwing. Under the shipped defaults, behaviour is unchanged.
- **Fixed:** `StepExecution::markFailed()` accepted a timestamp and discarded it, so a failed step had no record of when it failed; it is now persisted to `failed_at`.
- **Fixed:** a declared-but-empty environment variable (`LARAFLOW_RETRY_MAX_ATTEMPTS=`) cast to `0` and was rejected by policy validation, turning a stray blank line in `.env` into an application that could not resolve the runner. Blank now means "use the default".
- **Fixed:** `laraflow:list --status` help text listed only the four original statuses. It and the invalid-status error now derive from the enum.
- `composer playground` runs `migrate:fresh`. Because migrations are edited in place before the schema freeze, an existing playground database silently missed new columns.
- The test suite enforces SQLite foreign keys, which the schema has declared since Milestone 0 but no test had exercised.

### Milestone 2 — queue execution and operational recovery

#### Added

- `Laraflow\Queue\WorkflowDispatcher` (public): `dispatch(Workflow, $input, ?connection, ?queue)` creates an execution and queues it; `dispatchExecution(id, ...)` queues an existing one for retry or recovery. Queue concerns live here rather than on `WorkflowRunner`, which keeps no queue dependency.
- `Laraflow\Queue\ExecuteWorkflowJob` (public): the queued job. Its payload carries **only the execution id** — the workflow class is read from the execution record, so a job can never disagree with durable state, and no workflow input reaches the queue backend.
- Eight lifecycle events in `Laraflow\Events` (public, `readonly`): `WorkflowExecutionDispatched`, `WorkflowExecutionStarted`, `WorkflowStepStarted`, `WorkflowStepCompleted`, `WorkflowStepFailed`, `WorkflowExecutionCompleted`, `WorkflowExecutionFailed`, `WorkflowExecutionRetryScheduled`. Each fires strictly after the durable write it describes.
- `laraflow:recover` command: finds interrupted executions (stale claims, and optionally never-dispatched pendings) and retries them, with `--dry-run`, `--sync`, `--limit`, `--max-attempts`, `--stale-after`, `--pending-after`, and `--workflow`. Exits non-zero when work was abandoned or an action failed, so a scheduled run surfaces stuck work through existing alerting.
- `--queue` on `laraflow:execute` and `laraflow:demo`.
- `ExecutionRepository::stale()` and `::pendingBefore()`: bounded, clock-free scans for recoverable work. `stale()` uses the same `claimed_at <= cutoff` comparison as `claim()`, so scanning and claiming cannot disagree about staleness.
- Configuration: `queue.*` (`connection`, `queue`, `tries`, `backoff`, `timeout`, `after_commit`), `recovery.*` (`limit`, `max_attempts`, `pending_after`), and `events.include_error_messages`.
- `docs/queue-and-recovery.md` specifying dispatch, the retry decision, duplicate-delivery semantics, recovery policy and bounds, and event payload safety.
- End-to-end coverage in `tests/Feature/Queue/QueueRecoveryTest.php` using a real database queue driver and a real `queue:work` worker, rather than `Queue::fake()`: async completion, crash-to-recovery from a checkpoint, duplicate deliveries, the abandonment bound, and the absence of retry multiplication.
- Dependencies: `illuminate/bus`, `illuminate/queue`, `illuminate/events`, and `illuminate/console` (the last was already used by the existing commands but never declared).

#### Decisions

- **The queue does not retry by default** (`queue.tries` defaults to 1). Queue retries and Laraflow step attempts would otherwise multiply on two unrelated schedules. Re-running a failed execution is an explicit operation until per-step retry policy arrives in Milestone 3.
- **Duplicate deliveries are no-ops, not failures.** The existing compare-and-set claim is the only authority; `ExecutionAlreadyClaimedException`, `ExecutionNotRunnableException`, and `ClaimLostException` are caught and logged so the job succeeds. No cache lock or `ShouldBeUnique` is involved.
- **Recovery is bounded by step attempts.** An execution whose steps reached `recovery.max_attempts` is reported as abandoned rather than re-dispatched, so a crash-looping workflow cannot be retried forever by the scheduler. The bound reuses durable `attempts`, so Milestone 2 required **no migration**.
- **Recovery refuses executions whose workflow class is gone** (reported as *unrecoverable*, exit code 1). A retry of a missing class fails before any step runs, so attempts never increment and the attempt bound alone could never stop a scheduled re-dispatch loop.
- **Recovery of `pending` executions is opt-in** (`recovery.pending_after` defaults to null). `pending` is also the state of work created with `start()` and deliberately not yet run; recovery must not start that behind the application's back.
- **Events never carry input, output, or context**, with no opt-in. Failure events carry the exception class and, unless `events.include_error_messages` is disabled, the truncated message — data the execution record already holds.
- **Event listeners are observational**: a throwing listener is logged and swallowed rather than altering execution state, aborting a dispatch, or masking a step's exception. Listeners needing retry semantics should be queued listeners.

#### Changed

- `WorkflowRunner` takes two optional trailing constructor arguments (an internal event emitter and an error-message flag). Construction is internal wiring; resolve the runner from the container.
- `laraflow:execute` now resolves the recorded workflow class through a shared resolver and, with `--queue`, validates it *before* queueing, so a missing class fails at the console rather than minutes later on a worker.
- README gained a "Running on a queue" section; its configuration sample now reflects every shipped key, and "Current limitations" has been rewritten for the post-Milestone-2 state.

### Milestone 1 — execution lifecycle and recovery

#### Added

- `WorkflowRunner::start()` creates an execution and its **full step plan** up front, atomically, without running anything; `WorkflowRunner::execute()` claims an execution and runs every non-completed step, serving both first execution and recovery through a single code path.
- Compare-and-set execution claiming with per-worker claim tokens: only one worker can own an execution; `running` executions with a claim older than `laraflow.execution.stale_after` (default 300s) can be reclaimed after worker loss. Checkpoints and terminal writes verify the claim, so a superseded worker gets `ClaimLostException` instead of corrupting state.
- Transactional checkpoints: each completed step's output and the full context snapshot commit together; the context is restored from durable state on recovery, so later steps see earlier results without re-running them.
- Enforced execution and step state machines via `mark*()` transition methods (`InvalidStateTransitionException` otherwise), documented in `docs/execution-lifecycle.md` together with the full crash-boundary and at-least-once contract.
- Workflow-definition validation on `execute()`: a changed workflow class or step list raises `WorkflowDefinitionMismatchException` instead of silently reinterpreting durable state.
- Serialization contract enforcement: workflow input, step outputs, and context values must be JSON-serializable; violations raise `UnserializableValueException` naming the offending key. Input is validated before anything is persisted.
- Idempotency hooks on `WorkflowContext`: `executionId()`, `stepPosition()`, `attempt()`, and `idempotencyKey()` (stable across retries of the same logical step).
- Robust failure persistence: step failures store the exception class and truncated message (`laraflow.execution.max_error_length`) on both step and execution; if persisting the failure itself fails, the storage error is logged and the original exception still propagates.
- Workflow exception hierarchy under `Laraflow\Exceptions\Workflow`.
- Schema: executions gained `context`, `error`, `error_class`, `claim_token`, `claimed_at`, and status indexes; steps gained `error_class`. (Existing migrations edited in place per the pre-release schema policy.)
- Recovery test suite simulating worker death at every persistence boundary, claim contention, stale takeover, definition drift, serialization violations, and failure-persistence failure.

#### Changed

- **Breaking:** `WorkflowRunner::run()` now returns the `WorkflowExecution` handle instead of the `WorkflowContext`, and accepts workflow input that seeds the context (rationale in `docs/public-api.md`).
- **Breaking:** `WorkflowRunner::resume()` is removed; call `execute()`.
- **Breaking:** `ExecutionRepository` contract reworked: `create()` now takes the step plan; `claim()`, `checkpoint()`, and `release()` added; `save()` and `createStep()` removed. `find()` throws `ExecutionNotFoundException` instead of Eloquent's `ModelNotFoundException`.
- A step found `running` during recovery is treated as interrupted and re-runs (the documented at-least-once boundary); `started_at` now records the first start and survives re-execution; completing clears a previous error.

### Milestone 0 — contracts and packaging

#### Added

- Package migrations are now loaded automatically by the service provider, with an opt-out via `laraflow.migrations.load` / `LARAFLOW_LOAD_MIGRATIONS`.
- `laraflow-migrations` publish tag for applications that want to manage the migrations themselves.
- Package metadata: license, keywords, support links, `illuminate/database` dependency, `composer test` script.
- Documentation: installation and usage README, public API and stability levels (`docs/public-api.md`), compatibility and support policy (`docs/compatibility.md`), contributing guide, security policy, this changelog.
- `.gitattributes` enforcing LF line endings.

#### Changed

- The service provider now merges the package configuration (`mergeConfigFrom`), so `config('laraflow.*')` has defaults without publishing.
- The GitHub connector token is cast to a string when the configuration value is missing, so resolving the connector no longer raises a `TypeError`; requests without a token will fail at the GitHub API instead.
